## 3. 关键结论：护栏防范的风险未被复现

护栏注释原文（`sync_daemon_runner.py:85`）：

> 「云端护栏：若 openworker-server 在跑，双写会抢锁，拒绝启动。」

压测结论：

1. **「抢锁」未发生** —— WAL 允许一写多读，写写由 `busy_timeout=5000` 兜住，实测 `SQLITE_BUSY = 0`；
2. **「双写丢数据」未发生** —— 25,868 笔写入全部落库，且**全部被触发器捕获进 oplog**（这正是阶段 2 的设计意图，实测 100% 生效）；
3. **「双写产生重复/不一致」未发生** —— dup_fp = 0。

> 换言之：**app 写与同步写并非两股敌对力量，而是都经由触发器汇入同一个 append-only oplog——天然收敛。**

## 4. 过程中发现的问题（均为压测工具自身缺陷，非产品缺陷）

诚实记录，便于复现者避坑：

1. **`mp.Queue` 死锁**：首版用 `q.put()` 回传结果，高频写入填满管道缓冲后 worker 永久阻塞在 `futex_wait_queue`（首轮跑完 8 分钟不退出）。改为**每 worker 各写一个 JSON 文件**后正常。
2. **`id` 列类型误判**：`learned_history.id` 是 INTEGER 自增主键，首版传字符串触发 `IntegrityError: datatype mismatch`，导致 app 写入全失败而报告 `ok=0`。
3. **写入 `root` 属主**：隔离库由 root 创建，`openworker` 无法写入。
4. **判定谓词写错**：把标记写进 `entity` 列却按 `source` 查询，导致 `facts_delta=0`、误报 `lost=true`；按 `entity` 重查实为 25,868 行，**无丢失**。

> 这些均属测试脚本问题，**生产代码未受影响**。

## 5. 为什么本报告不直接建议"删护栏"

压测通过 ≠ 可以立刻删。三点保留：

1. **压测用隔离副本，未覆盖真实后端负载形态**：真实 `openworker-server` 除业务表外还会写 `chat.db`/`journal.db`/`cognitive.db` 等**多个库**，并可能有长事务；本压测只覆盖 `deskmate.db` 单库。
2. **60s 未覆盖 WAL checkpoint 压力窗口**：本轮 max 延迟 180ms、WAL 曾涨到 16MB；长跑需验证 checkpoint 期间的表现。
3. **护栏是阶段 1 的产物，但删除是不可逆的架构决策**——应保留可回滚路径。

#### 修正记录（2026-10-04 21:2x，闭环复验后）

本节原据此推断「护栏所防范的风险已被充分证伪 → 可以删除」。**该推断犯了一个维度错误**：

- 本节只证明了**数据层**——SQLite 在 WAL + busy_timeout 下并发双写**不丢数据**；
- 护栏防的是**运行态**风险——两个**独立进程**同时认为自己该写生产库（双主语义冲突）；
- **数据层无丢失 ≠ 运行态无冲突**。二者不是同一件事，前者不是后者的充分条件。

更关键的是，闭环复验 C 项（2026-10-04 21:20）在**进程级 + 多库级**实测出了本节未覆盖的风险：

```
BACKEND: ok=114,      busy=12     # 后端 180 秒仅写成功 114 次
DAEMON : ok=433,049,  busy=0      # daemon 写 43 万次 —— 相差约 3800 倍
```

原因：SQLite WAL **只允许一个写者且不保证公平**，紧循环的 daemon 几乎常占 `deskmate.db` 写锁，把后端**饿死**（busy=12 即等满 5s 超时回滚）。

**这是安全行为（无丢失），但是吞吐/延迟行为**——若两者真同库常驻，轻量一方会被饿到高延迟甚至超时。**这正是护栏要防的场景，故护栏应保留。**

详见 `2026-10-04_阶段5_双写压测_闭环复验.md` §10.4② / §10.5。

**结论**：护栏所防范的风险，在 WAL + busy_timeout=5000 + 触发器捕获这一技术前提下**已被充分证伪**。

**根因判断（对架构设计的启示）**：护栏写于阶段 1，当时**尚无 WAL、无触发器捕获**——那时 app 写与同步写确实是两股敌对力量。阶段 2 落地触发器后，app 的每次写入都会汇入同一个 append-only `_sync_oplog`，**双写变成了「同一 oplog 的汇聚」而非「两写者的争抢」**。护栏是在用**过期的前提**限制今天的能力。

## 9. 阶段 5 下一阶段的前置项：写饥饿（来自闭环复验 §10.4②）

> **这不是「别删护栏的理由」而已，而是后端常驻时的真实性能风险**，需在阶段 5 单独解决。

### 9.1 问题

```
BACKEND: ok=114,     busy=12    # 后端 180 秒仅写成功 114 次
DAEMON : ok=433,049, busy=0     # 同步 daemon 写 43 万次 —— 相差约 3800 倍
```

SQLite WAL **只允许一个写者持有写锁，且不保证公平**。紧循环写单一库的 daemon 几乎常占 `deskmate.db` 写锁，把后端**饿死**；后端每轮还要额外提交 chat/journal/cognitive 三库，被持续压制。`busy=12` 是等满 5s `busy_timeout` 后放弃回滚，属正常兜底、**非错误、非数据丢失**。

**性质**：这是**吞吐/延迟行为**，不是数据安全问题。

### 9.2 为什么必须在阶段 5 之前解决

若按原计划让 `openworker-server` 与 `xiaoju-sync` 同机常驻：

- 后端的写入延迟可能被推到秒级甚至超时 → **她"想记一笔"经常写不进去**；
- 用户体验上表现为「她偶尔失忆 / 记不住」，且**极难归因**（不像报错那样显眼）；
- 且此风险**不会触发任何告警**（daemon 自报 `ok=True`，与此前 401盲区同类问题）。

### 9.3 候选方案（择一，需萧哥拍板）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A · 错峰常驻** | 后端常驻；同步 daemon 改 systemd timer 定期跑（如每小时几分钟），非常驻 | 冲突面最小；改配置即可，可回滚；不碰代码 | 记忆同步从秒级降为小时级 |
| **B · 写节流** | 保留两进程常驻，给同步 daemon 写循环加间隔/批量 | 同步仍近实时 | 需改 daemon 逻辑；节流不够则仍可能饥饿；**需先做公平性实验** |
| **C · 删护栏共存** | 直接移除互斥 | — | **已被 §10.4② 实测否决**：饥饿风险原样保留 |

**我的建议：A（错峰常驻）**。它用配置换掉风险，与 §7.4 兜底路径一致；B 需要改代码且有效性未经验证。

### 9.4 若选 A，后端常驻的完整方案

```bash
# 窗口内（默认）：只跑后端，她随时在线
sudo systemctl start openworker-server

# 同步改为定时任务（错峰窗口内短暂停后端或直接跑 daemon）
sudo systemctl stop  openworker-server
sudo systemctl start xiaoju-sync
sudo systemctl stop  xiaoju-sync
```
