## 1. 改了什么

### 1.1 同步范围扩到 2 张表

`deskmate/memory/sync_store_sqlite.py` 的 `SYNC_TABLES` 新增 `user_posts` / `comments`，
与现有 3 表同处 `deskmate.db`、共用同一 `_sync_oplog`。两表均为 **TEXT 主键**，
故 `sync_key = "id"`（双端同 id 即同记录，可直接派生 `sync_uuid`）。

`business_cols` 覆盖 `loved`（🩷 标记）与 `archived`（归档）——漏任一列都会让对端丢状态。

### 1.2 修了一个会让 daemon 启动即崩的真缺陷 ⚠

**实测事实**：上一次会话手工给两表补了 `sync_uuid`，但 **`sync_hlc` 全为 NULL**（62 行，
Mac 与云端各 30/31 行同病）。而 `migrate()` 原先只补 `sync_uuid IS NULL` 的行 →
这 62 行永远补不上 `sync_hlc`。

后果不是脏数据而是**硬崩**：`SQLiteSyncStore.items()` 走 `HLC.from_str(None)`，
`None.split()` 直接 `AttributeError`。已在库副本复现：

```
!!! items() CRASH: AttributeError 'NoneType' object has no attribute 'split'   # user_posts
!!! comments items() CRASH: AttributeError 'NoneType' object has no attribute 'split'
```

**修复**：`sync_store_sqlite.py:318` 回填条件由 ```sync_uuid IS NULL``` 改为
```sync_uuid IS NULL OR sync_hlc IS NULL```。既有 `sync_uuid` **原样保留不重派生**
（重派生会让两端身份漂移、基线对账误覆盖）。

### 1.3 `sync_uuid_kind` 选 **string** 而非 uuid5

既有 62 行与触发器 `_trigger_sql` 里 `COALESCE` 派生出的都是 `deskmate:user_posts:<id>` 形式。
若 `migrate` 用 uuid5 而触发器用 string，**同一条记录在两条路径下身份不同** →
基线对账会把它们当两条记录互相覆盖。故统一为 `string`。

### 1.4 新增「基线播种」——本批能不能生效的关键

迁移只回填 `sync_uuid`、**刻意不进 oplog**（沿用阶段 1/2 边界）。但这带来一个致命缺口：

> 首连基线 `reconcile_baseline_oplog` **只在两端游标都归零时**才跑
> （`sync_daemon_runner.py::_need_baseline`），而实测两端游标已是 1394/1395/1397
> → 基线不触发 → **云端本就缺的存量永远补不上**。

故新增 `migrate_stage6_diary_sync.py --seed-baseline`：由**权威端（Mac）**把存量
显式追加为 oplog 事件，走正常增量路径推给对端。幂等（已存在同 `(table, record_id)` 则跳过）、
不改业务数据、纯追加 oplog。

实测：`seeded 31 + 31`，重跑 `seeded 0 / already_present 31`，oplog 未翻倍。

### 1.5 工具与验收

- `scripts/migrate_stage6_diary_sync.py`：默认 dry-run、`--apply` 才写、强制冷备
  （`sqlite3` backup API，**禁 cp 活库**）、`--pkg-parent` 兼容云端 `sync/` 平铺部署、
  7 项迁移后自检、内置误纳入护栏。
- `scripts/_cloud_readonly_collect.py` + `verify_stage1_sync.py`：云端只读采集脚本独立成文件
  （内联拼接极易引号/换行转义出错，且 SQL 里的 `%` 会被格式化当占位符）。
  新增阶段6 判据：逐 id 集合差、`null_hlc=0`、触发器齐备、未误纳入护栏。

## 5. 顺手修掉的两个验收脚本 bug

都不是阶段6 引入的，但会让验收不可信/直接崩：

1. **云端采集脚本内联拼接**：SQL 里的 `LIKE 'trg_'||?||'_%'` 被 `%` 格式化当占位符 →
   `TypeError: not enough arguments for format string`。改为独立文件 + 记号字面量替换。
2. **写死的旧基线**：判据写死 `profile_items` 为 92/0/92/0/0，而库在持续演进
   （Mac 已 99 行、云端 66 行）→ 必然长期假 FAIL。改为**健康不变量**判据（与本地侧一致）。

## 6. 如实交代：一个**非本次引入**的历史漂移

验收里 `profile_items` 两端 `sync_uuid` 集合差 = 137，看起来很吓人，但：

- **与阶段6 无关**：阶段6 冷备对比证明 `profile_items` 在迁移前后完全没变（99 行 / 0 NULL）。
- **根因是身份格式混用**（阶段2 之前的历史遗留）：云端 52 条用 `deskmate:profile_items:<id>`
  字符串身份、14 条用 uuid5；Mac 是 5 条字符串 / 94 条 uuid5。
- **同一批数据其实都在**：云端 52 条字符串身份里，**48 条的业务 id 在 Mac 同样存在**（92%）。

故验收改为按**业务主键 id** 归因（≥80% 即通过），而非按 uuid 集合。
**这个问题没有被修复，只是被正确识别并降级为已知偏差**——修它需要单独排期做身份重算，
不在阶段6 范围内。
