## 1. 改了什么

### 1.1 同步范围扩到 2 张表

`deskmate/memory/sync_store_sqlite.py` 的 `SYNC_TABLES` 新增 `user_posts` / `comments`，
与现有 3 表同处 `deskmate.db`、共用同一 `_sync_oplog`。两表均为 **TEXT 主键**，
故 `sync_key = "id"`（双端同 id 即同记录，可直接派生 `sync_uuid`）。

`business_cols` 特意覆盖了 `loved`（🩷 标记）与 `archived`（归档）——
漏任一列都会让对端丢失状态（实测 `archived` 是 UI 直接 `UPDATE` 的列）。

### 1.2 修了一个会让 daemon 启动即崩的真缺陷 ⚠

**实测事实**：上一次会话手工给两表补了 `sync_uuid`，但 **`sync_hlc` 全为 NULL**（62 行）。
而 `migrate()` 原先只补 `sync_uuid IS NULL` 的行 → 这 62 行永远补不上 `sync_hlc`。

后果不是"脏数据"而是**硬崩**：`SQLiteSyncStore.items()` 走 `HLC.from_str(None)`，
`None.split()` 直接 `AttributeError`。已在副本上复现：

```
!!! items() CRASH: AttributeError 'NoneType' object has no attribute 'split'   # user_posts
!!! comments items() CRASH: AttributeError 'NoneType' object has no attribute 'split'
```

**修复**：`sync_store_sqlite.py:318` 的回填条件由
```sync_uuid IS NULL``` 改为 ```sync_uuid IS NULL OR sync_hlc IS NULL```。
既有 `sync_uuid` **原样保留不重派生**（重派生会让两端身份漂移，基线对账误覆盖）。

### 1.3 `sync_uuid_kind` 选 **string** 而非 uuid5

上批已落库的 62 行用的是 `deskmate:user_posts:<id>` **字符串**形式，且触发器模板
`_trigger_sql` 里补列的 `COALESCE` 表达式派生的也是同一形式。
若 `migrate` 用 uuid5、触发器用 string，则**同一条记录在两条路径下身份不同**——
基线对账会把它们当两条记录互相覆盖。故统一为 `string`（与 `learned_history` 同策）。

### 1.4 新增迁移工具 `scripts/migrate_stage6_diary_sync.py`

默认 **dry-run**（只体检不写库），`--apply` 才执行；执行前强制冷备
（`sqlite3` backup API，**禁 cp 活库**——WAL 下 cp 会拿到撕裂快照），
内置误纳入护栏（断言 `interview_sessions` 不在注册表）与迁移后 7 项自检。

### 1.5 验收脚本 `scripts/verify_stage1_sync.py` 扩判据

新增：① 两表同步身份完整性（**含 `null_hlc=0`**，比阶段 2 更严）；
② 两表捕获触发器齐备（缺则 app 直写永不上云）；
③ **未误纳入护栏**（`interview_sessions` 触发器必须为 0）；
④ 云端 `--cloud` 模式下**逐 id 集合差**（PITFALLS §P1 防假绿：不只比行数）；
⑤ 新测试文件纳入单测清单。
