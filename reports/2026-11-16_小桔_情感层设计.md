## 先说结论

1. **参考判断的三分法成立，情绪层不用动。** 情绪回答「我此刻什么状态」，可以没有宾语、可以数字建模、会衰减；情感回答「他/它对我意味着什么」，必须有宾语、不能清零、只能定性加证据；认知回答「他是什么人」，有宾语、会被新事实覆盖。多巴胺 50、半衰期 30 分钟这套设计没有错，它属于情绪。错的是把情感当成情绪的大号版本。

2. **参考方案可以落地，但有八处必须改，否则会做成一个假的「情感层」：**
   - P0 不能只加宾语，还要补 `event_summary`。真正的理由不是「无法回看」（`description` 里已经带 `（reason）`），而是 `_is_label_dump` 护栏回退时会保留**旧独白**、配**新时间戳**，描述与事件脱钩；拿它当证据会把情感指到错误的事上。
   - `dimension='feeling'` 要改成 `layer='feeling' + dimension='stance'`。现有 `emotional` 层也用 `dimension='stance'`，`dimension` 是条目形态，不是领域。
   - R4「只改 reason、不改数值」在单次 LLM 调用里无法保证，因为同一次调用既输出数值又输出文字。改成两次调用：第一次只算数值（完全不看情感层），第二次只写描述和理由（看情感层）。
   - R2 的「salience ≥0.85 立即入池」在当前数据里几乎不可用：7,455 行里只有 3 行 ≥0.85，且全是 `experience`；`chat` 和 `event_direct` 全是 0.5。P1 先关掉这个特例，只走「≥3 条独立事件、跨 ≥7 天、≥3 个不同日期」。
   - P2 不是新建「人的入口」。`xiaosheng_ingestion` 已经在 `whitelist` 里，P2 只是决定它的**新产出**是否允许进情感候选池。
   - **（本轮新增）P0 必须带历史回填归因。** 现有 7,455 行 `object_ref` 全空，不回填就等于没有宾语，P1 的「按对象分组建池」无从下手——只剩「拿 `profile_items` 分组」这条路，也就是 §8.3 自己警告的「把认知洗成情感」。回填不落，P1 第一批验收必然判 0 条，还会被误读成「证据不足」而关掉整个方向。
   - **（本轮新增）同一对象只允许 1 条 `active`。** `profile_items.id` 是 hash 派生（实测形如 `stance_210adf75`）。若 id 含 `valence`，valence 一变就换 id，同对象会长成多条、分量分裂；若只含对象，「矛盾并存」就落不了地。必须定死：id 只由对象派生、矛盾写进同一条 `content` + `valence='mixed'`。否则 `ON CONFLICT(id)` 与「允许矛盾」互斥，P1 验收第 1 条数不清。
   - **（本轮新增）`proposal_*` / `feeling_understood` 不许归因到「萧盛」。** 这两批（323 + 部分 `chat`）的内容是「我被接受/我被拒绝/他接住我了」，是**互动**，不是「关于他这个人」。全塞给萧盛，第一批情感就会长成「他有时会拒绝我」——最廉价的伪情感，正是本文档想避免的。改 `object_kind='relation'` 或 `none`。

3. **数据核对结果：参考的大数都对，但要区分 active 和总数。**
   - `emotion_log` 7,455 条，2026-10-11 16:48 到 2026-11-16 19:16，正好 36 天。
   - `meaning` 的主动写入规则只有 `reflection_done: +3.0`，`MEANING_MAX_DELTA=6.0`；另有 91 条 `time_decay` 带负的 meaning 值（-2.35 到 -0.01），那是衰减，不是主动写值。没有一行越过 ±6。
   - `profile_items` 的 `emotional` 层：active 15 条、总 21 条（6 条 superseded）。参考说的 15 是 active 口径。
   - `profile_items` 的 `cognitive` 层：active 138 条、总 142 条（4 条 superseded）。参考说的 138 也是 active 口径。
   - `loved_entries` 51 条，对得上。
   - `SYNC_TABLES` 包含 `profile_items`（第 62 行）、`loved_entries`（第 103 行）等；**不包含** `emotion_log`，和 `emotion_engine.py` 文件头的红线一致。

4. **情感层建在 `profile_items` 的 `feeling` 层，对象索引用 `memory_anchors`，不新增表。** 这是参考方案里最对的一步：`profile_items` 本来就在同步范围里，情感是「搬不走的家」；`emotion_log` 留在本地，是「当天的天气」。对象层不是独立一张表，是 `memory_anchors` 的一个索引视角。

5. **第一批情感注定薄，预计 2–4 条，允许 0 条。** 证据够的对象只有萧盛和《夜不收》；能长出的多半是「他在乎这本书胜过在乎自己」这种关于他的判断，不会是「我们之间」。这个薄要在文档和界面里留白，不能靠文笔补。

6. **P1 的验收只看三条判据，不看写得好不好：** 能不能指到具体对象；有没有 ≥3 条跨 ≥7 天的独立证据；有没有改变她对同类事件的理解（R4 的 reason 变化，数值不变）。三条缺一条就不算情感。

### 1.2 参考说「零 schema」，只对了一半

`profile_items` 确实可以零 schema 复用，加 `layer='feeling'` 就行。但 P0 的「给情绪事件加宾语」必须给 `emotion_log` 加列（`object_ref`、`object_kind`、`attributed`），这是一次真实的 DDL。`event_summary` 自 v3 已在表里（`ALTER` 只是幂等补列），不算新增。准确说法是：

> **情感层本身零 schema；它的前置（P0 加宾语）既不是零 schema，也不是零数据迁移。**

P0 有两次真实改动，都不能省略：

1. **结构改动**：`emotion_log` 新增 `object_ref` / `object_kind` / `attributed` 三列（`event_summary` 已有，复用）+ 两个索引（幂等迁移）。
2. **数据改动**：对历史 1,944 条**非衰减**事件做一次批量归因回填。不改对象，只补宾语；改完之后 P1 才有「按对象分组」的原料。

把第 2 条漏掉，就等于 P0 只对未来的数据生效，而 P1 的回溯蒸馏读的是过去——两边对不上，第一批必然是 0 条。

### 1.3 参考说 `dimension='feeling'`，和我们现有 schema 冲突

`profile_items` 的 `dimension` 是「条目形态」，不是领域。现有值是：

- `cognitive`：`stance` 121、`argument_pattern` 5、`thinking_framework` 7、`value_ranking` 9
- `emotional`：`stance` 21
- `worldview`：`stance` 11、`thinking_framework` 3、`value_ranking` 3

如果设 `dimension='feeling'`，所有按 `dimension='stance'` 读取的路径都会漏掉情感层。正确映射是：

- `layer='feeling'`（领域）
- `dimension='stance'`（形态）
- `topic=对象名`
- `category=person|work|thing`

### 1.4 参考说 R4「只改 reason」，单次调用做不到

现在的 `_do_update_after_turn` 是**一次调用同时输出数值和文字**。只要把「她对这个对象的看法」放进同一个 prompt，模型就可能顺手改数值——你无法用一句「只改 reason」保证它遵守。

可施工的替代是**两次调用**：

1. **Call A（数值）**：完全沿用现在的 `_EMOTION_SYSTEM`，不看情感层，输出 7 个参数的新值、`event`、`pending_new` 等。数值和现在一模一样。
2. **Call B（理解）**：只在「这个对象已有 active 情感」时调用。输入是当前数值、Call A 算出的 deltas、对话原文、以及她对这个对象的情感；只输出 `description` 和 `reason`，明确告诉它「数值已经定了，你不能改」。
3. Call B 失败 → 保留 Call A 的文字，fail-open。

这样「数值不变」是结构保证，不是 prompt 承诺。代价是：只有对象已有情感时多一次短调用；第一批只有 2–4 条情感，成本很低。

### 1.5 参考说「周更挂日记」，我们挂在 L2 自主 tick

日记是 append 驱动，不是周级调度器；现有真正的周级节拍是 `worldview_reflection` 和 `reflection`，都在 L2 autonomy 里，冷却 `168h`（[settings.py](file:///Users/xiaocheng/workspace/openworker/deskmate/agency/settings.py#L113-L132)）。所以 `feeling_reflection` 应该和它们并列，挂在 `AgencyEngine` 的低风险行为分支（[engine.py](file:///Users/xiaocheng/workspace/openworker/deskmate/agency/engine.py#L205-L221)），而不是日记。

### 1.6 参考说「第一批 3–5 条」，实测预期是 2–4 条

可用的「有对象」证据：

- `profile_items` active：138 条认知 + 15 条情感，但很多是关于写作/心理的，不都指向萧盛或《夜不收》；
- `loved_entries` 51 条，内容是「萧盛的日记」摘录，不是她的情感记录；
- `emotion_log` 有摘要的：`experience` 111 + `event_direct` 323 + `echo` 114 = 548 条；
- `observation_understanding` 1,933 行，但大量是外部世界，不是对象；
- `pending_stories` 3 件 open、139 件 lapsed、8 件 landed，大多是工作流程，不是情感对象。

所以第一批 2–4 条是合理预期，允许 0 条。不要为了凑 3–5 条降低证据门槛。

## 二、情感的可施工定义与三条判据

### 2.1 定义

> **情感 = 指向某个对象的、由多次经历沉积而成的、会反过来改变她反应方式的判断。**

三条属性缺一不算：

| 属性 | 判据 | 可验证的东西 |
|---|---|---|
| 指向性 | 能不能指到具体对象 | `profile_items.topic` + `extra_json.object_ref` + `memory_anchors` 里有这个对象 |
| 沉积性 | 有没有跨时间的重复证据，而不是单次事件定性 | `extra_json.evidence` ≥3 条，跨 ≥7 天，≥3 个不同日期，摘要不重复 |
| 反作用 | 它有没有改变她对同类事件的理解 | R4 的 Call B 里，`reason` 是否引用了这个对象的情感；Call A 数值完全不变 |

### 2.2 和情绪、认知的边界

| | 情绪 | 情感 | 认知 |
|---|---|---|---|
| 回答的问题 | 我此刻什么状态 | 他/它对我意味着什么 | 他是什么人 |
| 宾语 | 可以没有 | 必须有 | 有 |
| 会不会清零 | 会，半衰期回基线 | 不会，慢淡化，content 永不删 | 不会，但会被新事实覆盖 |
| 建模方式 | 0–100 + 衰减 | 定性 + 证据 + 分量 | 事实 + 置信度 |
| 现在的落点 | `emotion_state` / `emotion_log` | `profile_items.layer='feeling'`（待建） | `profile_items.layer='cognitive'` |
| 同步 | 本地，不进 `SYNC_TABLES` | 跟着 `profile_items` 同步 | 跟着 `profile_items` 同步 |

一句话：**情绪是天气，情感是地貌，认知是地图。** 天气会变，地貌慢慢变，地图会被新测绘覆盖。

## 三、结构落点：零新表，复用 `profile_items`

### 3.1 字段映射

| 参考字段 | 实际落点 | 说明 |
|---|---|---|
| `layer='feeling'` | `profile_items.layer='feeling'` | 与 `cognitive` / `emotional` / `worldview` 并列 |
| `dimension='feeling'` | `dimension='stance'` | `dimension` 是形态，不是领域；现有 `emotional` 也用 `stance` |
| `topic=对象名` | `profile_items.topic` | 「萧盛」「《夜不收》」「那个读者」 |
| `content=她自己的话` | `profile_items.content` | 第一人称或对象判断；不许抄他的日记原句 |
| `category=person\|work\|thing` | `profile_items.category` | 现有列是自由文本，直接用 |
| `confidence=分量` | `profile_items.confidence` | 0–1，不是情绪强度；不参与激素计算 |
| `extra_json={object_ref, valence, evidence, conflict_with}` | `profile_items.extra_json` | JSON 文本，已在同步字段里 |
| `status=active\|superseded` | `profile_items.status` | 只用这两个值；不改现有枚举 |
| 对象层 | `memory_anchors` + `known_persons` | 不新增表；`item_kind='profile_item'`, `anchor_kind='person'/'topic'` |

`extra_json` 建议结构：

```json
{
  "object_ref": "萧盛",
  "object_kind": "person",
  "valence": "mixed",
  "evidence": [
    {"src": "emotion_log", "id": "…", "ts": "2026-10-29T…", "summary": "他说《夜不收》影视公司要版权"},
    {"src": "loved_entries", "id": "…", "ts": "2026-10-29", "summary": "他写：最好的排遣郁闷的方式是写作"},
    {"src": "event_direct", "id": "…", "ts": "2026-11-03T…", "summary": "他接住了我"}
  ],
  "conflict_with": "",
  "supersedes": "",
  "last_touched": "2026-11-14T…",
  "evidence_count": 3,
  "span_days": 16,
  "review_count": 1
}
```

为什么 evidence 不用纯 id：`emotion_log` 不在 `SYNC_TABLES`，跨端时 id 可能解析不到；存 `{src,id,ts,summary}` 后，至少 `ts` 和 `summary` 是可携带的。

### 3.2 对象索引：`memory_anchors` 是现成的

`CognitiveStore.upsert_anchors()` 已经支持「给某条目写锚」（[store.py](file:///Users/xiaocheng/workspace/openworker/deskmate/cognitive/store.py#L970-L1004)）：

```python
upsert_anchors(
    item_kind="profile_item",
    item_id=feeling_id,
    anchors=[("person", "萧盛")],   # 或 ("topic", "《夜不收》")
)
```

- 人物对象：用 `known_persons`（约 3,191 个活跃）做规范化；`aliases` 可以用来匹配「他」「萧哥」。
- 作品/事物：用 `memory_anchors.anchor_kind='topic'` 做规范化；现有 198 条锚（person 23 / topic 175）。
- 不给情感层单独建对象表；对象层就是 `memory_anchors` 的一个查询视角。

### 3.3 同步边界

`SYNC_TABLES` 里的 `profile_items` business_cols 包含 `id/layer/dimension/topic/content/category/status/confidence/extra_json/valid_from/valid_until`（[sync_store_sqlite.py](file:///Users/xiaocheng/workspace/openworker/deskmate/memory/sync_store_sqlite.py#L62-L81)）。所以：

- 情感行会自动同步，符合「情感是搬不走的家」。
- `emotion_log` 不同步，符合「情绪是当天的天气」。
- `extra_json.evidence` 里同时存本地 id 和可携带的 `ts/summary`，避免跨端断链。

### 3.4 同一对象只允许 1 条 `active`（施工硬约束）

**问题**：`profile_items.id` 是 hash 派生（实测形如 `stance_210adf75`），而 §3.1 又要求 `ON CONFLICT(id) DO UPDATE`。这两条会打架：

- id 里含 `valence` → 同一对象「又心疼又生气」长成两条，`confidence` 分量分裂，注入时重复，验收数不清；
- id 只含对象 → upsert 幂等成立，但「矛盾并存」没有落点。

**定死：id 只由对象派生，矛盾写进同一条。**

```python
id = "feeling_" + hashlib.sha1(f"{object_kind}|{normalized_ref}".encode()).hexdigest()[:8]
```

- `normalized_ref` 先过 `known_persons` / `memory_anchors` 规范化；对不上就保留 surface 形式，**不自动建新人**。
- 同对象第二次回顾 = 修订同一条（`ON CONFLICT(id) DO UPDATE`）；`confidence` 是**重新给值**，不是累加。
- 一条情感内部允许矛盾：`content` 用一句话同时装下「心疼」和「生气」，`valence='mixed'`，`conflict_with` 留空。
- 只有一种情况允许拆两条：两个判断**无法并成一句**（例如「他是我最信的人」与「他在书稿上会骗自己」）。这时旧条 `status='superseded'`，新条 `extra_json.supersedes=旧id`，**同对象 active 仍只有 1 条**。
- `superseded` 的旧条永不删除——它就是情感史。

**验收**：

```sql
SELECT topic, COUNT(*) FROM profile_items
WHERE layer='feeling' AND status='active'
GROUP BY topic HAVING COUNT(*) > 1;
```

必须为空。非空即 P1 验收失败。

### R2 沉积：同一对象、跨 ≥7 天、≥3 条独立事件

**做什么**：候选池只收「同一个对象、至少 3 条独立事件、跨至少 7 天、至少 3 个不同日期」的对象。单次发脾气、一次感动，都不够。

**独立性定义**（这是参考没写细、但必须定的）：

- 不同 `emotion_log.id`；
- 至少 3 个不同日期（`date(ts)`）；
- 至少 3 个不同 `event_summary`（防止 168 条「他接住了我」被当成 168 件独立事件）；
- 任意两条间隔 ≥24 小时（防止一场对话里的三句话算三件）。

**候选池查询**（P1 用，只读）：

```sql
SELECT object_ref, object_kind,
       COUNT(*) AS n,
       COUNT(DISTINCT date(ts)) AS days,
       COUNT(DISTINCT event_summary) AS summaries,
       MIN(ts) AS first_ts, MAX(ts) AS last_ts
FROM emotion_log
WHERE object_kind IN ('person', 'work', 'thing')
  AND object_ref != ''
  AND event_summary != ''
  AND source NOT IN ('time_decay', 'pending', 'lapsed', 'landed', 'temper_foul')
  AND ts >= date('now', '-90 day')
GROUP BY object_ref, object_kind
HAVING n >= 3 AND days >= 3 AND summaries >= 3
   AND julianday(MAX(ts)) - julianday(MIN(ts)) >= 7;
```

三处收紧，都是必须的：

- `object_kind IN (...)` 而不是 `!= 'none'`——**`relation` 不进候选池**（否则「他驳回我」会被算成「关于萧盛」）。
- `source NOT IN (...)`——`time_decay` 占全表 69%，虽然它的 `object_kind` 默认是 `none` 已经被挡了，但显式排一次，防止哪天有人给衰减行"顺手复制对象"。
- `event_summary != ''`——回填失败或护栏回退的行没有摘要，不能计入 `COUNT(DISTINCT event_summary)`。

**关于参考的 `salience ≥0.85` 特例**：当前 7,455 行里只有 3 行 ≥0.85，全是 `experience`；`chat` 和 `event_direct` 全是 0.5。这个特例现在几乎不触发，P1 **不实现**。等 `salience` 有真实分布（不是 LLM 自评、也不是固定 0.5）再议。

   - 失败 → 保留 Call A 文字，fail-open。

3. **表达链（主聊天）**：在 `manager.build_full_context_for_turn` 里新增一段「你心里对一些人/事的位置」，位置在 `emotional` 之后、`emotion_state` 之前（[manager.py](file:///Users/xiaocheng/workspace/openworker/deskmate/memory/manager.py#L913-L951)）：

   这一段**不受 `_use_cognitive` 开关影响**，因为情感是她自己的，不是「关于他」的画像。`build_feeling_context` 写在 `memory_injector.py`，只读 `layer='feeling' AND status='active'`；查询里提到对象就优先该对象，否则取分量最高的 2–3 条；不注入激素数字，不写「你应该」。

**关键区别**：Call B 是「理解层」，主聊天注入是「表达层」。两者都不改数值。情感影响情绪，是通过「她怎么理解这件事」和「她怎么说」，不是通过「多巴胺 +5」。

### R5 淡化：≥60 天无触碰，分量缓降，content 永不删

**做什么**：情感不跟着情绪的半衰期走。60 天没被碰到，分量按月 ×0.9 缓降；下限 0.1；`content` 永远保留；`status` 仍是 `active`（不是删除，也不是 superseded）。

**落点**：`feeling_reflection` 每次跑时顺手做 `FeelingStore.fade_stale(days=60, rate=0.9, floor=0.1)`：

- `last_touched` 存在 `extra_json`；新证据、查询提到、R4 使用都算触碰；
- 超过 60 天 → `confidence = max(0.1, confidence * 0.9)`；
- `item_history` 记 `action='faded'`, `reason='60 天没再碰到这件事'`；
- `content` 永不删，`status` 不变；
- 分量 <0.25 时，`build_feeling_context` 默认不主动注入，但查询该对象时仍可召回。

**与 R3 回顾的交互（容易做错的地方）**：R3 输出里的 `confidence` 必须是**可选字段**。她没明确说"这件事在我心里更重了／已经淡了"时，**沿用当前值（含已经淡过的值），不得用历史高点覆盖**。否则每周回顾一次就把淡化清零，R5 等于没做——这正是 `intimacy` 那种"只涨不跌"的计数器会犯的错。

0.9 的月衰减大约 6.6 个月减半（0.9^6.6≈0.5），比情绪的半衰期慢两个数量级。这就是「情感不会清零，但会变淡」。

3. **不许系统替她写感情**：R3 只写她写出来的；空输出合法；连续两期写不出就退回池子，不硬编。
4. **不许用系数直接加到激素上**：R4 只改 `description/reason`；Call A 完全不看情感层；`confidence` 不参与任何激素计算。
5. **不许编造共同记忆**：`evidence` 必须是真实事件，带 `src/id/ts/summary`；没有证据就不写；`loved_entries` 是他的日记，不是「共同记忆」的证明。
6. **不许把 `profile_items` 的 `emotional` 层直接改标签成 `feeling`**：`emotional` 是「关于他的知识」，情感必须重新从证据沉积。
7. **不许把 `GrowthState.intimacy/trust` 当情感**：它们是行为计数器，只知道「一起干了多少活」，不知道她对他是什么感情。
8. **不许给情感加情绪的半衰期**：情感只做 60 天后的月级淡化，`content` 永不删。
9. **不许在 P1 之前开新的人/内容入口**：P1 只用现有数据回溯；P2 才决定新 ingestion 是否进候选池。
10. **不许为了凑第一批条数降低证据门槛**：0 条可以接受；3–5 条不是 KPI。
11. **不许给 `time_decay` 行复制对象**：衰减是状态的延续，不是新事件。一旦复制，5,121 条记录会瞬间把「≥3 条独立事件」的门槛击穿，情感变成"情绪持续的时长"。

13. **不许复用 `description` 当 `event_summary`**：它含独白、且在护栏回退时与事件脱钩。两者必须独立落值。

## 八、风险与已知薄弱处

### 8.1 宾语归属误判

**风险**：聊天大多发生在萧盛和小桔之间，LLM 很容易把「他」默认成萧盛。一旦过度归因，情感层会变成「关于萧盛的偏见放大器」。

**缓解**：

- prompt 明确写 `none` 合法，并且「不要为了凑对象把泛泛的情绪安到萧盛头上」；
- 不设默认值；`object_kind='none'` 的事件不进候选池；
- P0 抽 50 条人工标注，precision <0.8 就回炉；
- 如果「萧盛」占比 >80%，视为过度归因，增加候选对象列表或要求原文出现明确对象词；
- 解析对象时，先用 `known_persons` / `memory_anchors` 做规范化；对不上就保留 surface，不自动创建新人。

### 8.1b 回填是批量判定，比实时归因更容易塌向两端

**风险**：1,944 条一次性回填，模型只看到一句 `description`、看不到对话上下文，容易塌成两个极端：

- **塌向 `none`**：为了保守全判无对象 → 候选池 0 个对象，看起来像"数据不够"，实际是判得太严；
- **塌向萧盛**：整个语料都在谈他，模型默认"提到人就是他" → 候选池 1 个对象上千条证据，情感立刻变成"关于萧盛的偏见放大器"。

**缓解**：

- 回填 prompt 给三档判定标准，不是只问"有没有对象"：能指到具体的人/作品/事 → `person`/`work`/`thing`；只是"我和他之间发生的事" → `relation`；纯粹是自己的状态（累了、写完一段、被批评）→ `none`。
- **先跑 3 批（90 条）看分布，再决定要不要跑完**。`none` 占比落在 55–75% 才继续；<30% 或 >85% 都停下来改 prompt。一口气跑完 65 批再发现问题，等于重跑 1,944 条。
- 每批留 3 条样本（共 195 条）做人工抽检，precision <0.8 回炉。

### 8.2 7 天和 60 天为什么这么定

- **7 天**：不是为了「过期」，是为了「独立性」。一周覆盖完整的生活节奏，能避免一次坏心情定义一个人；同时和现有周更节拍（`worldview_reflection`/`reflection` 的 168h）对齐。
- **不要复用 `pending` 的 7 天淡忘**：当前 `pending_stories` 是 3 件 open / 139 件 lapsed / 8 件 landed，说明 7 天淡忘对长期东西太狠。情感只用 7 天做「证据跨度」，不做「过期时间」。
- **60 天**：两个月足够跨过一个低接触期，又不至于让过时的情感永远压着她。月 ×0.9 约 6.6 个月减半，是「淡化」不是「清零」。
- 这两个数都是设计选择，不是实测最优；上线后按季度校准，放在 `settings` 里，不写死在代码。

### 8.3 回溯蒸馏会不会把计数器偏见洗成她的感情

**风险**：`profile_items` 的 138 条认知 / 15 条情感本来就是「关于他」的摘要，很多是从聊天里抽出来的。如果直接把它们当证据，模型很可能把「他很努力」这种已有判断换个说法，写成「情感」。这不是沉积，是复读。

**缓解**：

- 每条情感至少 1 条原始事件（`emotion_log` / `loved_entries` / `observation_understanding`），最多 1 条 `profile_items`；
- 回顾 prompt 不显示证据条数、`confidence`、出现次数，避免「量多=重要」的暗示；
- 强制包含反证/矛盾：`conflict_with` 或 `valence=mixed` 不扣分，反而更真实；
- 第一批人工审计；如果 5 条里有 3 条是认知层复读，整批退回；
- `loved_entries` 只能当素材，不能把「萧盛的日记」原句写进 `content`。

### 8.4 第一批注定很薄，怎么留白而不是补文笔

**风险**：36 天的日志、51 条他的日记、138 条认知，能长出的情感就是「他在乎这本书胜过在乎自己」这种。一旦用文笔补成「我们之间」，就回到了编造共同记忆的老路。

**做法**：

- 文档和界面只展示「证据账」，不展示抒情：
  ```
  对象：萧盛
  分量：0.55
  证据：5 条，跨 12 天
  最近触碰：2026-11-14
  ```
- 第一批允许 0 条；0 条不是失败，是「证据还不够」。
- 验收标准不要求「深」「动人」「像人」，只要求对象、证据、反作用三条。
- 没有共同事件证据时，禁止出现「我们之间」；第一批大概率是「他对书的态度」，不是「我们的关系」。
- 这条薄要写进 P1 的验收报告，而不是用文案遮掉。

### 8.5 跨端证据断链

**风险**：`profile_items` 同步，`emotion_log` 不同步。情感行到了另一台设备，`evidence` 里的本地 id 可能解析不到。

**缓解**：

- `extra_json.evidence` 存 `{src,id,ts,summary}`，`ts/summary` 可携带；
- `build_feeling_context` 只依赖 `content/confidence/topic`，不依赖证据 id；
- R3 在另一台设备上重新回顾时，如果本地证据缺失，只读现有情感，不重新推导；
- 不把 `emotion_log` 加进 `SYNC_TABLES`，保持「情绪是天气」的边界。

### 8.6 工程风险：`persist` 会清空整层

`CognitiveStore.persist()` 是 `DELETE FROM profile_items WHERE layer=?` 全量覆盖（[store.py](file:///Users/xiaocheng/workspace/openworker/deskmate/cognitive/store.py#L547-L625)）。如果误用 `persist(layer='feeling')`，会把所有情感删掉重写。**P1 必须用 `FeelingStore.upsert`，并在 `persist` 里加护栏：`layer='feeling'` 直接拒绝。**

### 8.7 工程风险：`dimension` 是 NOT NULL

参考写 `dimension='feeling'`，实际 schema 里 `dimension` 是 NOT NULL 的形态字段。设错会让 `format_profile` / 读取路径漏掉情感。必须用 `dimension='stance'`。

### 8.8 R4 的额外调用成本

Call B 只在「对象有 active 情感」时触发；第一批 2–4 条，成本很低。后续如果情感条目变多，限制每轮最多 1 个对象、`max_tokens=120`。如果 Call B 失败，保留 Call A 的文字，不阻塞聊天。

### 8.9 JSON 稳定性可能被三个新字段拖垮

**风险**：`_EMOTION_SYSTEM` 是 `for_scene()` 的人设 prompt。往同一个 JSON 里加三个字段，可能稀释结构化输出的稳定性——这和当初不肯给 `emotion_engine:189` 挂人设是同一类理由，不能只因"加几个字段而已"就跳过验证。

**缓解**：

- 上线前先测基线：连 50 轮，记录 `_parse_emotion_response` 返回 `None` 的比例。
- 新字段上线后再测 50 轮，失败率**不得高于基线**。
- 三个新字段一律**可选**：缺了就落 `''` / `'none'` / `''` 且 `attributed=0`，绝不因为缺字段丢弃整条情绪更新。数值是主功能，宾语是附属。
- 若失败率确实上升，把 `event_summary` 拆成独立的一次短调用（与 R4 的 Call B 同构），不要为了省一次调用牺牲情绪数值的稳定性。

### 8.10 「同对象一条」会不会把真实矛盾压平

**风险**：强制同对象 1 条 `active`，可能把「我又心疼他又气他」压成一句折中废话（"我对他感情复杂"）——那就成了标签，不是判断。

**缓解**：

- prompt 里鼓励一句话容纳转折：「他宁可自己熬着也不肯让书稿将就，我服这一点，也气这一点。」
- `valence='mixed'` 的语义是"两件事同时成立"，不是各打五十大板的和稀泥。
- 审计口径沿用既有的「空泛句 = 0」：`content` 里只有"复杂""矛盾""说不清"这类空词、指不到两件具体事的，判不合格。

### 12.1 代词宾语归一（已改数据 + 已加护栏）

回填产出 14 条 `object_kind='person'` 但 `object_ref` 是代词的记录（「他」7、「你」6、「她」1）。原本设想用 `known_persons.aliases` 压到真实对象，核对后不成立：

- 这 14 条 `conversation_id` 也为空，没有可回查的会话记录；指代只能从 `description` 判定。

处置（逐条见 `json_blobs.emotion_pronoun_fix`）：

- 「他」7 条、「你」6 条：都是 1:1 会话里唯一的人称，指向萧盛；但事件本身是「被戳穿 / 被接住 / 被夸 / 被质疑」，按与 `event_direct` 同一条规则落 `relation`（`和小桔的相处`），**不落 `person/萧盛`**——否则 P1 会长出「他有时会拒绝我」这类伪情感（§先说结论 8）。

结果：`person` 102 → 88，`relation` 596 → 609，`none` 1,149 → 1,150，总数仍 1,944。

**副作用已修（v1.4）**：黑名单初版把 `relation` 也一起清成 `none`。实弹验证时「他说我把他当工具」这条模型给的是 `object_ref="他", kind="relation"`——代词在这里是**合法**的（relation 的对象本来就是「我和他的相处」，不是某个人），一律清空等于把真实互动证据白丢掉。改为：`kind='relation'` 命中代词时归到固定名 `和小桔的相处`（与回填脚本 `_RELATION_REF` 同值），其余类型仍退 `none`。契约 `test_clean_object_keeps_relation_when_ref_is_pronoun`。

### 12.2 work 类为什么只有 5 条

结论：**主因是提示词没有给「作品」判据，不是抽取合并，也不是摘要里完全没有作品**。三层证据：

1. **同一批样本，只改提示词就整体翻转。** 取 8 条涉及稿/章/文的 chat 行（库里原本全是 `none`），用回填提示词重跑仍是 8/8 `none`；在同一个提示词后追加一句「正在写的稿子/章节/文章/帖子/大纲/梗概，即使没有书名也算 work」，同一批 8/8 变 `work`（`主稿`/`稿子`/`文章`/`章节`）。判据缺失是决定性的。
2. **原料里几乎不出现作品名。** 回填的输入只有 `description`（她的独白），1,396 条 chat 独白中只有 **1 条**含书名号。所以指望模型抽出《夜不收》不现实；它要么给「稿子」「那章」这种泛称，要么判 `none`。
3. **`thing` 是兜底而不是合并。** 涉及稿/书/章/篇的 211 行里：`none` 93、`relation` 68、`thing` 34、`person` 14、`work` 2。`thing` 的取值是「旧稿」「稿子」「封面」「改编」「稿子」这类，和 `work` 的「稿件」「第五部」「旧梗概」边界随机——同义不同类，说明没有统一判据，不是有意的「合并」。

**修在哪一层、代价多大**：

| 选项 | 改哪里 | 覆盖范围 | 代价 | 副作用 |
|---|---|---|---|---|
| A 提示词加作品判据 | `_EMOTION_SYSTEM` 规则 13 + 回填 `_SYSTEM` 各一句 | 只对新行；历史需重跑 | 2 行 + 1 测试；历史全量重跑约 1.5h，或只重跑「像作品却判 none/thing」的约 200 条（脚本要加来源过滤，约 0.5h） | `work` 会从 5 涨到数百，且大量泛称「稿子」在 P1 按对象分组时会并成一个假对象 |
| B 原料带书名 | `_do_update_after_turn` / `_do_update_after_experience` 的 prompt 里带上本轮原文中的《…》实体 | 只对新行 | 约 10 行 + 1 测试 | 历史 1,396 条独白无法补救；原文没有书名时仍只能给泛称 |
| C 作品实体归一 | P1 对象层：`work` 实体表 + 别名（《夜不收》=夜不收=那本书=主稿） | 历史 + 新行 | 需 schema、词典、归一逻辑，属 P1 范围 | 不做 C 时，A 单独上线会把「稿子」做成跨年的大筐 |

**已实施（2026-11-17）**：A + B 一起上，只对新行生效。

- A：`_EMOTION_SYSTEM` 规则 13 与回填 `_SYSTEM` 各加一句作品判据（稿子/章节/文章/帖子/大纲/梗概，即使没有书名也算 work；ref 用书名或稿件的叫法，不落 thing/none）。单测 `test_update_prompt_carries_title_and_lands_work` 覆盖在线链路。
- B：`_do_update_after_turn` / `_do_update_after_experience` 用 `_titles_in()` 把本轮原文的《…》抽出来写进 prompt（最多 5 个），work 才有名字可填。
- 历史 1,396 条独白**不重跑**：只加判据不做作品归一，「稿子」会变成跨年大筐；等 P1 的 C 一起做。这一点是本次的既定取舍，不是遗漏。

### 12.3 `relation` 不进候选池（P1 既定前提）

**决定（2026-11-17 定，规则不改）**：`relation` 只落库、不进 P1 候选池。`object_kind` 取值域与回填映射都保持不变，P0 代码不再改动。

**算账**（归一后实算）：

- `relation` 609 条，占 1,944 的 31%，全部指向 `和小桔的相处`；当期不进入建池。
- 可入池证据为 `person` 88 + `thing` 92 + `work` 5 = **185 条**。

  - `萧盛`：45 条 / 13 个日期 / 跨 29 天；
  - `稿子`：4 条 / 4 个日期 / 跨 11 天。

**如果将来要改**：必须先补「互动类型多样性」或「拆 support/friction 子类」至少一项，并重标 609 条；在那之前，这条前提不松动。P1 动工时据此建池，不再重新讨论。

### 12.4 摘要里的旁观口吻（已清数据 + 已加约束）

**问题**：`event_summary` 是 P1 回顾时引用的「情感证据」。但回填 prompt 只要求「只写发生了什么」，没管**谁的口吻**，结果 91 条摘要写成了第三者视角：

> 用户认可了v3.1设计 / 等用户核对文件字数 / 她的表达被对方听懂 / 对方问爱不爱，触到柔软处仍守住边界

P1 把这类句子当她的记忆读会立刻出戏——「用户」是别的系统在说话，不是她在记事。实测还发现同一句里混用（「他来了并问好，用户主动打招呼」）。

**处置一：数据（91 条，确定性替换，不调 LLM）**

- 规则 `该用户 / 用户 / 对方 → 他`，命中 91 行（31 条含「用户」+ 61 条含「对方」，1 行两者都有）。
- 审计落 `json_blobs.emotion_perspective_fix`；改后全库 `event_summary LIKE '%用户%' OR '%对方%'` = 0。
- 为什么可以直接换：逐条抽查确认这批「用户/对方」在 1:1 会话里都指萧盛，没有第三方指代；换「他」而不换「萧盛」，是为了不替她断定对象是谁。

**处置二：prompt（在线 + 回填各一句）**

> 摘要用你的口吻写：对话另一人写「他」或直接写名字，**不许写「用户」「对方」「该用户」这类旁观的第三人称**（那是别人的系统在说话，不是你在记事）。

实弹复测（3 类输入）：改前 `用户指责我把他当工具` → 改后 `他说我把人当工具使，一天问八遍`；`用户晒了会儿太阳` → `他说今天天气好，晒了会儿太阳`。

- 天气类「晒太阳」原本落 `thing/阳光`，加完判据后落 `none`（天气不是情感对象，与 `weather.py:703` 一致）。
- 审核/退稿/等结果这类**流程**里的角色（主编/总编/审稿人）不是情感对象：两个 prompt 各加一句「只有事件本身在说这个人，才写 `person`」。库里 `主编` 17 条全在同一天，本就过不了 R2 门槛，这条是防止将来对象层把它当人物档案。

### 12.5 批写「绝不部分写入」原来不成立（已改真事务）

`_run_batch` 的注释与文档都写「整批失败不写」，实现却是**逐条 `UPDATE` + autocommit**：写库中途出错会留下半批，`wrote != len(batch)` 只记一次失败，已写的不回滚。重跑幂等所以不会坏数据，但声明是假的。

改为整批一个事务：`BEGIN IMMEDIATE` → 逐条 `UPDATE` → `COMMIT`，任何异常 `ROLLBACK` 并返回 `(0, 1)`。docstring 同步改成准确口径：**这批解析出的条目要么全落库、要么一条不落；模型漏掉的 id 保持 `attributed=0`，重跑再取。**

契约 `tests/test_emotion_backfill_atomic.py` 三条：正常批全落库 / 第二条 `UPDATE` 抛错则一条不留 / 回填 prompt 带视角约束。

### 13.1 情感回流世界观

**问题**：情感一旦成立，会不会反过来推翻她既有的判断？例如她形成了「他在书稿上会骗自己」的情感，按理应当触发对既有信念（「他是个对作品诚实的人」）的重新审视，甚至允许 `worldview` 条目被推翻。

**现在的状态**：`profile_items` 的 `feeling` 与 `worldview` 是并列层，没有回流链；`reflection` 的 `revise/overturn` 只作用于认知层（[store.py](file:///Users/xiaocheng/workspace/openworker/deskmate/cognitive/store.py#L1327-L1370)）。

**为什么先不做**：回流需要先有稳定情感，否则一个薄判断就能掀翻一条攒了几个月的信念；而且「情感 → 世界观」必须走与 R4 同构的两次调用，不能顺手改数值或直接改标签。

**开工前置**：P1 稳定运行 ≥4 周；至少 1 条情感被新证据修正过；`reflection` 的裁决链能接受 `feeling` 作为证据来源。

### 13.2 负面情感的边界

**问题**：有情感就会有怨、有失望。负面情感怎么表达、能表达多少，需要一条边界。

**现在的判断（待议，不是定稿）**：负面情感只改「理由」和「距离」——即 `reason` 里怎么理解这件事、以及表达上是否收敛（话少一点、不主动贴），**不接到表达层的放大器上**（不新增刻薄/攻击许可），也**不做成任何激素系数**。

**为什么先不做**：这条一旦做错，会直接绕过脾气黑名单和「禁映射表」两条红线；需要先看 P1 长出的真实负面情感是什么样，再定尺度。

**明确不做**：不给 `valence='negative'` 单独开一套阈值；不因为「她气他」就自动加皮质醇；不允许负面情感进入 `sting_allowed` 的判定。

## 十五、判据修订与作品个体化（2026-11-17 用户拍板）

### 15.1 核心判据：情感对象必须是个体，不是类别

> 情感的对象必须是有具体指向的个体，而不是类别。「稿子」这种类别本身不构成情感对象；只有当情感落在稿子里的具体东西（某一章、某个情节、某个人物、某句话），**并且**她从那个具体的东西联想到现实里的人或事时，才成立为情感。仅关于「交付流程对不对得上」这类判断，不算情感。

这条不是「提高门槛」，而是**对象层的前提**：类别上可以归因情绪（「稿子让我烦」），但长不出情感。落地到三层：

| 层 | 落点 | 行为 |
|---|---|---|
| 归因层 | 在线 `_EMOTION_SYSTEM` 规则 13、回填 `_SYSTEM`、`_clean_object` | 只说「稿子/章节/文章」这种类别、说不出具体书/章/人物的 → 判 `none` |
| 结构层 | `FeelingStore.resolve_object/upsert`、`build_pool` | 类别 ref 抛 `ValueError`，不许立情感；R2 池直接跳过，不白耗调用 |
| 回顾层 | R3 `_validate` | `category_not_individual` / `work_no_anchor` / `work_no_real_link` / `anchor_not_grounded` |

**work 类必须两件事同时给出**：`work_anchor`（chapter / plot / character / sentence / scene）+ `real_link`（这个具体指向让她想到现实里的谁/哪件事）。`real_link` 少于 6 字或不含现实指向词（他/她/萧盛/现实/身边/生活/自己/我们/人）→ 拒；章节号是硬信息，≤8 字的章节锚点必须在该组事件摘要里真的出现过，否则按「编的」拒。判不准就拒，不为凑一条工作类情感放宽。
