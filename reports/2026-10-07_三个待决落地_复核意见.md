## 三、实测抓到的缺陷（按严重度）

### P1 · 日历 tick 是「每天 02:04 一次」，且该时刻在窗口外 → 明早首跑大概率失败
- **实现与测试锁的是日周期**：`_next_slot_delta` 把 "02:04" 解析为 HH:MM=当日 02:04:00（测试实证：01:00→02:04=64min、过点回绕明天、多时刻 ["02:04","04:30"] 均为每日时刻表）。
- **但所有文字口径都是小时级**：argparse help「对齐云端 :02 错峰窗口」、docstring「默认 :02 与 :04」、plist 注释、清单验收「**每整点 +4 分**一条成功」「下一轮 :04 出现」。
- **窗口实测 27s**：今晨 02:02:00–02:02:27 → 02:04:00 落在窗口结束后 ~93s，cloud:8765 已还给 app server → tick 必失败；且日历循环**每个时刻只打一枪、无窗口内重试**，分钟粒度对 27s 窗口本身极脆。
- 部署后 `窗口 tick` 出现次数 = **0**（首跑要等明早 02:04）。**后果链**：tick 不成功 → Mac push 水位继续冻结 → 清单观测项「游标开始推进」落空 → §P2 的"Mac 解锁"也落空。
- 建议（需拍板）：slots 支持**分钟标记**（如 `:02,:04` 每小时触发）或**窗口分钟内 15s 级重试**；验收口径二选一改齐。

### P2 · GC max(push, pull) 拿错了游标：空间混用，云端护栏失效、Mac 毫无变化
- `pull_after_seq` 是**本端从对端拉走**的水位（对端 oplog 的 seq 空间），不是"对端从我这拉走"（那存在**对端的** cursor 里）。commit 引用的"云端 pull 已到 4587"是云端 cursor 里的数，**Mac 的 gc 脚本根本读不到**。
- **云实测**：push=3989（自身空间）pull=4789（**Mac 空间**）→ max=4789 **> 云 oplog 自身 max(≈4050)** → `seq <= min_safe_seq` 恒真 → **seq 护栏在云端形同虚设**，只剩 30 天龄兜底（原护栏防的是"push 停摆>30 天时删掉未送达事件"）。
- **Mac 实测**：max(1676,1662)=1676，**与改前一模一样** → "解 Mac GC 永不生效"在 Mac 上并未兑现（要等 P1 修好 tick 才解锁）。
- 测试 `test_gc_min_safe_seq_uses_max_of_push_and_pull` 锁的是公式，不是语义。
- 建议：**a)** 先 revert 回 push-only（云 push 本就正常；Mac 随 P1 自然解锁）；**b)** 正解 = HttpOplogServer 暴露对端 cursor，取**对端 pull_after_seq（它才是我空间里的"对端已拉水位"）**；**c)** 无论如何加同空间护栏 `min_safe_seq = min(…, 本端 oplog watermark)`——有这条，云上 4789>4050 当场就会被测出来。

### P3 · drift 检测三连败（没落库 + 必误报 + 假日志）——首跑"成功"是假的
1. **零落库（云上实测复现）**：`_record_drift` 只 `from ledger import run_producer`，而 `sync_health` 生产者靠 **import `health_producers` 注册**（`proactivity/__init__` 不自动注册；只有 `run_producers_all` 才 import）→ 新进程 `PRODUCERS={}` → 实测 `registered=[] , run_producer 返回 0` → 台账 15 行里 **0 条 sync_health**。修法：先 `import deskmate.proactivity.health_producers`（一行）。
2. **判据不对称 → 每跑必误报**：对端快照 = `live_items(exclude_local=True)`（仅活记录），本端 = `items()`（**含墓碑侧表**）。实测 14:05 报的 11 条差异 **100% 是两端都已删除的探针墓碑**（`probe_e2e_20261005`、`probe_hlc_0..3`、`probe_hlcfix_20261005`…逐条验过：profile 7/7 全 tomb、lh 1/1 全 tomb）；活记录口径 12:19 巡检=0 差异。修法：本端也用 `live_items(exclude_local=True)`。（原 Mac `_check_drift` 同病——它从未真正跑过所以没暴露。）
3. **假日志**：`_record_drift` 不看 run_producer 返回值就打「已写入 sync_health 台账」→ 排障被带偏。修法：n>0 才算写入，否则 WARN。
- 当前因①"因祸得福"没污染台账；①②一旦单修、不同修②，**窗口每小时会递一张漂移误报卡**。三处必须同批修。

### P4 · vault 残留：2 个文件云端读不了
- 内容比对 294/296 全等；**云端 openworker 读取失败**：`life/07-作品年表.md`、`小桔眼中的萧盛.md`（sha256=UNREADABLE）→ 云端小桔 vault_read 这两篇会失败（其中一篇是自我认知文件）。判断：云 syncthing 用户新落的文件权限未带 g+r（清单只 chmod 了 g+w）。修法：云 `chmod -R g+rX vault` + 给 syncthing 配 umask/或以 openworker 身份跑该 folder，并把 `g+r` 纳入清单回滚段。
