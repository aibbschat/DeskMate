### 0.1 实测补充（2026-10-05 12:0x，两侧逐表核对）

## 2. 方案 A：扩大 SYNC_TABLES（同库 deskmate.db，低风险）

> **范围已按萧哥 10-05 拍板收窄**：纳入 `user_posts` + `comments`；**`interview_sessions` 不同步**。

把以下 2 表加入 `SYNC_TABLES`（与现有 3 表同处 `deskmate.db`）：

- `user_posts`（个人中心日记 / 短帖）
- `comments`（日记评论）

### 2.0 前置步骤（原方案遗漏，缺则跑不起来）

**实测：`user_posts` 与 `comments` 的 sync 列全为 `NONE`**，即 `sync_uuid` / `sync_hlc` / `sync_tombstone` 三列**都不存在**。oplog 触发器模板（`sync_store_sqlite.py:137 _trigger_sql`）依赖这些列，**不迁移则触发器无法创建、写入不会被捕获**。

| # | 前置动作 | 说明 |
|---|---|---|
| 0.1 | 两表补 3 个 sync 列 | 与现有 3 表同构：`sync_uuid TEXT` / `sync_hlc TEXT` / `sync_tombstone INTEGER DEFAULT 0` |
| 0.2 | 存量行回填 `sync_uuid` | 复用现有回填模式（`deskmate:表:id` 形式），**幂等、可重跑** |
| 0.3 | 云端同样迁移 | 两端 schema 必须一致，否则触发器创建会失败 |
| 0.4 | **冷备** | 动库前 `sqlite3 .backup()`（禁 cp 活库），记录路径 |

> ⚠️ 迁移必须在**错峰窗口内**做（与 §2.5「回填时机」同一约束）。

### 2.0.1 两张表的实际情况（实测）

| 项 | user_posts | comments |
|---|---|---|
| 主键 | `id` | `id` |
| 时间列 | `created_at` ✅ | `created_at` ✅ |
| sync 列 | 无（需 0.1 迁移） | 无（需 0.1 迁移） |
| archived 列 | 有（`archived`，全部 31 条 = 0） | — |
| 外键 | — | `moment_id` → 指向 user_posts |

> **冲突策略可行**：两表都有 `created_at`，可直接沿用「时间戳较新者胜」。
> 注：`comments.moment_id` 依赖 `user_posts`，**回填顺序必须先 user_posts 后 comments**（否则可能触发外键校验失败）。

### 实施要点（复用现有 oplog 机制，改动小）

1. **注册表扩展**：`SYNC_TABLES` 增加 **2 表**（`user_posts` / `comments`，已排除 `interview_sessions`）；每表补 `row_identity`（主键或业务唯一键）与 `change_kind` 列（insert/update/delete），模式与现有 3 表完全一致。
2. **触发器复用**：现有同步用 SQLite 触发器把写操作记入 `_sync_oplog`（见 `sync_store_sqlite.py`）。新表复用同一触发器模板，无需另写挂钩逻辑。
3. **首同步回填**：Mac 侧首次纳入时，对 2 表做全量基线对账（现有「首连全量基线对账」机制，`1f31cb7` 已实现），把现存行推上云。**回填顺序：先 `user_posts` 后 `comments`**（外键依赖）。云端现状为 Mac 的真子集（`only-on-cloud=0`），按「**Mac 为权威**」增量补齐即可（实测仅缺 1 条 `42c3706cbdb3`）；若将来 Mac 侧删除日记，**必须走墓碑删除**而非云端留残余行，否则会产生幽灵数据。
4. **对账判据**：复用现有 4 条硬判据（A 只读预演 / B 心跳 / C 三条硬判据 / D 全量覆盖）；本次新增表的判据行直接并入验收脚本 `verify_stage*.py`。
5. **冲突处理**：日记/评论是用户产出，双向冲突按「`created_at` 较新者胜」+ 保留双方（不静默丢）；具体沿用 `learned_history` 的覆盖+history 模式。（两表均已实测具备 `created_at`，策略可落地。）

### 风险与注意

- **隐私**：✅ **萧哥 10-05 已确认接受**「个人中心日记进云端常驻库」。实测内容为家庭日记（家庭关系、写作状态、经济观察等），云端由 basicauth 保护、不公开。
- **回填时机**：必须在错峰窗口内（独占库）做，避免与后端写争抢——已修的窗口脚本（`xiaoju-sync-window.sh`）支持这一点。

## 3. 方案 B：chat.db（主聊天）是否纳入 —— 建议本期不动

- `chat.db` 是**独立 SQLite 库**（coworker 的 `ChatStore`），与 `deskmate.db` 物理分离。
- 纳入需：① 为 `chat.db` 单独建 `_sync_oplog`（或让 sync daemon 跟踪第二个库）；② 解决「主聊天量大、几乎每次交互都写」带来的 oplog 膨胀与**写饥饿**（与阶段 5 写饥饿硬骨头同源）。
- **建议**：本期**不动 chat.db**。理由：主聊天是最高频写、最易触发写饥饿；且当前「Mac 本地为主、云为只读协作节点」定位下，主聊天跨端一致性收益低、成本高。留待「写饥饿根治 → 两进程共存」后再评估。
- 若萧哥坚持要主聊天也上云：走独立 oplog + 限流（仅同步「已结束 / 已收藏」会话，跳过进行中），单独排期，不与本方案混做。

## 4. 验证（trust-but-verify）

- **迁移前**：`PRAGMA integrity_check` = ok + 冷备落盘 + 记录备份路径。
- **本地单测**：对 2 新表各触发一次 insert/update/delete → 断言 `_sync_oplog` 出现对应 `table_name` 且 `sync_uuid` 已回填；确认 `sync_tombstone` 删除行写入 `_sync_tombstones`。
- **云上端到端**：错峰窗口内跑 daemon → 云上 `user_posts` = 31、`comments` = 31；**逐 id 集合 diff 为空**（不只数行数——PITFALLS §P1 防假绿）；`interview_sessions` 保持 18 不变（确认未误纳入）。
- **窗口健康**：窗口日志 `grep -c NOT_ALIGNED` = 0。
- **缺失条目专项**：确认 `42c3706cbdb3`（10-02 那条日记）**已出现在云端**。
- **回滚**：`SYNC_TABLES` 改回 3 表 + 删除新表触发器即可（数据不丢，仅停止同步）；sync 列可保留（无害），也可用冷备整库回退。

## 5. 与阶段 5 的关系

本次扩大**不解决**「写饥饿 / 两进程共存」（那是硬骨头，单独排期）。扩大后同步量略增（新增 62 行 / <8KB），但 2 表数据量远小于主聊天与已同步的 `learned_history`（763 行），**不会显著加剧写饥饿**。

> 实施需在错峰窗口内进行（§2.0.4 冷备 + §2.5 回填时机）；窗口 5 分钟上限对本次体量（62 行）**绰绰有余**（实测日常窗口 10s 收工）。
