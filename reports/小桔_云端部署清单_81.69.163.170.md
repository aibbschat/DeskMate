   - **DeepSeek**：provider id `deepseek`，endpoint `https://api.deepseek.com`，env key `DEEPSEEK_API_KEY`（`registry.py:647-652`）。
   SecretStore 的 profile 键格式确为 `provider:<id>`（例：`provider:openai`，见 `coworker/providers/openai_provider.py:40`），因此两种写法都可行：在 GUI 里配这两个 provider，或直接在 `/etc/openworker/env` 写上面两个 env key（600，**勿入 git、勿动本地含 key 的 settings.json**）。腾讯云在国内，OpenAI/Anthropic 可能被墙，故国内优先火山/DeepSeek。
2. **前端地址/token 注入（无需 fork 代码，但方式必须是「运行时注入」）**：`surfaces/gui/src/api.ts:8-23` 的解析顺序是 `__COWORKER_HTTP__ → VITE_COWORKER_HTTP → 127.0.0.1:8765`。⚠ **v1 稿的 `export VITE_COWORKER_HTTP=/` 是错的**：api.ts 全部 202 处调用都是 ``fetch(`${httpBase()}/v1/...`)`` 字符串拼接，`httpBase()` 返回 `"/"` 时拼出 `//v1/health` —— 这是协议相对 URL，浏览器会解析成 `https://v1/health`（主机名变成 "v1"），所有请求打错机器；WS 侧 `//ws/events` 解析成 https scheme，`new WebSocket(...)` 直接抛 `SyntaxError`。**正确做法：构建后往 `dist/index.html` 注入 `window.__COWORKER_HTTP__ = location.origin`（连同 `__COWORKER_WS__`／`__COWORKER_API_TOKEN__`）**，运行时全局变量优先级最高。详见阶段 4。

## 架构结论：本地 vs 云端，一套代码、两条构建（回答"会不会要两套"）

**结论：不需要两套代码。** 小桔的源码从设计上就区分了「桌面 GUI 路径」和「浏览器路径」，靠运行时/构建期配置切换，而不是代码分支。证据：

- **后端同一份**：`openworker-server`（FastAPI/uvicorn）在本地被 Tauri 当 sidecar 拉起，在云端被 systemd 拉起，**同一个入口点、同一份 Python**。`lib.rs:852` 仅 Tauri 会设 `COWORKER_EXIT_WITH_PARENT=1`；云端不设这个变量，进程就常驻。本地更新后端 → 重新上传代码（阶段 2 的 rsync，见该节关于 `.git` 的说明）→ 重装 venv → 重启服务，代码零改动。
- **前端同一份 SPA**：`api.ts:5-23` 注释明写 *"This keeps a single codebase: browser `npm run dev` hits 8765; the desktop shell hits its sidecar."* 端点解析顺序是 `__COWORKER_HTTP__ → VITE_COWORKER_HTTP → 127.0.0.1:8765`，**本地不注入** → 默认连 `127.0.0.1:8765`（连自己机器）；**云端注入 `window.__COWORKER_HTTP__ = location.origin`** → 同源走 Caddy 反代。`vite.config.ts:52` 的 `envPrefix:["VITE_","TAURI_"]` 也能把 `VITE_*` 烤进构建，但**地址类变量绝不能填 `/`**（会拼出 `//v1/...` 坏 URL，见前置②），要填就填完整 `https://<隧道域名>`。所有 Tauri 原生调用（`tauri.ts` 的 `isTauri()`）在浏览器里自动降级，不会崩。
- **差异全是「配置」，不是「代码」**：
  | 差异点 | 本地（桌面） | 云端（headless） | 性质 |
  |---|---|---|---|
  | 端点地址 | 默认 `127.0.0.1:8765` | 运行时注入 `window.__COWORKER_HTTP__=location.origin` | 运行时全局变量，非代码 |
  | LLM 上游 | 本机 OmniRoute `localhost:20128` | 火山/DeepSeek（云端可达 endpoint） | 运行时 env / SecretStore |
  | 启动方式 | Tauri sidecar（含窗口） | systemd + Caddy | 打包/运维，非源码 |
  | 桌面功能 | 语音/自动更新/开机自启 | 浏览器里惰性降级（不可用但无害） | 前端 `isTauri()` 判断 |
  | 数据目录 | `~/.deskmate` | `/var/lib/openworker/.deskmate` | 环境变量 `DESKMATE_DIR` |

**所以你本地改完、上云的工作流是**：
1. 改后端 Python → 提交 → 服务器更新代码（用阶段 2 的 `rsync`；注意该命令 `--exclude='.git'`，服务器上没有 git 仓库，**不能** `git pull`——要么重跑 rsync，要么把 `.git` 一起同步）→ 重装 venv → `systemctl restart openworker-server`（同一份代码）。
2. 改前端 TS → 提交 → 本机 `npm run build`（**不设** `VITE_COWORKER_*` 地址变量）→ 按阶段 4 往 `dist/index.html` 注入 `__COWORKER_HTTP__`/`__COWORKER_WS__`/`__COWORKER_API_TOKEN__` → `rsync dist/` 上服务器（同一份代码，仅注入脚本不同）。
3. LLM / token / 目录 / 额外 Origin 等环境差异**永远只在 `/etc/openworker/env`（600）和注入脚本里**，不进 git、不污染源码。

唯一要留意的：云端**必须**做阶段 4 的运行时注入（构建期 `VITE_*` 仅在填完整域名时可用，填 `/` 是坏的）；若忘了注入，前端会回退连 `127.0.0.1:8765`（即服务器自己 8765，其实也能通，但浏览器侧仍会被 Origin/门禁拦——所以必须注入）。

## 概念澄清：本地与云端「互通」的本质（回答三个核心疑问）

> 先纠正一个措辞：**风味 C 下不存在"两台小桔互相同步"**。正确的模型是**「一台云上的小桔 + 一块本地浏览器窗口」**——大脑只在云端（`/var/lib/openworker/.deskmate`），Mac 只是指向它的显示器。所以"互通"不是"两端各一份、定时对拍"，而是"本来就同一份，两端看的是同一个"。这比同步更强：无冲突、无延迟、无分叉。

**Q1：本地和云端是互通的吗？**
是，且是「同一实例、两端访问」，不是「两个实例同步」。本地浏览器经隧道连云端后端，所有数据读写都落在云端那一份 `~/.deskmate`；本地不持有独立大脑。

**Q2：看世界读新闻——Mac 关了云端还读吗？Mac 开了会不会两端同步？**
- **Mac 关了，云端照读**：「看世界」是后端 L2 自主层的定时动作（`deskmate/agency/engine.py:114` `run_world_ingestion` 摄入、`engine.py:165` `observation_diary` 写观察日记、`engine.py:182` `worldview_reflection` 沉淀认知），挂在后端 scheduler 每 30s 的 `extra_tick`，**与有没有客户端连着完全无关**。Mac 合盖 = 云端继续读新闻、写日记、长世界观。
- **Mac 开了，无需"同步"**：重开浏览器 = 重新连上同一个云端实例，它趁你不在时读的新闻/写的日记已经在云端库里，打开即见。没有"同步事件"、没有延迟——因为从始至终只有一份。

**Q3：记忆层 / 感知层 / 理解层（含情感、意志），云端和本地互通吗？**
**全部互通，且同源于云端一份库**。证据：
- 五层（感知=world_context、情感=emotion、认知=profile_items/worldview、意志=will、记忆=vault/deskmate.db）都由后端进程持有，落点在 `base_dir`（默认 `~/.deskmate`，受 `DESKMATE_DIR` 控制，`deskmate/memory/manager.py:195-208`；`world_context.py` 的 `build_world_context(self.base_dir, …)` 也读这里）；统一库 `deskmate.db` 在后端侧，前端经 `/v1/deskmate/external/*` 实时拉取。
- **前端 `localStorage` 只缓存 UI 偏好**（主题明暗、桌宠大小 `deskmate_pet_scale`、动画去重 `deskmate_acted_types`、上次会话、语言）——**没有任何一条是记忆/感知/认知层**。所以换设备/清缓存不会丢大脑数据，只丢界面设置。
- ⚠ 关于 `deskmate/memory/sync.py`（"云端同步"模块）：它**真实存在**，但默认 `NoopBackend`（关闭、不联网、无密钥），设计用途是「多台**独立本地安装**经 iCloud/Dropbox 共享知识记忆」——**风味 C 不依赖它**（因为本就一个库，用不着同步）。不要把"互通"归功于这个模块；互通来自单后端架构本身。该模块若误开启，反而可能与单后端模型打架，首版保持默认关闭。

**★ 互通成立的两个前提（操作红线）**：
1. **本地 Mac 必须只当客户端、不跑自己的后端、不连自己的 `~/.deskmate`**。若你继续像今天一样开本地 Tauri 桌面（它拉起本地 sidecar、连本地 `~/.deskmate`），就变成"两台独立小桔"——看世界重复读、记忆分叉，回到我们想消灭的双开问题。阶段 7.5 规定首版用浏览器走隧道、不开本地后端。
2. **完整互通在阶段 9 迁记忆之后才成立**：迁之前云端是空脑、本地是满脑；迁完并归档本地老库，云端即满脑，本地浏览器连云端 = 看到全部历史积累（记忆/感知/认知/世界观全在）。

## 阶段 4：前端地址/token 注入（关键 —— 方式必须是「运行时注入」）
**做法（推荐，零改代码、且不依赖隧道域名）**：构建后往 `surfaces/gui/dist/index.html` 的 `<head>` 最顶部插入运行时注入脚本，再 rsync 上服务器：
```html
<script>
  window.__COWORKER_HTTP__      = location.origin;                          // https://<隧道域名>
  window.__COWORKER_WS__        = location.origin.replace(/^http/, 'ws');   // wss://<隧道域名>
  window.__COWORKER_API_TOKEN__ = "（阶段0生成的32字节hex）";
</script>
```
一键注入（在 `surfaces/gui/` 下执行；每次 `npm run build` 后都要重跑，因为构建会覆盖 index.html）：
```bash
python3 - <<'PY'
import pathlib
p = pathlib.Path("dist/index.html")
html = p.read_text(encoding="utf-8")
snippet = """<script>
  window.__COWORKER_HTTP__      = location.origin;
  window.__COWORKER_WS__        = location.origin.replace(/^http/, 'ws');
  window.__COWORKER_API_TOKEN__ = "REPLACE_WITH_TOKEN";
</script>
"""
if "__COWORKER_HTTP__" not in html:
    p.write_text(html.replace("<head>", "<head>\n" + snippet, 1), encoding="utf-8")
print("injected:", "__COWORKER_HTTP__" in p.read_text(encoding="utf-8"))
PY
```
- `api.ts:8-23` 的优先级 `__COWORKER_HTTP__ → VITE_COWORKER_HTTP → 127.0.0.1:8765`：运行时全局变量最高 → 同一份 `dist/` 在本地（不注入，连 8765）和云端（注入，同源）都能跑。
- 用 `location.origin` 而非写死域名：**隧道域名变了不用重新构建**。
- 注入后 `rsync -avz surfaces/gui/dist/ ubuntu@81.69.163.170:/opt/openworker/frontend/`。

**替代做法（构建期烤完整域名）**：先 `export VITE_COWORKER_HTTP=https://<隧道域名>`、`export VITE_COWORKER_WS=wss://<隧道域名>`、`export VITE_COWORKER_API_TOKEN=<token>`，再 `npm run build`——`vite.config.ts:52` 的 `envPrefix` 会收进去，此时不必改 index.html。
> ⚠ **绝不要用 `=/`**（v1 稿写法）：会拼出 `//v1/health` → `https://v1/health`，请求全废；WS 直接抛异常。详见阶段 0 警告。
> ⚠ token 会出现在 HTML 里——公网入口有腾讯隧道登录鉴权、且页面本身必须持 token 才能调 API，可以接受；但不要把这个 `dist/` 放到无鉴权的静态托管上。

## 阶段 5.5：修复 WebSocket Origin 门禁（新增 —— v1 稿漏项，不改则云端聊天不可用）
**问题**：`coworker/server/app.py:5116-5118`（`/ws/session/{id}`，聊天/流式核心通道）与 `app.py:6120-6122`（`/ws/events`）都在 `accept()` 之前校验 Origin，白名单只有 `tauri://localhost / localhost / 127.0.0.1 / tauri.localhost`（`app.py:36-41`）。浏览器发 WS 握手**必带 Origin**，隧道域名不在白名单 → 直接 `close(1008)`，前端 `Session` 一构造就断（`api.ts:2407`）。

> ⚠ 与 REST 的区别：`_ALLOWED_ORIGIN_RE` 对 **HTTP** 只是 CORSMiddleware 的响应头规则（`app.py:316`），同源请求本来就不走 CORS，所以 REST **无需改代码**；但 **WS 是另一套 accept 前门禁**，同源照样拦。原稿「同 origin 反代规避 CORS」对 REST 成立、对 WS 不成立。

**方案 A（推荐）：白名单加环境变量（约 6 行代码）**
> ⚠ **执行顺序**：先在本机改好 `coworker/server/app.py`（见下），**再跑阶段 2 的 rsync** 把它传上服务器（或打补丁后重跑阶段 2）。详见阶段 2 末尾「顺序陷阱」说明——顺序错了服务器会跑旧代码，云端聊天被 `close(1008)` 拦。

在 `app.py` 的 `_origin_allowed` 附近加：
```python
_EXTRA_ORIGINS = [o.strip() for o in os.environ.get("COWORKER_EXTRA_ORIGINS", "").split(",") if o.strip()]

def _origin_allowed(origin: str | None) -> bool:
    if origin is None:
        return True
    if _ALLOWED_ORIGIN_RE.match(origin):
        return True
    return origin in _EXTRA_ORIGINS
```
然后在阶段 5 的 `/etc/openworker/env` 写（域名从浏览器地址栏复制，只写 `scheme://host`，不要路径、不要结尾斜杠）：
```
COWORKER_EXTRA_ORIGINS=https://<隧道域名>
```
好处：只放行自己这一个隧道域名，其它网站对云端的 CSRF 仍被拦；本地（不设该 env）行为零变化。

> ⚠ **方案 A 的隐藏前提（WS 还必须带 token 作为 subprotocol）**：后端 `_websocket_authenticated()`（`app.py:294-302`）在 `COWORKER_API_TOKEN` 非空时，要求客户端把 token 作为 **WebSocket subprotocol**（`Sec-WebSocket-Protocol`）发来。浏览器 WS 握手**无法自行设置任意请求头**，而前端 `Session` 构造函数（`api.ts:1651`）`new WebSocket(url)` 既没带 subprotocol、URL 也没带 token → **一旦设了 `COWORKER_API_TOKEN`，浏览器 WS 仍被 `close(1008)`**（REST 不受影响，前端 `fetch` 已带 `X-OpenWorker-Token` 头，`api.ts:33`）。
> **解决（免重打包，已落地）**：在 `dist/index.html` 注入脚本里追加一段运行时 shim，monkey-patch `window.WebSocket`，自动把 `window.__COWORKER_API_TOKEN__` 注入为 subprotocol（见阶段 4 注入块末段）。这样后端 subprotocol 校验通过、WS `101` 建立。⚠ subprotocol 是浏览器 WS 鉴权的唯一可用载体，不要用 query param / 自定义头替代。若日后重打包前端，更干净的做法是改 `api.ts` 让 `new WebSocket(url, [tok])` 直接带 subprotocol，shim 即可移除。
> **真实域名**：本机用户自备域名 `xj.aibbs.chat`（指向 8080 隧道）。`COWORKER_EXTRA_ORIGINS=https://xj.aibbs.chat`。

**方案 B（不改代码，Caddy 兜底）**：把阶段 6 里需要的 `reverse_proxy` 改成块形式并改写 Origin：
```
handle /ws/* {
    reverse_proxy 127.0.0.1:8765 {
        header_up Origin "http://localhost"
    }
}
```
代价：等于对所有经隧道的请求伪造 Origin，这台实例的浏览器 CSRF 防护失效（云端本就有腾讯隧道登录鉴权，风险可接受），且以后排查问题会困惑。**仅作应急。**

**验证**：浏览器 DevTools → Network → WS，`wss://<隧道域名>/ws/session/...` 应显示 `101 Switching Protocols`；出现 `1008` 就是门禁没修好（表现为页面能开、聊天不回话）。

## 阶段 6：Caddy 反向代理（复用系统 caddy 2.11.4）
写 `/etc/caddy/Caddyfile`（监听 127.0.0.1:8080，与隧道对接）：
```
{
    admin off
}
http://127.0.0.1:8080 {
    # 信任腾讯隧道转发的头（与 DSH 时期一致）
    header {
        Strict-Transport-Security "max-age=31536000"
    }

    # ⚠ 反代一律用 handle（原样透传路径）。绝不要用 handle_path：
    #   1) handle_path 只接受 1 个 matcher —— 写成 `handle_path /v1/* /ws /roundtable /a2a /cloud`
    #      会让 Caddy 直接解析报错（ArgErr），服务起不来；
    #   2) handle_path 的语义是「剥掉匹配到的前缀」（/v1/health → /health → 后端 404）。
    # 另注：Caddy 的 path matcher 是精确匹配（`/` 只匹配根路径，`/foo/*` 才是前缀匹配），
    #       所以每个后端前缀各写一条 handle。
    handle /v1/*          { reverse_proxy 127.0.0.1:8765 }
    handle /ws            { reverse_proxy 127.0.0.1:8765 }
    handle /ws/*          { reverse_proxy 127.0.0.1:8765 }
    handle /roundtable    { reverse_proxy 127.0.0.1:8765 }
    handle /roundtable/*  { reverse_proxy 127.0.0.1:8765 }

    # 可选：外部 A2A 客户端经隧道访问时保留（不需要可整段删）
    handle /.well-known/* { reverse_proxy 127.0.0.1:8765 }
    handle /tasks/*       { reverse_proxy 127.0.0.1:8765 }
    handle /message:*     { reverse_proxy 127.0.0.1:8765 }

    # 其余一切：前端静态（assets / pets / skins / *.html），找不到则回退 SPA。
    # 放在最后，兜住 dist/ 里非 assets 的静态文件（v1 稿的兜底反代会把它们送去后端 404）。
    handle {
        root * /opt/openworker/frontend
        try_files {path} {path}/ /index.html
        file_server
    }
}
```

## 多实例互补约束（必读：本地与云端如何"互通、互补、不重复"）
你的核心诉求：上云不是"再开一个镜像副本"，而是本地和云端**互补**——本地在时它干活，本地不在（睡眠/关机）云端**接着干未完成的**，不要重复、不要断档。

**根因（为什么 naive 双开会重复）**：小桔的 AI 圈自动任务（广场发声 `ai_circle_share`、公开手记 `ai_circle_column`、回信 `ai_circle_reply`、素材摄入）属于 L2 自主层，挂在后端常驻 Scheduler 的 `extra_tick`（`coworker/server/manager.py:4843` + `deskmate/proactivity/background.py`），后端一常驻就每 30s 跑。这些动作是 low-risk 无审批闸、直接执行。若本地 Mac 和云端**各跑各的后端、各持一份独立 `~/.deskmate`**，冷却/去重状态互不可见 → 必然两边都去发帖/回信 = 重复。所以"双开两个独立 worker"是错的；但早先"二选一永久关一个"（A/B 单活）也没抓住你要的互补——那等于上云没意义。

**正确模型 = 共享状态 + 单写权威 + 自动故障转移（active-standby）**：
- 只有一个 **canonical 后端**持有 `~/.deskmate` 并真正执行 L2 任务；
- 另一端是**客户端 / 备援**，自己不执行 L2；
- 两者通过**同一份状态**互通，"谁领了哪个任务、冷却到几点"两边都看得到 → **不重复**；
- 主端不在时，备端**自动接管**继续未完成的 → **不断档、互补**。

**落地风味（首版先选一个）**：
- **风味 C（推荐，近零代码改动）— 云端为家，本地为窗**：
  - 云端 `openworker-server` 常驻、持有 `/var/lib/openworker/.deskmate`、L2 **开启**（7×24 worker，阶段 7 已设 `DESKMATE_L2_ENABLED=1`）；
  - 本地 Mac 桌宠**改为连云端**：Tauri 前端 API base 指向隧道 URL（走腾讯隧道 + 登录鉴权），**本地 sidecar 后端不启 L2**（或根本不启后端、纯客户端）；
  - 效果：你在 Mac 前 = 多一块交互屏（聊天/看动画本地、响应快）；Mac 睡了 = 云端继续发帖/回信/写手记，醒来接着看同一份状态。**零重复、零 gap，上云 = L2 真正 7×24。**
  - 代价：本地桌宠需联网才能用；本地不再"独立"干活（大脑在云端）。
  - ⚠ 关键安全规则：**本地绝不跑一个连同一份云端 DB 的第二个后端**（SQLite 跨网络双写会损坏）。本地要么纯客户端、要么本地后端只连自己那份库且 `L2_ENABLED=0`。
- **风味 D（真·本地为主 + 云端兜底，需改代码）— 双后端共享 DB + 心跳/claim**：
  - 本地 + 云端都跑后端、都连**同一份**云端 DB（DB 需服务化或走单写代理，避免 SQLite 双写并发）；
  - 加 heartbeat：本地写心跳到共享状态，云端 scheduler 检测"本地心跳新鲜 → 云端 standby 不抢 L2；本地心跳过期（睡/关）→ 云端 claim 接管 L2"；每个待执行任务加 claim/锁，谁领到谁做；
  - 好处：最贴合"A 没完成 B 继续"的字面语义；本地离线也能用小桔（连本地 sidecar），回来再 sync；
  - 代价：要解 SQLite 并发（DB 服务化或单写代理）、加 heartbeat/claim 逻辑，工作量不小 → 作为上云后的**后续加固**，不在首版。

**首版按风味 C 部署**（先把云端价值跑起来）；风味 D 等你确认"本地离线也要能用桌宠"再排期。
