## 三、P2-R2 截断：技术判断（实测，非猜）

**现状（store.py:941-962 实测）**：
```
sql += " ORDER BY bm25(profile_items_fts) LIMIT ?"   # L941-942, LIMIT=top_k=8
params.append(max(1, min(int(top_k), 50)))
...
hits = [FTS 结果][:8]                                 # L949-952
if DESKMATE_ANCHOR_RECALL != "0" and hits:            # L957
    hits.extend(self._recall_anchor_neighbors(...))   # L959, 追加 ≤5 邻居
return hits[:top_k]                                   # L962, 再截到 8
```
→ FTS 已返回满 8 条时，`hits` = `[8 fts] + [≤5 nb]` = 13，`:8` 把**全部邻居截掉**。邻居仅在 FTS 稀疏（<8）时露出。
→ 汇流在萧哥**密集写作**（一个话题下 FTS 命中很多）时静默失效——正是「白做了」风险。

**三种方案对比**：
- **A 维持现状**：拒绝。P1 头条特性在负载下 no-op。
- **B 保留配额（采用）**：邻居恒现，最小改动、零消费方影响。
  实现（精炼版，不退化通用召回）：
  ```python
  hits = fts_rows[:top_k]                      # 不变，FTS 仍可取满
  if anchor_recall and hits:
      nbs = self._recall_anchor_neighbors(hits, excl)   # ≤5
      if nbs:
          keep = max(0, top_k - len(nbs))       # 有邻居才为邻居让位
          hits = hits[:keep] + nbs              # 无邻居时 hits 完全不变
  return hits
  ```
  语义：无邻居 → FTS 满 8（通用记忆召回不退化）；有邻居 → FTS 让位给邻居，邻居**永现**。直击 P1「汇成河」承诺。
- **C 双通道（hits / anchor_neighbors 分返回）**：更彻底，但改返回契约、动 memory_injector 消费方。留待未来有独立「相关推荐」surface 时再做。

**判定**：P2-R2 采用 **Option B**。既最简（改动 4 行），又是根治（编码「邻居有保底可见性」），不是 raise top_k 那种 workaround。
