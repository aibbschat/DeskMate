## §10 C 项实测：双进程多库并发互不干扰验证

> 实测时间 2026-10-04 21:20（云端 `openworker-mirror`，隔离目录 `stress_c/`，生产库全程只读）。

### 10.1 为什么需要 C（相对 A/B 的新维度）

A/B 只证了 **`deskmate.db` 单库、同进程多线程** 在 WAL+busy_timeout 下并发双写安全。C 要补的是两个更贴近真实的维度：
1. **两个独立 OS 进程**（不是同进程线程）—— `openworker-server` 与 `xiaoju-sync` 是两进程；
2. **多库并发** —— 真实后端除 `deskmate.db` 外还写 `chat.db`/`journal.db`/`cognitive.db`，同步 daemon 同时活动。

### 10.2 方法

- 隔离目录 `/var/lib/openworker/.deskmate/stress_c/` 自建 4 个独立 SQLite 库：`deskmate.db`（复用生产 DDL+9 触发器+learned_history，已剔 FTS 影子表）、`chat.db`、`journal.db`、`cognitive.db`，各设 `journal_mode=wal`、`busy_timeout=5000`、`synchronous=FULL`。
- **后端进程（独立 PID）**：循环写 `deskmate.db(learned_history, entity=c_backend_*)` + `chat.db` + `journal.db` + `cognitive.db`（每轮 4 个库各一写）。
- **同步 daemon 进程（独立 PID）**：循环写 `deskmate.db(learned_history, entity=c_daemon_*)`（模拟把远端变更 apply 回本地，即双进程**同时写同一库**的最坏情形），并周期性读 `chat.db`。
- 两进程真并发跑 180s，各自统计 ok/err/busy。校验按规矩用**独立只读连接**复算（不依赖运行期聚合）。

### 10.3 结果

**运行期聚合（c_run.py 输出）：**
```

DAEMON : {"role":"daemon", "ok":433049,"err":0,"busy":0,"wrote":433049}
```

```json

  "journal_integrity": "ok", "cognitive_integrity": "ok"
```

### 10.4 两条核心结论

**① 数据层安全 VERIFIED（多进程 + 多库维度，且可独立复现）：**
- `learned_history` 总数 `433,163 = 114（后端）+ 433,049（daemon）`，零差；
- 两个进程的写入**触发器均 100% 捕获**（后端 114 / daemon 433,049），无丢失；
- `chat/journal/cognitive` 各 114 行（仅后端写，与后端 ok=114 完全吻合），证明后端多库写入**互不干扰、互不串库**；
- **四个库 integrity 全部 ok**，无损坏、无死锁、无 `err`。
- 这把 §9.3① 的信任缺口**彻底闭合**——本次 C 的隔离库 `stress_c/` 已保留（不像 `.deskmate_iso` 被删），任何人可随时只读复算。

**② 暴露「双进程争抢同库 → 吞吐饥饿」（这是保留护栏的新硬理由）：**
- 后端在 180s 内只成功写 114 次，而 daemon 写了 433,049 次——相差约 3800 倍。
- 原因：SQLite WAL 只允许一个写者持有写锁，且**不保证公平**；daemon 是紧循环单一写入、几乎常占 `deskmate.db` 写锁，后端每轮还要额外提交 chat/journal/cognitive 三库，被持续饿死（`busy=12` 即 12 次等满 5s 超时后放弃回滚，属 busy_timeout 正常兜底，非错误）。
- **这是安全行为（无丢失），但是吞吐/延迟行为**——若生产里 `openworker-server` 与 `xiaoju-sync` 真的同时写 `deskmate.db`，轻量一方会被饿到高延迟甚至超时。护栏（`Conflicts=` + `_cloud_server_running` 拒绝启动）防的正是这个**双进程双主同库写**场景。

### 10.5 对护栏去留的结论

- C 没推翻 A/B 的数据层安全结论，反而在**进程级 + 多库级**补实了它（无丢失、无损坏、可独立复现）。
- **但同时给出保留护栏的实测依据**：双进程争抢同库会饿死轻量写入方。这与 §四.3 / §9.4 的判断一致——**护栏不应删除**。
- 终判：数据层双写安全已 verified（A/B/C 三向）；运行态护栏（防两进程双主）基于 C 实测的饥饿证据**更该保留**。删护栏须先满足「后端常驻首周零饥饿告警 + C 重现实验证明公平调度可行」，二者皆未达。
