## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 谁写的 | 写入动作是 `append_to_section("user", …) → save_user → atomic_write_locked`；**触发它的是当时仓库里跑的测试/验证进程，不是桌面端的自动记忆同步或复盘写入**（确证见 §2.1） |
| 为什么重复 | 不是"反复拼接旧内容"，而是**读取源被测试替身替换**：`load_user` 被 monkeypatch 成返回 `"画像"*4000`，`append_to_section` 拿它当"现有内容"再拼上抽取出的提示词残句，写入真实 USER.md。合成结果与事故快照**逐字节一致**（确证） |
| 是否并发导致 | 不是并发交错。事故时**不存在** sha256 读前写前双校验；原子写 + fcntl 只能防半截/交错，防不住"写入内容本身就是错的" |
| 丢失范围 | 8,000 字退化区是**合成占位串**，不含任何原始正文；与 16:43 备份做行级比对，除 12 个已迁 journal 的「自动复盘」标题外无实质缺失。17:36 索引副本未留存，该窗口无法事后独立复核（见 §4） |
| 防护 | `user_profile.save_user` 单一收口：重复度 / 分节结构 / 长度突变三道检查，异常拒写 + 现场快照 + `alerts.log`；每次正常写入前轮转备份（保留 5 份） |

| 重启后是否生效 | 立刻生效，无需额外操作；重启即加载新代码，首轮对话开始监测 |

## 2. 根因

### 2.1 谁写的（确证部分）

**写入调用链（全部为实际执行路径，非推测）：**

1. 抽取：`post_session_summary`（`deskmate/memory/manager.py:2958`）
   → `_extract_single_session`（`manager.py:2756`）
   → 事实文本 `2026-11-11: 用户不希望再原样重复）---`
2. 写入：`append_to_section("user", fact_text)`（`manager.py:2850`）
   → 用户分支 `current = load_user(self.base_dir)`（`manager.py:1926`）
   → `updated = current.rstrip() + "\n\n" + entry`（`manager.py:1954`）
   → `save_user(self.base_dir, updated)`（`manager.py:1957`）
   → `atomic_write_locked`（`deskmate/memory/user_profile.py:137` 起）
3. 同步落 vault：`self.vault.write_entry(..., source=f"session-{session_file.stem}")`（`manager.py:2861`）

**三项证据把时间与内容钉死：**

1. **vault 同源证据**：`~/.deskmate/vault/preferences/2026-11-11.md` 内容正是
   `2026-11-11: 用户不希望再原样重复）---`，frontmatter `source: session-1794390068058416000`，mtime **17:41:08**。
   这与损坏文件尾部半句、以及 `manager.py:2861` 的 `source` 拼接格式完全一致。
2. **字节级合成证据**：损坏文件 = `("画像"*4000) + "\n\n" + 上述残句`，
   在 Python 中直接拼接与快照 `==` 为 `True`（8,028 字符 / 24,050 字节）。
   分隔符 `"\n\n"` 正是 `append_to_section` 的拼接格式（`manager.py:1954`）。
3. **字符串唯一来源**：全仓库检索 `"画像"*4000`，生产代码**零处**，唯一出现是
   `tests/test_context_budget.py:158`（`heavy_manager` fixture 里
   `monkeypatch.setattr("deskmate.memory.manager.load_user", lambda base: "画像" * 4000)`）。

**因此，17:41:08 的写入进程不是桌面端的常规记忆同步，而是当时仓库内的测试/验证进程：**
它一边用**真实 `~/.deskmate`** 作 `base_dir`，一边让 `deskmate.memory.manager.load_user`
处于**测试替身状态**（返回 `"画像"*4000`）。`append_to_section` 读到替身内容后，
`save_user` 把它当成"用户画像"原子写入真实文件。

**同一秒的三处"测试泄漏到真实目录"佐证该进程身份：**

- `~/.deskmate/sessions/1794390068058416000.md` 内标题为
  「盯一个会出错的目标」——该字符串**只存在于** `tests/test_autonomy_loop.py`；
- `~/.config/coworker/creation_pipelines.json` 中出现 `concept=测试概念`、
  `executor_kind=stub` 的条目，来自 `tests/test_creation_pipeline.py`；
- 真实工作区 `output/` 出现同一次创建的 `测试概念_outline_20261111-174108.docx`。

即：那一刻 pytest/验证脚本确实在往真实用户目录里写东西，`USER.md` 只是其中一个受害者。

### 2.2 为什么会产生重复文本（逐条排除）

| 假设 | 是否成立 | 证据 |
|---|---|---|
| 把已有内容当新增反复拼接 | **排除**（作为"拼接旧内容"不成立） | 旧文件 9,334 字符在损坏文件中**一字不剩**；普通追加必然保留旧内容。真实机制是"读到的旧内容本身就是替身串" |
| 截断后错误回填 | **排除** | 损坏内容与旧文件无任何前缀/后缀/切片关系；旧文件任何片段都不在损坏串中 |
| 模板/编码环节把片段展开 | **排除** | 生产链路无任何构造 `"画像"*N` 的代码；4,000 次重复精确等于测试常量，不是随机退化 |
| 并发读半截再写回 | **排除** | `atomic_write_locked` 先写临时文件再 `os.replace`，读者只会看到完整旧版或完整新版；损坏串是完整合法 UTF-8，不是半截 |
| **读取被替身劫持 + 真实目录写入** | **成立（逐字节可复现）** | 见 §2.1；在临时目录用同样替身复现，生成内容与事故快照逐字节相同 |

**复现记录（临时目录，未触碰真实 USER.md）：**

```

monkeypatch load_user -> "画像"*4000
```

这正是它能识破本次事故的关键（见 §5）。

## 3. 并发与"既有防护"

- **事故时没有 sha256 读前写前双校验**。当时 `save_user` 只有
  `atomic_write_locked`（fcntl 锁 + 临时文件 + `os.replace`），没有任何内容检查。
  因此不存在"防护生效仍被写坏"；是根本没有这层防护。
- **即便有哈希比对也拦不住**：本次读到的"旧内容"来自替身（8,000 字符），
  写出的也是合法完整的 UTF-8 文本；读写一致性校验只能发现"文件被外部改过"，
  发现不了"要写入的内容本身是错的"。
- **仍然存在的洞（非本次原因）**：`append_to_section` 是"先读后写"，
  读与写不在同一把锁内（`manager.py:1926` 读、`1957` 才加锁写）。
  两个并发写入仍可能丢更新（last-write-wins），但不会产生这类退化覆写。
  本轮不扩大改动范围，仅记录。

## 4. 丢失范围

### 4.1 结论

**8,000 字退化区不含任何原始正文**——它是测试常量 `"画像"*4000` 的合成产物，
不是"写到一半截断"或"旧内容残留"。原始画像被整篇替换，但已按下述依据恢复。

### 4.2 证据

1. **合成性**：损坏内容 = 测试常量 + 抽取残句，与旧文件无重叠（§2.1/§2.2）。
   因此"退化区"本身就是占位串，不是被截断的正文。
2. **行级比对**：以 16:43 的 `~/.deskmate/USER.md.bak`（拆分前 147 行）对照当前恢复版（137 行）：
   - 仅 17 行"只在旧备份出现"：12 个 `## 自动复盘 · 2026-10-31 … 2026-11-11` 标题，
     1 条在恢复版中已加注「（已被更新覆盖，旧值保留备查）」，
     4 条事实（在恢复版中带 `- ` 列表前缀落位）；
   - 其余全部内容行一一对应，无缺失。
3. **复盘内容已迁 journal**：`~/.deskmate/journal/2026-10.md`、`2026-11.md` 内
   有 10-31～11-10 对应的 `[归档]` 条目；被移除的只是 USER.md 里的日期标题，
   正文事实仍在 journal 与恢复版中。
4. **硬规矩与 gold 全中**：31 条硬规矩、9 条 gold 均在恢复版中（前序验收已核对）。

### 4.3 无法确证的点（如实说明）

- 17:36 那次建索引时的 `memory_chunks` 没有留下可回放副本
  （17:32 的 DB 备份早于该表创建；17:57 基线 DB 已是恢复后重建的索引）。
  因此**无法事后独立复核 16:43 备份 → 17:36 索引之间是否发生过未落盘的编辑**。
  现有痕迹显示该窗口没有其他写入（growth/vault 时间戳都集中在 17:41:08）。
- 进一步收紧的办法：APFS 本地快照/Time Machine；或今后依赖 `user-rolling` 的逐次快照。

## 5. 防护（实现位置、阈值、误伤评估）

### 5.1 位置：USER.md 写入的唯一收口

`deskmate/memory/user_profile.py`

| 函数 | 行号 | 作用 |
|---|---|---|
| `check_user_content(content, old)` | 68 | 三道内容检查，返回 `(ok, reason)` |
| `_record_alert` | 97 | 拒写时留存现场快照 + 追加 `alerts.log` |
| `_rolling_backup` | 121 | 每次正常写入前轮转备份 |
| `save_user(..., force=False)` | 137 | 检查 → 轮转 → 原子写；**读旧内容直接读磁盘** |
| `check_user_file_health` | 195 | 旁路监测（见 §6） |

所有 USER.md 写入都已改走该函数并**检查返回值**：
`write_memory`（`manager.py:1200`）、`replace_section_entry`（1250）、
`remove_section_entry`（1286）、`append_to_section`（1957）、`_replace_user_entry`（2226）；
压缩（2169）与 dream（2309）被拒时原文件保持不变（静默保护，不影响流程）。

### 5.2 触发阈值

| 检查 | 阈值 | 理由 |
|---|---|---|
| 退化重复（单字符） | 同一字符连续 ≥ 200 次 | 正常中文不会出现 |
| 退化重复（片段） | 同一 2 字单元连续 ≥ 50 次（如 `画像` × 50） | 命中本次事故形态，正常行文不可能 |
| 分节结构丢失 | 旧文件 ≥ 3 个 `##` 且新内容 0 个 | 拦住"整篇变成一坨文本" |
| 长度骤降 | 新 ≤ `max(200, 旧×25%)` | 压缩任务最多减 30–40%，25% 下探仍留余量 |
| 长度骤增 | 新 ≥ 旧×4 且 > 4,000 字符 | 拦住异常膨胀 |
| 保护性跳过 | 旧文件 < 300 字符时跳过结构与长度检查 | 首次写入/模板阶段不误伤 |

### 5.3 会不会误伤

- 正常追加：放行（长度只增、结构保留）。
- 正常压缩（约 −30%，实测约七成保留）：放行（有回归用例）。
- 局部替换 / 删除条目 / 手动精简：放行。
- 整篇重写（如 `reset_user`）：走 `force=True` 逃生口，不会卡死。
- 唯一会拦的是"整篇覆写且重复/结构/长度异常"，即本次事故形态。

### 5.4 留存

- 拒写现场：`~/.deskmate/backups/user-rejected/USER.md.rejected-<时间戳>.bak`（保留最近 20 份）
- 审计行：`~/.deskmate/alerts.log`
  `时间 \t USER.md \t 拒绝写入 \t 原因 \t size=… \t sha256=前16位`
- 正常轮转：`~/.deskmate/backups/user-rolling/USER.md.<时间戳>.bak`（保留 5 份）

## 6. 监测（第一时间发现）

- **落点**：`build_full_context_for_turn` 入口（`deskmate/memory/manager.py:618`，

## 8. 关掉桌面端 / 重启后的生效情况

- 防护是**进程内代码**：重启桌面端即加载新代码，**立刻生效，无需迁移或额外操作**。
- 监测在重启后的**第一轮对话**开始工作（此后 5 分钟节流一次）。
- 关闭期间不产生写入，也不需要监测。
- 重启后看三个信号即可确认生效：
