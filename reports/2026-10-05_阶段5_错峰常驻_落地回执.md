### 1.1 关键设计：游标追平即提前收工

窗口**不是定时 5 分钟**，而是**游标追平就收工**，5 分钟只是硬上限：

```bash
# 每 10s 轮询，pull_after_seq >= oplog_max(seq) 即视为追平，立即收工
```

**实测首轮窗口：10 秒收工**（基线 pull=1291 / oplog_max=1290，本已追平）。
真实场景下窗口时长取决于增量大小，通常 30 秒内完成。

> **这比"固定 5 分钟"重要得多**：她掉线的时间从 5 分钟降到实际所需，接近 0。

### 1.2 出窗口后强制核对

沿用 3b 方案「硬要求 1」判据——**游标交叉对齐**，结果写入 `/var/log/xiaoju-sync-window.log`：

```
[2026-10-05 06:18:32] 窗口后 pull=1291 oplog_max=1290 [ALIGNED] backend=active daemon=inactive 用时=10s
```

若为 `NOT_ALIGNED` 即说明窗口内积压未补齐，需人工介入——这是**唯一的告警点**，补上了此前"401 静默盲区"的同类问题。

## 3. 已知代价（必须知情）

### 3.1 每小时约 10–30 秒的短暂不可用

`Conflicts=openworker-server.service` 决定了：窗口内后端必须停。窗口时长≈实际增量同步时间（实测 10s），因此她**每小时掉线约 10–30 秒**。

**若要彻底消除**：需解决闭环复验 §10.4② 的**写饥饿**（给同步 daemon 加写节流），届时才可能让两进程真共存。当前方案是"用极短窗口换常驻"。

### 3.2 记忆同步从秒级降为小时级

Mac 上产生的记忆，最长需等 1 小时才会进云。**兜底**：Mac 端 daemon 若仍常驻（当前未改），Mac↔云仍走隧道实时同步；本次改的是**云端常驻服务**的启停方式，不影响 Mac 侧行为。

### 3.3 机器重启时序

`openworker-server` 已 enable（开机自启），`xiaoju-sync` 已 disable。重启后：后端自动起，同步等下一个整点 :02 窗口。

## 4. 遇到的问题（已修复，记录备查）

| 问题 | 原因 | 修复 |
|---|---|---|
| 窗口脚本末行报 `ELIGN: unbound variable` | 变量名笔误（定义 `ALIGN`，输出 `ELIGN`） | `sed -i` 修正，`bash -n` 通过 |
| `timer has a bad unit file setting` | `OnCalendar=*:02/60` **不是合法的 systemd 日历语法** | 改为 `*-*-* *:02:00`，`systemd-analyze calendar` 验证通过 |
| 端口 8765 被谁占 | 一度怀疑冲突 | 实为**设计如此**：oplog server 与后端共用 8765，故有 `Conflicts=`；已由端口分离（18767）缓解但未根治 |

## 6. 后续可选动作

1. **回滚路径**（随时可用）：
   ```bash
   sudo systemctl disable --now xiaoju-sync-window.timer
   sudo systemctl enable --now xiaoju-sync      # 恢复原来 daemon 常驻
   sudo systemctl disable --now openworker-server # 或维持常驻
   ```
2. **彻底消除掉线**：解决写饥饿后，改「同步 daemon 加节流 + 两进程共存」。
3. **窗口频率可调**：改 `OnCalendar` 即可（如每 2 小时 `*-*-* */2:02:00`）。
