# 团队协作成熟化方案：上游对齐 × 业界对标 × 三目标落地

> 日期：2026-10-31 · 作者：萧哥侧调研（上游精读 ×2 + 业界调研 ×1 + 事故取证）
> 起因：夜不收 V3 团队轮（jigang/dengying/mingcha）「三人八小时零字」误判中断事故。
> 目标（萧哥原话）：**这次修正之后至少能够工作流畅、顺利产出，是一个成熟的产品，而不是继续修修补补。**
> 三个子目标：① 给主编足够视野，看到成员每一步动作；② 给足够执行时间且中间不断层（审批、断点重续）；③ 在①②之上保证配合流畅。

---

## 〇、结论先行

**这不是一个"再修几个 bug"的问题，而是一次「移植对齐债」的清算。**

- 上游 OpenWorker（origin/main，2026-10-26，PR #792）已经把团队协作的 80% 机制造好了：不可变团队工件、案例日志、双游标投递、唤醒过滤合批、委托审批、durable resume、watchdog、自续命协议、上下文压缩契约。
- 本地移植时：**接线层漏了 7 处**（最致命是 `artifact_tools` 整套没接——worker 产出对全队不可见的直接原因）；**人设教义反了 5 处**（主编被命令用一个她没有的工具去轮询，而上游明令禁止轮询）；**连续性栈带着 11 处上游后来修掉的回归**（最致命是挂起审批+重启后 resume 被占位结果破坏）。
- 业界（LangGraph / OpenAI Agents SDK / Claude Code agent teams / Devin / A2A / Temporal / Restate…）补的只是上游没有的 3 件：**时区锚点、心跳式进度信号、验收闸门**。其余不必发明——上游的哲学（板面是事实源、证据上流、事件驱动不轮询）与业界公分母一致。

**三目标的一句话答案：**

| 目标 | 答案 | 主要动作 |
|---|---|---|
| ① 透明 | "在跑"必须是机器信号，永远不让主编用"有没有消息"推断 | 接回 artifact_tools；digest 带全队 running/step/tokens；worker 合同回填 set_status + journal |
| ② 不断层 | 审批等待=持久化暂停态；恢复精确到轮边界；中断不产生孤儿 | 修 trailing-call 豁免、线程安全 waiter、decide_worker_call 走 resolve_inbox；selfwake 补让位协议 |
| ③ 流畅 | 干预一律排队到轮次边界，声明一律过闸门；主编事件驱动不轮询 | 人设教义改回上游原文；时区锚点；`_actionable_team_events` 过滤 + 2s 合批；lost_assignment 即时中断 |

## 一、事故根因链（30 秒版，取证见 `~/.deskmate` 与四份会话记录）

1. **时区错觉**：看板工具给 agent 的 `ts` 是 UTC 裸串（上游同款），主编拿 `02:37` 减本地时钟 `10:57` 算出「八小时」——实际派活到中断只有 **21 分钟**。
2. **产出不可见**：jigang 10:57:47 已写出 32KB 合格骨架（`~/OpenWorker/0e7e2124ac83/V3-骨架…md`），mingcha 已写 2 份台账——但 `artifact_tools` 未接线，worker 文件落在主编感知范围之外，看板评论为零 →「零字」。
3. **在跑被当空转**：jigang 因撞 docx 坑+大模型轮次（单轮 5-7 分钟）未转 in_progress；主编 digest 里没有任何"谁在跑"的机器信号 →「没动」。
4. **中断时机**：主编 10:58:07 全项取消，10:58:20 三个 worker 收到 interrupted——jigang 正在写她点名要的那条「章序+烧仓因果链」评论，差 33 秒交付。
5. **主编自身沉睡**：主编人设要求 sleep_until 自轮询，但 `requires_folder: true → scheduling: false`，她根本没有这个工具；10:52–10:57 之间无人能叫醒她，只有萧哥的消息可以——她醒来后没有时间感，才拿 UTC 减本地钟。

## 二、上游官方代码全景

### 2.1 连续性四支柱（manager.py / engine.py / inbox.py / selfwake.py / conversations.py）

1. **轮次互斥 + 软中断**：一会话一 turn；`request_interrupt()` 四态全杀（mid-stream/mid-tool/awaiting-approval/iteration 间）但**全部落合法历史**——部分输出存 `_partial_turn()`，pending tool_call 全补 stub，历史永不带孤儿。
2. **durable wait queue**（inbox.py）：一切人机交互 = 落盘 pending item + `(session_id, tool_call_id)` 幂等键 + 多 surface 解决（WS/REST/Slack/TG/lead 委托）；重启后 `resolve_inbox → _durable_resume → engine.resume` 精确续跑，已答的跳过不重放。
3. **self-wake + scheduler + 事件驱动 + watchdog**：`sleep_for/sleep_until/wake_on/wake_on_event`（调完即让位，`__coworker_yields_turn__` 强制结束轮次）；30s tick 先 team_tick 后 resume_due_wakes（异步派发，一个长轮不卡调度器）；watchdog 600s 只提醒不干预，"healthy busy workers and human waits are quiet"。
4. **append-only transcript + checkpoint + 自愈**：`turn_start / permission_required / iteration_end` 三个落盘点；读侧容忍截断行、tool 配对自愈（**trailing 未答调用豁免——durable resume 的命门**）、孤儿调用启动时补诚实 stub。

### 2.2 teams 模块（15 文件）机制速查

| 文件 | 一句话职责 |
|---|---|
| store.py | 板面唯一写入路径：哈希链事件日志 + 物化投影；动词即门卫（worker 永不能 done）；可见性= slice（assigned∪filed∪link 对端）+ claim 池 |
| artifacts.py | **团队共享的不可变文件版本**：`attach_file` 发布（≤10MB，全队可读，含未认领该 item 的同侪）、版本化不覆盖、sha256 校验、每次操作重验身份 |
| journal.py | 案例日志（finding/evidence/decision/note/raw，≤16K 摘录）；授权随 assign 流转；worker 不能授权 |
| summary.py | TeamView 投影：per-worker **running/step（解析 todo_write）/tokens/timing 归因**；纯代码只读，永不是唤醒源 |
| chat.py | 群聊：@mention 唤醒语义在读侧（未@的闲聊永不唤醒）；`record_on_item` 双写板面 |
| registry.py | roster + 每小时 60 次唤醒预算闸（只在轮次间生效） |
| tokens.py | 外部板面客户端身份（`owb_` 令牌，只存哈希） |
| proposals.py | 组队/拆项两道结构化提案门（依赖图环检测、final_acceptance 必须存在） |
| tools.py | 动词→工具，角色过滤（worker 见不到 assign）；`set_status` 不唤醒；comment 工具内写明 handoff 纪律 |
| dialect.py / cli.py / mcp_server.py | 本地直连 / HTTP / CLI / MCP 四种接入面，同一 store 权威 |

### 2.3 上游三目标的原生解法

**透明（7 层）**：① artifacts 版本化工件；② journal 证据；③ digest 行（assigned/moved/filed/waiting/comment/chat——**不含工具流水，靠板面动词留痕**）；④ summary（running/step/tokens → 前端）；⑤ chat；⑥ WORKER_WAITING + decide_worker_call；⑦ 前端组件。**关键设计：工件发布本身不唤醒主编（"Publications are evidence, review is the handoff"），needs_attention 才唤醒**——透明不等于打扰。

**连续**：审批挂起即持久暂停点（`persist_session` 在挂起瞬间落盘）；无超时（watchdog 把人类等待视为健康静默）；压缩有完整契约（80%/250k 触发、用户消息第一条钉死全保留、verbatim 转录落盘可回读、"re-read it" 续跑指令）。

**流畅**：`delivery_page` 单扫描双游标（订阅游标永不跃过未扫描的直接指令）；`_actionable_team_events` 唤醒过滤（例行评论/工件发布不造模型轮）；主编侧 2 秒合批；steer 注入**迭代边界**（busy 会话不杀）；`lost_assignment` 改派即时中断；`mark_idle` 收尾即踢 team_tick（轮次结束=投递时刻）；每 worker digest 附全队 roster（@name 可达）。

### 2.4 上游人设教义（swe-lead / swe-worker 合同，本地创作组人设的蓝本）

- lead："**no polling or sleep timer is needed while teammates work**… never to periodically ask whether the team is finished"；"Instructions flow down, evidence flows up… never ask a worker 'how's it going'"；"your context window is disposable, **the board is not**"。
- worker："**Journal as you go** (journal_append)… Your transcript is disposable; the journal survives to your successor"；"At a meaningful step change, use `set_status`… **Do not post heartbeats**"；"Finish = transition to review with a TIGHT hand-off comment… full evidence belongs in the journal"；"**You NEVER mark your own work done**"；"no silent skips"。

### 3.1 接线层漏了 7 处（teams 文件本体与上游逐字节一致，差距全在 manager 接线）

| # | 漏接 | 上游位置 | 后果 |

| 2 | `board_tools(roots=, on_change=)` 实时闭包未传 | L2834-2837 | `attach_image` 因 roots 恒空 **fail-closed 实际不可用**；板面变更不立即踢投递 |

### 3.2 连续性回归 11 处（上游分叉后修的，fork 带着旧伤）

按严重度：

1. **`_repair_tool_pairing` 无 trailing-call 豁免**（conversations.py）——挂起审批中重启的会话，pending call 被塞占位结果 → durable resume 空转，审批解决后不再续跑。**连续性最实质的回归**。
2. **inbox `waiter.set()` 非线程安全**——REST/lead 委托从非事件循环线程 resolve 可能不唤醒挂起 agent（偶发永久悬挂）。
3. **无 `promote_to_inbox`**——最后一个 viewer 关窗后 inline 审批卡不可见地等。
4. **无 `stop_session`/`stopped_sessions`**——用户 Stop 后 timer 照常唤醒。
5. **`_lead_decide_worker_call` 直连 `inbox.resolve` 不走 `resolve_inbox`**——主编批完 worker 的挂起调用**不触发 durable resume**，worker 要等下一次板面事件才动（上游 b691c687 移植了工具但没移植这条语义）。
6. **`resume_due_wakes` 顺序 await**——一个慢 worker 轮卡死整个调度 tick，所有团队投递延后。
7. **后台引擎无默认 team/items approver**——重建的引擎无法组队/拆项（上游 2026-09-05 修过的 headless 死路）。
8. **定时任务 BYPASS + 全 ONCE**——无人值守自动化无"问人"退路（与上游 §25 优雅降级哲学相反；§十五 已定性，此处只登记不擅改）。
9. **历史缩短重写非原子**——崩溃窗口可清空 transcript。
10. selfwake **缺 `sleep_for`、缺 `_END_TURN_HINT`/`__coworker_yields_turn__`**——worker 调 sleep_until 后轮次不强制让位，续命协议只有一半。
11. permissions 缺 run-grant/trust/site-wall（审批疲劳源；§十五 红线，另议）。

### 3.3 人设教义偏差 5 处（创作组四 manifest vs 上游合同）

| # | 上游 | 本地 | 后果 |
|---|---|---|---|
| 1 | lead：**不轮询**，事件驱动，sleep 只用于明确 deadline | 主编人设：强制 3-20 分钟自轮询 | 催更风暴（15 分钟 10 条 steer） |
| 2 | lead 有 sleep 工具可用（scheduling 默认） | 主编 `requires_folder: true` → scheduling=false → **没有 sleep_until**，人设却命令她用 | 主编沉睡无人能叫醒（10:52-10:57） |
| 3 | worker：journal as you go | 创作工人设**零字提 journal** | 没人留证据，主编只能看评论 |
| 4 | worker：step change 用 `set_status`（单行、不唤醒、不发心跳） | 人设不知道有这个工具 | 板面无轻量进度行 |
| 5 | worker：tight handoff（评论短段落+refs，全文进 journal/artifact） | 人设只说「把进度落到工作项或日志」 | 交付物去哪、主编看什么，全凭模型发挥 |

### 3.4 上游也没有、本地必须自补的（本地特有场景）

1. **时区锚**：上游用户看 GUI（前端渲染本地时间），agent 不做时间算术；我们的主编是 AI，直接拿 UTC 裸串减本地钟。必须在工具输出/digest 层修，不能靠提示词自觉（她 10:45 换算对过一次、10:57 又算错——压力下必错）。
2. **慢模型节奏标尺**：上游推荐 opus 级模型跑 swe 团队；我们的 deepseek-v4.1-flash 单轮 2-7 分钟、32KB 交付物 5-7 分钟。主编的"正常耗时"心智模型必须由系统给（digest 标注"X 已在跑 N 分钟，属正常区间"），不能靠人设写死数字。
3. **docx 正文读取**：上游无此场景；本地已在工作区修好（`files.py` + `file_reader.py` + `test_read_file_docx.py`，未提交）。

## 四、业界对标（12 家，A/B/C 框架）

### 4.1 三问题的业界公分母

- **A 透明**：结构化事件流 + 显式状态机。"空闲"必须被**声明**（Claude Code idle notification："teammate finishes and stops, it automatically notifies the lead and includes its final answer"），永远不由"没消息"推断（Claude Code 官方 Limitations 自己也踩："task status can lag"）。
- **B 连续**：审批等待=可序列化暂停态（OpenAI RunState "designed to be durable… store pending work in a database or queue"；Restate 连超时余量都持久化）；恢复粒度=轮/checkpoint 边界（LangGraph "resumes from the start of the node, re-executing all logic"——恢复轮会重跑，轮内逻辑须幂等前置）；**运行中阻塞式人工介入是官方级反模式**（AutoGen："will hold up the team's progress and put the team in an unstable state that cannot be saved or resumed"）。
- **C 流畅**：共享任务列表+依赖+文件锁认领（Claude Code）；产出走**引用回传**不走消息搬运（Anthropic："pass lightweight references back to the coordinator"——防 game of telephone）；只读旁路询问不打断主轮（Devin Side Chats）；完成闸门（Claude Code `TaskCompleted` hook exit 2 打回；CrewAI manager "reviews outputs, and assesses task completion"）。

### 4.2 Top 10 可移植机制 → 落点

| # | 机制 | 解决 | 落点 | 参照 |
|---|---|---|---|---|
| 1 | worker 心跳/进度信号 | A | **用上游现成的 `set_status`（工具已随 tools.py 同步可用）+ digest 带 summary 的 running/step**——不新造事件类型 | Temporal heartbeat、A2A statusUpdate |
| 2 | 显式任务状态机+中断子状态 | A/B/C | 上游 ItemState 已是状态机；补 `input-required` 语义=WORKER_WAITING 已有；**不加新 schema**，digest 呈现层强化 | A2A 8 态 |
| 3 | 空闲是声明出来的 | A/C | worker 人设回填 handoff/idle 纪律 + `_stalled_team_state` 已判 is_running（fork 已有 `_revive_stalled_workers`，保留） | Claude Code idle notifications |
| 4 | 审批=持久化暂停 | B | 上游 inbox+`persist_session`+durable resume 已是此设计——**修 §3.2 的 1/2/5 把它接通** | OpenAI RunState、Restate |
| 5 | 每轮 checkpoint | B | 上游 `iteration_end` 落盘点已有——**修 trailing 豁免让它真可恢复** | LangGraph checkpointer |
| 6 | 产出走 artifact 引用 | A/C | **接回 artifact_tools 即得**（版本化、全队可读、sha256） | Anthropic、ADK、A2A Artifacts |
| 7 | 依赖图+认领锁+背压 | C | 上游 blocks link+claim 仲裁已有；背压=唤醒预算闸已有；**接回 `lost_assignment`** | Claude Code、Temporal |
| 8 | 完成闸门 | A/C | 上游"worker 永不能 done+review 门"已是闸门；可选 P2 加机械验收 hook | Claude Code hooks |
| 9 | 只读旁路+轮次间反馈 | C | 上游 steer 注入迭代边界已是此设计；教义上写明"催=评论，不=打断" | Devin、AutoGen |
| 10 | 统一观测时间线 | A | 前端 TeamView（在飞未提交工作）吃 summary；digest 侧补 running 行即 agent 版 | LangSmith、Devin |

### 4.3 明确不抄的（防过度工程）

- **不新造 `progress` 事件类型/新表**：上游 `set_status`（单行、不唤醒）+ todo 解析（summary step）已覆盖，新造事件只会加哈希链噪声。
- **不引入 LangGraph 式全量 checkpoint replay**：我们 transcript 天然 append-only + 轮边界恢复，粒度已够。
- **不做审批超时默认放行/拒绝**：上游哲学=watchdog 兜底提醒，超时自动化与 §十五 权限红线纠缠，只做"等待中的 worker 在 digest 里持续可见"。
- **不做自由群聊式多 Agent 议事**：MetaGPT 发布订阅/AutoGen speaker selection 适合并行研究，不适合我们的流水线门禁（串行验收是产品语义）。

## 五、修正方案（三层，全部落到文件级）

### 第一层 P0：把上游接回来（对齐即修复，1-2 天）

> 原则：**能用上游代码就不写新代码。** 以下每项都先写红测试再改（仓库先红后绿文化）。

1. **接 `artifact_tools`**（manager `_team_tools_for`，对齐上游 L2841-2855）：worker+lead 都获得 `attach_file / list_team_artifacts / read_team_artifact`。
   验证：worker 写文件→`attach_file`→主编 `list_team_artifacts` 可见、`get_item_comments` 带 artifact 元数据、TeamView 附件可开。
2. **补 `board_tools(roots=…, on_change=kick_team_tick)` 闭包**：`attach_image` 从 fail-closed 变可用；板面变更即时投递。
3. **投递对齐**：`delivery_page` 单扫描 + `_actionable_team_events` 过滤 + 主编 2s 合批 + `lost_assignment` 中断。

## 六、「成熟」的验收标准（可测定义）

### 6.0 时钟预算：一个大纲不需要 4 小时，需要 ≤ 90 分钟

基于本轮实测单环节耗时（flash 全员），V3 整轮的诚实预算：

| 环节 | 耗时（实测/推算，deepseek-v4.1-flash） |
|---|---|
| jigang 骨架（读料+规划+32KB 生成） | **20–30 分钟**（本轮实测 21 分钟，含 7 分钟 docx 弯路——已修，扣掉后 14 分钟即接近交付） |
| dengying 三块硬料（含史料核对） | 30–40 分钟（与上并行） |
| mingcha 六份台账（压缩修好后） | 35–45 分钟（与上并行；本轮 20 分钟被 4 次压缩拖成只交 2 份） |
| mingcha 审骨架 + 主编验收拍板 | 15–20 分钟 |
| 一轮打回修改（如有） | 15–20 分钟 |
| **端到端（三线并行 + 一轮修改）** | **≤ 90 分钟** |

四个烧时钟的因素，方案里各有对应：模型吞吐（flash 写 32KB 骨架单次生成 5.6 分钟，物理下限）；steer 重读（每次改向=worker 一轮 2–5 分钟重读，本轮三次改向烧掉 10–15 分钟——P0 教义+spec 版本治）；压缩风暴（本轮 4 次×2–3 分钟重取——P1 治）；docx 弯路 7 分钟（已修）。

**最大的单一杠杆是模型档位**：上游 personas 本就有 `recommended_models`（swe 系列推荐 opus 级）。若要把「一小时一个大纲」定为产品标尺，给 outline-writer 这种长文生成角色配中档以上模型（其余角色 flash 足够），端到端可压到 ≤ 60 分钟。

### 6.1 验收 A：真实任务，硬时钟（夜不收 V3 原任务书重跑，同 #10/#11/#14 criteria，只发一次开工指令）

| # | 断言 | 类型 |
|---|---|---|
| 1 | 主编每次 wake 的 digest 含全队 running/idle/waiting/blocked 行；任一 worker is_running 时**永不**被描述为"没动" | e2e + 单测 |
| 2 | worker 每次实质写文件后 2 分钟内在板面出现 artifact 引用（attach_file 或 handoff 评论带 refs） | e2e |

### 6.2 验收 B：机制浸泡（自动化，不吃真实创作任务）

慢机制（watchdog 兜底、唤醒预算、durable resume）只在长窗口里现形，但不需要用真大纲来泡——用合成任务（如"逐章抄写台账"N 轮）自动跑 ≥ 3 小时，中途注入：一次 `kill -9` 重启、一次挂起审批（主编 5 分钟后代批）、三次改向 steer、一次 10 分钟人为静默。断言：零人工干预下无静默蒸发、无预算暂停、无孤儿调用、每 5 分钟主编 digest 可见真实进度。
