# 小桔云端「写作工作区」互通方案（调研 + 设计） v2

> 时间：2026-10-01 22:0x｜触发：用户反馈「迁上云后写作助手能力丧失——云端够不到本机稿子/素材库」
> 立场：不做桌面壳「远程模式」（用户否掉）；目标 = 让云端小桔能读到本机写作资产，且长期可靠、不污染原稿
> v2 修订：并入子代理调研（新增坚果云 WebDAV 选项 + 若干坑）+ 服务器实测数据

## 一、先纠正问题定性（关键）

经实测，你的写作语料**只有约 30MB 纯文本**（不含截图）：

| 位置 | 体积 | 内容 |
|---|---|---|
| ~/Desktop/写作营素材库 | 856K / 94 文件 | 素材、已成稿、初稿备份 |
| ~/Desktop/AI圈素材库 | 232K / 45 文件 | 正文、草稿备份 |
| ~/Desktop/大明快报_全书 | 392K / 12 文件 | md + docx + db |
| ~/Desktop/documents | 72K | rtf / docx / key |
| ~/Desktop 散装 | 约 0.15MB | 国子监秘闻录_全书结构大纲.md、人物特征速查表.md、写作营每日文章 |
| ~/Desktop/桌面收纳 | 19M | 待归类 |
| ~/OpenWorker/<会话id>/ ×736 | 168M | **客户端的"每会话草稿目录"**，里面混着真稿（如 d99b9b0b-db5/第四章-稻粱谋-大纲.md、d8d7c4ac-b7d/*正文*.md） |

**结论：这不是"同步技术"难题，是"哪份是准稿 + 怎么让云端看见"的问题。** 30MB 文本用最土的办法都能秒级同步；真正要设计的是**角色与边界**（谁写、谁读、冲突谁说了算）。

另外实测到一个**云端已有但没人用**的能力：小桔的书稿库是 `$DESKMATE_DIR/manuscripts/*.json`，云端现存 2 本——《国子监秘闻录》(2 章，8-01) 和《夜不收：绝命救援》(8 章，7-30)。**都是旧的**：你 7 月之后写的正文根本没进去。这就是她说"够不到稿子"的直接原因——不是权限问题，是那些文件从来没上过云。

## 二、主流产品怎么做（调研结论）

业界解决"同一份文件多端可用 + 协作"其实只有 5 种范式：

### 范式 1：厂商网盘当中枢（iCloud / Dropbox / OneDrive / Google Drive）
- 所有端都连厂商云；冲突表现为"冲突副本"（Dropbox conflicted copy / iCloud 冲突版本）。
- **对本场景致命**：iCloud **没有官方 Linux 客户端**（只有第三方 FUSE 项目 icloud-linux），Dropbox 在大陆被墙、Google 全系被墙（耶鲁的不可用清单列名），OneDrive 无官方 Linux 端。
- ⇒ **排除**：你的"第二端"是一台大陆 headless Linux，这一格直接不成立。

### 范式 2：同步引擎当中枢，且支持**角色定型**（Syncthing / Resilio）
- 无厂商云、P2P 直连；Syncthing 的杀手锏是**文件夹类型**：`Send Only`（只发不收）/ `Receive Only`（只收不发）——[官方文档](https://docs.syncthing.net/users/foldertypes.html)。
- 含义：Mac 侧 Send Only、服务器侧 Receive Only → **云端物理上不可能改你的稿、也不可能产生冲突副本**。这正是"作者写、AI 读"需要的语义。
- 代价：两端各多一个常驻进程；需要放通 TCP/UDP 22000、UDP 21027。

### 范式 3：仓库当传输层（GitHub Copilot coding agent / OpenAI Codex 云端任务 / Devin）
- 云端 agent 拿到的是**仓库的克隆**，改完以 **PR/补丁**交回；**它从不直接写你的工作副本**。
- ⇒ **这是最该抄的一条**：云端产出走"独立回传通道"，绝不落回原稿。

### 范式 4：远程开发同步（VS Code Remote-SSH / Dev Containers / Mutagen / docker-sync）
- 把本地项目镜像到远端算力；Mutagen 做双向并带冲突检测。
- 经验可搬：**忽略规则**、**镜像 vs 双向要显式选**、**双向必须有冲突兜底**。

### 范式 5：实时协同编辑（Notion / Google Docs / Obsidian LiveSync，CRDT）
- 为"多个人同时改同一段"设计。你这里是**一个作者 + 一个只读 AI**，属于非对称场景，上 CRDT 是杀鸡用牛刀，还会逼你换写作工具。⇒ **排除**。

## 三、推荐方案（设计原则不变，传输层三选一）

### 设计原则
1. **Mac 是唯一写入方**，云端是**只读镜像**——从机制上消灭冲突（对应范式 2 的 Send Only / Receive Only 思想）。
2. **云端产出走独立回传通道**（对应范式 3 的 PR 思想）：她的批注写进 `_小桔批注/`，原稿目录她永不写。
3. **不做全盘镜像**：只同步你点名的写作目录；736 个会话目录不整体搬（那是客户端草稿区，搬过去只会污染检索）。

### 落地形态

```
[Mac]  ~/Desktop/写作营素材库, AI圈素材库, 国子监*.md, 大明快报_全书 ...
   │   ① 单向推送（传输层 A/B/C 之一）
   ▼
[云端] /var/lib/openworker/写作/          ← 只读镜像（Mac 是唯一写入方）
   ├─ ② 小桔开一个「工作区会话」指向这里（能力已存在）→ 她直接读文件
   ├─ ③ 注册进 ingest/dirs → 素材蒸馏进记忆，语义检索可召回（embedding 今天已修好）
   └─ ④ 她的批注/建议 → 写作/_小桔批注/ → 反向通道回 Mac
```

### ② 那个「挂目录」能力，App 里本来就有（我核过代码与接口）
- `POST /v1/workspaces/open` + `GET /v1/workspaces/trusted`：**会话可以开在一个真实文件夹上**（folder gate / workspace trust）。对小桔来说，这就是"你给我挂了个目录"，**不需要开发任何新功能**。
- `GET/POST /v1/deskmate/ingest/dirs`、`POST /v1/deskmate/ingest/scan`、`POST /v1/deskmate/ingest`：目录扫描 → 勾选 → 沉淀进 `learned_history`。**云端现在这个列表是空的 `{"dirs":[]}`**。
- 书稿（查进度/人物是否飘）：两条路——(a) 让她直接读工作区里的 .md（零维护、永远最新）；(b) 把章节导入 `manuscripts/*.json`（结构化、能按章审阅）。**建议以 (a) 为主、(b) 用于定稿归档**。

## 四、传输层三选一（按"省事程度"排序）

| | A. rsync 单向推送（自建） | B. Syncthing（P2P） | C. 坚果云 WebDAV（只读挂载） |
|---|---|---|---|
| 服务器侧要装什么 | 无（rsync 3.2.7 已装） | syncthing 守护进程 | rclone（轻） |
| Mac 侧要装什么 | 无 | syncthing 或原生 app | 坚果云客户端 |
| Mac 合盖时云端读得到 | ✅（已有副本） | ✅（已有副本） | ✅（云上版本） |
| 实时性 | 定时（分钟级） | 写完即同步 | 客户端触发（秒级） |
| 是否经第三方 | 否 | 否 | **是（国内云）** |
| 需要开新端口 | 否（复用 22） | **需要 22000/tcp+udp、21027/udp** | 否（纯出网） |
| 主要风险 | Mac 不开机就不同步 | 直连可用性**需实测** | 第三方托管 + 配额 |
| 结论 | **建议先跑通这个** | 要"实时"再升级 | 不想在服务器装东西、又不介意托管时最优 |

## 五、需要你拍板的四件事

1. **哪些目录算"准稿"**？默认建议：`~/Desktop/写作营素材库`、`AI圈素材库`、`大明快报_全书`、`documents`、`桌面收纳`，以及 Desktop 根下 `国子监*.md`、`写作营*.md`。**736 个 OpenWorker 会话目录默认不搬**，除非你点名哪几个里有活稿。
2. **传输层选 A / B / C 哪个**？（我的建议：先 A 跑通，要实时再升 B；不想在服务器装东西就 C）
3. **批注要不要回传**到 Mac？（要则建一条只回传 `_小桔批注/` 的反向通道）
4. **要不要把会话开在云端那个目录上**（= 小桔以后默认在那个文件夹里帮你干活）？

## 六、我可以立刻做的

1. 在云端建 `/var/lib/openworker/写作/`（属主 openworker）；
2. 写 Mac 侧推送脚本 + launchd（沿用现有密钥与 sudoers 通道，和你的备份脚本同一套思路）；
3. 把该目录注册进 `ingest/dirs`，并用 `/v1/workspaces/open` 建一个指向它的工作区会话；
4. 跑一次全量（30MB，几秒），然后当场验证：让她列出目录、读第 N 章、检索一条素材。

## 七、关键坑（含调研补充）

1. **只读镜像**：rsync 的 `--delete` 只在写作目录内生效，务必 `--exclude` 掉 `.DS_Store`、`*.tmp`，且**不要**把 `~/OpenWorker` 整体纳入。
2. **绝不让云端写原稿目录**。Syncthing 的 Receive Only 目录里若有本地改动，界面会提示 `Revert Local Changes`，点了就撤销 → **批注必须写到方向相反的另一个目录**（这条印证了设计原则 2，不是可选项）。
3. **macOS 文件名是 NFD、Linux 按原始字节** → 中文名跨端可能出现"同名不同码点"导致重复文件；上线前做一次文件名规范化最稳。
4. **大小写冲突**：macOS 默认大小写不敏感、ext4 敏感；两端仅大小写不同的路径会报 case conflict。命名别只靠大小写区分。
5. **Syncthing 的 `.stversions` 会膨胀**：40GB 盘 + 长年版本要设 Staggered 并定期清理。
6. **二进制不可合并**：.docx 是 zip 容器，任何文件级同步都只能整文件分胜负（Obsidian 对非 Markdown 明确 last-modified-wins）。**小桔的批注请用独立 `.md/.json`，不要直接改 .docx**；`.key`(Keynote) 基本读不了。
7. **冲突副本命名各异**（Syncthing `.sync-conflict-…`、Dropbox conflicted copy、OneDrive "Copy"），AI 读目录时要过滤。
8. **隐私边界**：写作目录一旦上云就在那台服务器（或选 C 时在坚果云）上了。`桌面收纳` 19M 是杂物，建议先筛；有敏感内容只传你确认的子集。
9. **同步 ≠ 记忆**：文件到位只是"她能读到"；要被"记住并主动召回"还要走 ingest（②③）。两步都要做。

## 八、排除项复核（调研结论与我一致）

- **Dropbox / Google 全系**：大陆被墙（耶鲁官方不可用清单列名）→ 排除。
- **iCloud Drive**：无 Linux 客户端；且 `.icloud` 占位/驱逐会让第三方同步工具**读到占位文件而不是内容**（这正是"服务端读到 0 字节"的来源）；rclone 方式需 2FA、token 30 天过期 → 排除。
- **Obsidian Sync**：必须跑 Obsidian GUI、不能当 headless daemon，且无大陆节点（最近新加坡）→ 排除。
- **Scrivener**：官方要求"一端关闭另一端才能打开"，与"随时可读"直接冲突 → 排除。
- **Notion**：是 block 数据库不是文件，Linux 无官方客户端 → 排除。
- **Nextcloud**：功能全，但在 3.6GB 内存的机器上跑 PHP+DB 太重 → 排除。
- **rclone bisync**：官方文档自己强调其复杂与风险（需 --resync、误删会传播）→ 不做主力。

## 九、v3 增量（第三份调研：云端 agent 到底怎么拿到文件）

### 9.1 根本性结论：主流云端 agent **从不直接读你的笔记本**
逐产品核过（Claude Code cloud / GitHub Copilot cloud agent / OpenAI Codex cloud / Cursor Cloud / Devin / Jules）：它们全都**先把工作集搬进一个 agent 能访问的位置**（git 仓库 / 云端 VM / 挂载卷），再在那边干活——因为云端 agent 解决的是"代码仓"问题，不是"作者本机散落文件"问题。

唯一两类**反向伸进本机**的模式：Claude Code Remote Control、Cursor Self-Hosted Machines、以及远程 MCP 隧道（ngrok/Cloudflare Tunnel/Tailscale Funnel）——**全部以"本机常开在线"为前提**（Claude 官方原文：机器必须开机、进程必须一直跑）。

⇒ 对你的硬约束（笔记本可能合盖），**"让云端反向连本机"这条路是死的**。"同步一份镜像过去"不是我保守，是行业统一范式。

### 9.2 它同时确认了 Syncthing 的语义正确性
Syncthing 官方把 `Send Only` 定义为"参考副本"、`Receive Only` 定义为"只读镜像"——**"作者写、AI 只读"这个业务语义，在工具协议层是有一等公民表达的**，不是我们自创的土办法。

### 9.3 一个我要加进设计的东西：用「文件权限」再兜一层
两份调研都提到、但第三份讲得最具体：**光靠同步语义不够，服务器侧还要用文件权限把"AI 改不了原稿"钉死**。落地形态：
- 服务器上用**独立运行账号**跑小桔（现有 `openworker` 即可），另建同步账号；
- 原稿镜像目录 `/var/lib/openworker/写作/原稿`：对 openworker **只读**（`chmod a-w`，属主给同步账号）；
- 批注目录 `/var/lib/openworker/写作/批注`：openworker **可写**，且是**反向通道**（服务器 Send Only → Mac Receive Only）。
- 加上 Syncthing 的 `Receive Only` 行为（本地改动不分发、GUI 会提示 Revert Local Changes），形成"协议层 + 权限层"双保险。

### 9.4 多出来的一个轻量备选：Mutagen `one-way-replica`
`mutagen sync create --sync-mode=one-way-replica` —— 语义上就是"beta 完全镜像 alpha"，忽略规则几乎等同 gitignore；走 SSH 复用你现有密钥。**代价：要同步时 Mac 必须在线**（比 rsync 的强项是 watching 触发、更接近实时）。可当 A 的升级版。

### 9.5 明确不要做的
- ❌ 把本机 MCP server 用反向隧道暴露到公网当**主**方案：需要本机常开，且把安全面扩大（MCP 规范要求 OAuth 2.1 + PKCE，还给了一堆 prompt injection 警告）。
- ❌ 用 git 当 1–10GB 二进制素材的传输层（.docx/图片不可 diff、要作者学 git）。
- ❌ 让 AI 直接写原稿目录（协议层会被 revert，权限层会被拒）。

— 至此**两份独立调研与我的实地核查三方收敛**：形态一致（单向镜像 + 反向批注目录），分歧只在传输层选 A/B/C。
## 十一、v4 增量（第三份工程调研：只保留会影响决策的 6 条）

1. **ICP 备案（合规，重要）**：腾讯云大陆服务器**绑域名对外提供 Web 服务需 ICP 备案**。这直接解释了两件事：为什么"在云上跑 Nextcloud / 自建 Tailscale DERP（都要域名+443）"更麻烦；以及为什么 **Syncthing 用静态 IP 直连（不需要域名、不需要备案）反而最省事**。
2. **带宽数学（决定"要不要折腾"）**：腾讯云轻量常见峰值 3–5Mbps ≈ 0.5MB/s → **1GB 约 35 分钟、10GB 约 6 小时**；而**你的语料只有约 30MB → 首次全量约 1 分钟**。所以这个量级下"定时单向推送"在体感上几乎无感，没必要为它引入重型同步设施。
3. **Tailscale 排除**：官方 DERP 全球 28 个 region，**亚洲只有新加坡/东京/香港，无大陆节点**；打洞失败会绕境外（300ms+）。自建 DERP 要域名 + HTTPS + 443 —— 会与服务器上已有的 Caddy(443) 冲突。⇒ 不作为主链路。
4. **删除安全（我要写进脚本的硬规则）**：单向同步的 `--delete` 会在"源端误删/目录挂载失败/目录为空"时把删除传播上去。**必须同时加 `--backup-dir`（被删/被覆盖文件进带日期的归档）+ `--max-delete N`（超阈值中止）**，且首次一律先 `--dry-run`。
5. **远程挂载被彻底否掉**：SSHFS 项目**已停止维护**；远程挂载对"扫描几千文件"是逐文件 stat 网络往返，延迟不可接受；WoL 的 magic packet 是局域网二层广播、跨互联网不现实，合盖场景更不行。⇒ Mac 一睡 AI 就失明，不能当数据路径。
6. **兜底建议**：夜间 `rclone sync --crypt` 到腾讯云 COS 做异地快照（3-2-1 备份：Mac 原件 + 服务器镜像/版本 + COS 加密快照）。运维细节：Syncthing Web GUI(8384) **只走 SSH 隧道**，绝不暴露公网。

> 至 v4，三份独立调研 + 我的服务器实测全部收敛：**形态一致（单向镜像 + 反向批注目录），唯一分歧只在传输层 A/B/C。**
## 十二、结论一句话

**别指望任何一家网盘当"第二端"（大陆 headless Linux 那格不成立）；照抄"云 agent 只读镜像 + 独立回传"这个已被 GitHub/OpenAI 云端 agent 验证过的范式。三步走：今天用 A（rsync 单向推 30MB + 开成小桔工作区，零新增依赖、当天可验收）；要"写完即同步"上 B（Syncthing，需先放行 22000 并实测直连）；不想在服务器维护任何同步组件就用 C（坚果云 WebDAV 只读挂载，服务器实测 0.11s 可达）。无论选哪个，"Mac 唯一写入 + 云端只读 + 批注走反向目录"这条不变。**
