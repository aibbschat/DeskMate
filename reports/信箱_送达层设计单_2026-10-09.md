# 信箱 · 送达层设计单（2026-10-09）

> 配套江河设计（§九 元认知）之外的另一条自主闭环铺路石。信箱不新造数据系统，是
> `proactive_ledger` 的**呈现层** + 用「带 `mailbox_letter` 标记的隐藏会话」承载轻回信。
> 目标：根治「新开会话/首页挂一长串主动提醒」的难看与不优雅；首页只留铃铛 + 未读数，干净。

---

## 0. 结论先行

- 信箱 = `proactive_ledger` 账本的**门面**。数据底座、生产者、节流、去重、防 nag、跨端同步**全部复用现有 ledger**，不另起炉灶。
- 信箱只持**信件元数据**（未读/已读/状态/引用）；所有对话内容走**同一个聊天引擎、同一个会话消息库**。
- 轻回信（关怀类）落在「隐藏的 mailbox 会话」里，信箱以**信件样式**渲染，不进主聊天时间线；值得聊（她的提议）「进聊天」= 把会话提升为普通会话（气泡样式）。
- **UI 双视图，两套视觉语言**：信箱 = 信笺/信封样式（抬头「小桔：」/「萧哥：」+ 日期落款）；聊天 = 气泡。**绝不**在信箱里弹气泡聊天框。
- 送达侧改造，**不动发起侧**（tick 节流/去重/冷却照旧）。风险低，可独立于 P3 自主闭环先行。
- 跨端：**Mac-only 不同步**（与 2026-10-08 决策5 同口径：Mac 常驻、无需收敛）。

## 2. 架构图（单一引擎 · 双视图）

```
                 生产者（云端审计/手机灵感/关怀/访谈/观察…）
                          │ record_proactive()
                          ▼
              proactive_ledger（账本，已存在，复用）
              status: pending→delivered→read→replied|dismissed|expired
              新增列: read_at（已读回流用）
                          │ GET /v1/deskmate/mailbox
                          ▼
              ┌──────────────── 信箱（呈现层）────────────────┐
              │  铃铛 + 未读数（首页/侧栏）                      │
              │  MailboxPage：信件样式渲染                       │
              │    ├ 标已读  → POST /mailbox/{id}/read           │
              │    ├ 稍后    → POST /mailbox/{id}/snooze         │
              │    ├ 不用了  → POST /mailbox/{id}/dismiss         │
              │    ├ 进聊天  → 解除 mailbox_letter 标记，切气泡    │
              │    └ 轻回信  → 隐藏 mailbox 会话 + WS 引擎(run)   │
              └─────────────────────────────────────────────────┘
                          │ 轻回信：建/复用 mailbox 会话
                          ▼
              隐藏会话（sessions.mailbox_letter = letter_id）
              - 同一 TurnEngine（engine.run，WS 驱动）
              - 同一 messages 消息库
              - list_sessions 过滤掉（不进侧栏）
              信箱以信件样式渲染该会话往来
```

**红线（唯一）**：信箱不持有对话状态，只持信件元数据；回复 100% 走 `TurnEngine` + `conversations` 消息库。守住它，信箱/聊天怎么分都安全——她只有一个脑子，状态只有一份。

## 3. 数据模型

### 3.1 `proactive_ledger` 加一列（ledger.py `_ensure_table`）
- `read_at TEXT`：用户「标已读/已展开」的时间戳。空 = 未读。
- 状态语义补一档：`read`（已读但未回复/未处理）= `read_at` 非空 且 `status` 仍为 `pending`/`snoozed`/`delivered`。
- 未读数 = `read_at IS NULL AND status IN ('pending','snoozed') AND (snoozed_until IS NULL OR snoozed_until<=now)`。

### 3.2 `sessions` 加一列（conversations.py）
- `mailbox_letter TEXT`：非空 = 该会话是某封信的轻回信承载；`list_sessions` 过滤掉（`WHERE mailbox_letter IS NULL`）。
- 「进聊天」= `UPDATE sessions SET mailbox_letter=NULL` → 该会话出现在侧栏，信箱留「跳转看对话」引用。

### 3.3 不动的部分
- 生产者、`record_proactive`、节流/去重/防 nag、`build_handoff_opening`（保留给活跃会话相关性注入）、跨端同步触发器——全部复用。

## 4. 后端 API 契约（coworker/server/app.py，紧挨现有 handoff 端点 4201–4385）

| 方法 | 路径 | 作用 | 实现 |
|---|---|---|---|
| GET | `/v1/deskmate/mailbox?status=unread\|all` | 列信；含 `unread_count` | 包 `ledger.pending_items` + read_at 计算；返回 items + unread_count |
| POST | `/v1/deskmate/mailbox/{id}/read` | 标已读；回流情感层「用户看见了」 | `UPDATE read_at=now`；触发 `emotion_sense` 轻量回流（已读语义） |
| POST | `/v1/deskmate/mailbox/{id}/snooze` | 稍后（3 天退避复活） | 复用 `acknowledge_ledger(id, 'snoozed')` |
| POST | `/v1/deskmate/mailbox/{id}/dismiss` | 不用了（终态） | 复用 `acknowledge_ledger(id, 'dismissed')` |
| POST | `/v1/deskmate/mailbox/{id}/reply` | 轻回信：建/复用 mailbox 会话，返回 session_id | 见 §5 |
| POST | `/v1/deskmate/mailbox/{id}/promote` | 进聊天：解除 mailbox_letter 标记 | `UPDATE sessions SET mailbox_letter=NULL` |

### 4.1 `/mailbox` 返回结构

```json
      "status": "pending", "read_at": null, "created_at": "…",
      "mailbox_session_id": null
    }
  ]
}
```

## 5. 轻回信（信件往来）实现

**不新造引擎/通道**：复用现有 WS 聊天路径（`/ws/session/{id}` + `engine.run`）。

1. 前端点「回信」→ `POST /mailbox/{id}/reply`（无 session 时后端建一个 deskmate 会话，`mailbox_letter=id`，返回 `session_id`）。
2. 前端用该 `session_id` 连 `/ws/session/{id}`（与正常聊天**同一套 WS**），把用户回信作为 user 消息发过去。
3. `engine.run` 产出她的回复，经 WS 广播 —— 前端在**信箱该信下**以**信件样式**渲染（抬头「小桔：」+ 日期），不弹气泡框。
4. 往来全部存 `sessions.messages`（同一消息库），侧栏看不见（被 `mailbox_letter` 过滤）。
5. 「进聊天」→ `promote` 解除标记 → 该会话进侧栏、信箱留引用，气泡样式续聊。

> 风险隔离：mailbox 会话只在 `/mailbox/{id}/reply` 路径产生，`list_sessions` 一行 `WHERE mailbox_letter IS NULL` 即可隔离，不影响任何现有会话逻辑。

## 7. 已读回流 + TTL 衰减（要害）

- **已读≠拒绝**：`/read` 必须回流情感层「用户看见了这条」（喂 `emotion_sense` 轻量信号），否则信箱变她的「表白墙+坟场」——她学到「主动没用」，与养孩子初衷相反。
- **稍后≠静默消失**：`/snooze` 走现有 3 天退避复活；前端「稍后」一键完成即回流「已读/稍后」语义。
- **TTL 衰减**：`read_at` 超过 7 天且无回复/处理的信，前端标「已搁置」灰度归档（不删，可展开）；不永远挂红点。

- 信箱 **Mac-only，不同步**（2026-10-08 决策5：Mac 常驻、两端记忆无需收敛）。

## 12. 与江河设计（§九 元认知）的关系

- 信箱是**送达层**，江河 §九 是**反思/元认知层**，两者正交。
- 元认知的 `meta_stances` 当前不同步（决策5）；信箱呈现层也不同步——口径一致。
- 信箱的「已读回流」可喂给情感层；未来元认知若要从「用户是否读信」学交互偏好，走同一回流钩子，不新造。

### 偏离设计单的两处（都是有意的）

1. **§3.2 不给 `sessions` 加列**：改用现成的 `origin`/`origin_label`。加列要动 `ConversationStore` 的 SQLite 索引 + `SessionRecord`，而冒号 id 已被证伪；`origin` 本来就是「这个会话从哪来」的既有语义，promote 也只是换标记。
2. **§9 的「日上限」不搬到信箱**：`DAILY_DELIVERY_CAP=3` 管的是「她主动开口」的**推送**预算，信箱是**拉**；照抄会变成藏信。节制改挂在红点口径上（只数准入过的信）。

- **送达回执（「已投递 · 她还没回」）**——萧哥 10-09 判：轻回信走的就是聊天通道，她本就该即时回，不该在信箱里再造一个「等回信」的中间态。稿子里案 B 那个回执条因此不实现。
