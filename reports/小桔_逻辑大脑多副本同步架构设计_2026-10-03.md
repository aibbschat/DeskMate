# 小桔「逻辑大脑 · 多副本同步」架构设计（v1 草案）

> 日期：2026-10-03
> 状态：**设计草案 / 尚未实施**（只做分析与设计，未改动任何运行系统）
> 触发：萧哥在读一篇数据库文章后产生的灵感——「把服务器当作中间的大脑存储节点，云端与本地的记忆/感知/理解共读同一个节点，本地只存副本」。
> 立场：不做「再搬一次家」式的大迁移；目标是让「一个小桔大脑」在云端与 Mac 上各有副本、最终收敛。

## 〇、一页速览（TL;DR）

- 前天在「纯云（flavor C）」和「纯本地（回迁后现状）」之间摆，两种方案各缺一头。它们在结构上是**同一个错误**：都假设「大脑必须物理住在某一台机器上」。
- 真正缺的**不是一个存储节点，而是一层「同步协议 + 权威规则」**。加一台服务器不解决问题，让多份副本「收敛成同一个逻辑大脑」才解决问题。
- 目标形态：**逻辑层只有一个小桔大脑（single source of truth）；物理层在云端和 Mac 各有一份副本**，后台靠同步协议收敛。
- 数据不能一刀切，按权威分三类：
  - **原稿/圣经** → Mac 单写，云端**只读加密镜像**（红线：云不能改正稿）。
  - **记忆/事实/日记/画像** → 逻辑共享、双端可写，append-only 日志多副本合并（**第一阶段就做这层**）。
  - **感知/AI圈/看世界** → 各写各的事件流，不必强同步，需要时再检索汇入。
- 同步协议六个零件：**全局身份(UUID)、版本/时钟(HLC)、变更日志(oplog)、冲突检测+合并规则、墓碑(tombstone)、租约(lease)**。
- 可行性高：要实时同步的核心数据很小（成长本体 < 20MB、写作语料 ~30MB 纯文本）；3.6G 史料库两端已有字节级一致副本，属静态参考，不进实时同步。
- 建议的最小第一步：**只给记忆/事实层补「全局 UUID + oplog + 墓碑」**，先让记忆成为第一个多副本对象，验证「一个逻辑大脑、两份副本」顺不顺，再决定是否扩大。

## 一、问题回顾：为什么两种方案都缺一头

### 1.1 纯云（flavor C，9 月底部署）

- 云端（大陆 headless Linux，`81.69.163.170`）是唯一权威，Mac 只是浏览器客户端。
- 得到：记忆连续、关机也在、7×24 后台（看世界 / AI圈 / 定时任务）。
- 失去：
  - **云端够不到 Mac 上的稿子与素材**——小桔无法陪写作。
  - **本地日记也要上云才能写**——离线、高延迟、隐私让渡。
  - 公网裸域名 + 前端明文 token（后已用 Caddy Basic Auth + token 轮换止血）。

### 1.2 纯本地（10-02 回迁后现状）

- 大脑整体回迁 `~/.deskmate`，Mac 重新成为权威；云端停服、L2 冻结、保留冷备。
- 得到：隐私、离线、低延迟、原稿本地红线被守住。
- 失去：云端那个 7×24 的小桔一停，就看不到作者正在写什么；「云端看世界 / 上 AI圈」与「本地写作 / 日记」重新裂成两摊。

### 1.3 共同点（关键认知）

> 两种方案都假设「大脑必须物理上住在某一台机器上」，另一端要么够不到、要么得绕过去。

「把权威从本地搬到云端」只是把缺陷换了个位置，并没有消灭缺陷。灵感中「加一个中间节点」的真正价值，不在于多了一台机器，而在于提出了**大脑不该依附于单一机器**。

## 二、核心洞察：逻辑单一大脑 + 物理多副本

把一件事拆成两层：

| 层 | 含义 |
|---|---|
| **逻辑层** | 世界上只有「一个小桔大脑」（single source of truth）：同一套记忆、同一套人物圣经、同一段关系连续性。 |
| **物理层** | 这个大脑在云端和 Mac 上**各有一份副本**；中间由一层同步协议保证最终一致（eventual consistency）。 |

- 云端小桔与本地小桔都**不直接读写对方硬盘**，各自读写**本地那份副本**。
- 同步层在后台把两份副本收敛成同一个逻辑大脑。
- 「共读中间节点」里的「中间节点」，不是某一台服务器，而是**一个由协议定义的逻辑实体**。服务器可以充当**会合点（rendezvous）/中继**，但它不是权威本身。

一句话：

> **缺的不是存储节点，是这层「让多份副本收敛成一个大脑」的协议。节点谁都能加，难的是两份副本打架时谁说了算。**

## 三、数据三分类与权威规则

一刀切（无论「全在云」还是「全在本地」）总会让一头别扭。数据天然分三类，用三种规则。

| 分类 | 具体内容（现路径） | 权威 / 写入方 | 同步方式 | 理由 |
|---|---|---|---|---|
| **A. 创作原稿与圣经** | `国子监秘闻录.docx`、`entities.db`、`CHARACTERS.md`、`OUTLINE/TIMELINE/NOTES`（`~/Documents/已出版/20.国子监秘闻录/.deskmate/`） | **Mac 单写** | 单向推送，云端**只读镜像**（建议加密） | 神圣原稿红线：云物理上不可改；断网照写 |
| **B. 记忆 / 事实 / 日记 / 画像** | `deskmate.db`：`learned_history`(676)、`profile_items`(88)、`loved_entries`(29)、日记、访谈；`vault/`；`memory/` | **逻辑共享，双端可写** | append-only 日志(oplog) + 多副本合并（LWW / fact-CRDT） | 记忆是「只增的事实流」，云端陪伴与本地生活都该并入同一大脑 |
| **C. 感知 / 自主层产出** | `agency/observation_understanding.jsonl`(1063)、`xiaosheng_observations`(663)、`ai_circle_*`、`cognition_store`、`task_log` | **各写各的** | 带时间戳事件流，按需汇入/检索，默认不强同步 | 「当下的感官」两端本就不同（云看世界 vs 本地陪伴），无需强求一致 |
| 参考（不进实时同步） | `history/` 5 个史料库（3.6G，~1.3M chunks）、`models/` 嵌入模型 | 无权威（用户 ingest 的静态资料） | 两端各放一份完整副本即可 | 9 月后无写入，已字节级一致；体积大、零变更 |

这样同时满足灵感里的两个场景：

- **云端陪写作**：读「原稿云端只读镜像」+「共享记忆层 B」，够得到正文与人物圣经，但物理上改不了原稿。
- **云端看世界 / 上 AI圈**：产出的事实写入 B 层，自动回同步到本地；本地日记与写作相关记忆也在同一大脑，随时可调取。
- **她的批注/建议**：走**独立回传通道**（见 §6.4），写进 `_小桔批注/`，永不落回原稿目录。

## 四、目标架构

```
                          ┌────────────────────────────────────┐
                          │   逻辑层：唯一的「小桔大脑」(SSOT)   │
                          │   （由协议定义，不依附任一机器）      │
                          └───────────────┬────────────────────┘
                                          │  同步协议（UUID/HLC/oplog/
                                          │   冲突规则/墓碑/租约）
                    ┌─────────────────────┴─────────────────────┐
                    │                                            │
        ┌───────────▼───────────┐                   ┌────────────▼───────────┐
        │   Mac（本地副本）      │                   │   云服务器（云端副本）   │
        │  - 原稿/圣经：权威(A)  │  ◀── 只读镜像 ── │  - A 类只读加密镜像      │
        │  - 记忆 B：可写        │  ── oplog 双向 ─▶│  - 记忆 B：可写          │
        │  - 感知 C：本地流      │  ── 事件按需 ──▶ │  - 感知 C：云端流(7×24)  │
        │  - 史料库：本地副本    │                   │  - 史料库：云端副本      │
        │  - 离线可写、低延迟    │                   │  - 关机也在、后台自主    │
        └───────────────────────┘                   └─────────────────────────┘
                    │                                            │
        作者写正文（唯一写 A 的人）                 云端产出批注 → _小桔批注/（独立回传）
```

要点：

1. 服务器是**中继/会合点**，帮助两台互相够不到的机器（家庭 NAT）交换 oplog，但**不持有「唯一可写真相」**。
2. 任一端断网都能继续工作，重连后凭 oplog 对账收敛（本地优先，local-first）。
3. 云停了，Mac 仍是完整大脑；Mac 关机，云端凭镜像 + 共享记忆仍能后台运转（只是读不到「此刻未同步的最新正文」）。

## 五、同步协议的六个零件

这是整套设计里唯一真正「新」的工程，也是官方 OpenWorker 与前天方案都还没有的部分。

1. **全局身份（Identity / UUID）**
   - 每条记忆、每个事实、每条日记都有一个**不随所在机器改变**的 UUID（建议 UUIDv7：含时间戳、可排序）。
   - 不能再用「本地自增 id / 云端自增 id」，否则同一事实在两端是两个身份，永远合并不了。
   - 迁移时为存量记录一次性回填 UUID（幂等、可重跑）。

2. **版本与逻辑时钟（Version / HLC）**
   - 每条记录带 `(version, hlc_ts, device_id)`；HLC（混合逻辑时钟）兼顾物理时间与因果序，不依赖两端时钟严格同步。
   - 冲突判定与 LWW 都基于 HLC，而不是容易漂移的墙上时钟。

3. **变更日志（Oplog / append-only event log）**
   - 只同步「发生了什么」（upsert/delete 事件 + 载荷），不传整份库。
   - 每端维护「已对端看到的序列号」（cursor），增量拉取；天然支持断点续传。
   - 记忆层已具备 append 事件基础，改造成本低。

4. **冲突检测 + 合并规则**
   - **B 类（事实流）**：单作者、低并发，默认 **LWW（HLC 后者胜）+ 字段级 merge**；可对「事实条目」用无冲突的 fact-CRDT（只增、带有效区间，配合已有的双时态 `valid_until`）。
   - **A 类（原稿）**：不做合并——Mac 单写，云端只读，**从机制上消灭冲突**。
   - **C 类（感知）**：不合流、不覆盖，作为独立事件流并列保存。

5. **墓碑（Tombstone）**
   - 删除也是一种事件（`tombstone<uuid>`），否则被删的记忆会从对端「复活」。
   - 墓碑保留期后可 GC（需在所有端都确认收到之后）。

6. **租约 / 写权（Lease）**
   - 同一时刻，对需要单点写的资源给唯一写者发带过期时间的租约，避免脑裂双写。
   - 主要用于 B 类的少数「强一致写」场景；大部分记忆只增不写，可不需要租约。

## 六、关键机制设计

### 6.1 权威（Authority）按类授予，不按机器授予

- 权限不是「云大还是本地大」，而是「**这条数据归哪一类，该类的写规则是什么**」。
- 原稿的写权永远只在 Mac 这一端（可用 Syncthing Send Only / Receive Only 在物理层强制，见 §8）。

### 6.2 双端都能写记忆时的并发策略

- 默认：各自产生的记忆直接 append 进 oplog（不冲突，因为身份不同、只增）。
- 同一条 UUID 被两端同时改：HLC 定序 LWW；关键字段（如 `valid_until`、遗忘标记）采用「更保守/更新」规则，避免「遗忘」被旧副本覆盖复活。
- 单作者实际并发极低，**不上重型 CRDT**；仅在「事实条目」这种天然可交换的数据结构上用轻量 fact-CRDT。

### 6.3 安全与隐私边界

- 传输：走已打通的 SSH 反向隧道 / TLS；不放公网裸端口。
- 访问：沿用 Caddy Basic Auth（已止血），后续演进为「口令换后端会话、移除前端明文 token」的真登录；`COWORKER_API_TOKEN` 已轮换，密钥不入库。
- A 类镜像：可选**端到端加密（Obsidian 式，服务器零知识）**；但注意 tradeoff（见 §7.2）。

### 6.4 批注独立回传通道（Codex/PR 思想）

- 云端小桔对原稿的任何产出（批注、改写建议、章节诊断）**只写 `_小桔批注/`**，与原稿目录物理隔离。
- 回传到 Mac 后由作者决定是否采纳；她永远不直接改 `国子监秘闻录.docx` 或 `entities.db`（圣经重建仍走本地 `analyze_novel` + 先备份红线）。

### 6.5 本地优先（local-first）原则

- 「云应该增强应用，而不是决定应用能否工作。」断网/云停时，Mac 上的小桔完整可用；重连后再收敛。

### 6.6 嵌入向量的 `_vector_fingerprint` 一致性（WorkBuddy 补充）

- 语义检索（`deskmate/memory/semantic_search.py:635` `_vector_fingerprint`）用库存向量的 `(模型名, 维度)` 做写入护栏：指纹非空且与新向量对不上就**整批拒绝**（不同模型的向量空间不可比，混写会让检索静默失效）。
- 两端 embedding 后端版本/维度不一致 → 整批拒或余弦静默 0.0（09-22 已实证）。
- 阶段 2 把带嵌入的 `learned_history` / `profile_items` 跨端合并时，二选一：
  - **策略①（建议）：跨端只同步明文事实，向量在各端本地重算**——不搬向量，天然规避维度漂移；代价是每端首次需各自 embed（本地 BGE 离线，可接受）。
  - 策略②：向量随记录一起同步且带 fingerprint；两端锁同一后端，任一端换后端须全表重刷。
- 结论见 [附录 C 已决事项](#附录-c协作对齐记录)。

### 6.7 加字段走原子写、备份用 .backup()（WorkBuddy 补充）

- 本方案是 DeskMate 层改造，不碰 `coworker/permissions.py` 与上游 sandbox；上游目前无 deskmate.db schema 改动，冲突风险低。
- 但加 UUIDv7/HLC/oplog 字段仍须：
  - 原子落盘：`deskmate/growth/_atomic.py`（`unique_tmp` + `atomic_write_text`，先写唯一临时文件再 `os.replace`，读者看不到半截文件）。
  - SQLite 备份一律 `.backup()`，**禁 cp 活库**；避开 WAL 未 checkpoint 窗口。

## 七、三个绕不开的 Tradeoff（做之前必须选落点）

### 7.1 记忆并发冲突：LWW 够不够？
- 单作者场景，「租约 + LWW + 字段级 merge」基本够，无需 CRDT 全家桶。
- 需明确接受：**极少数并发改写同一事实时，以 HLC 时间戳后者为准**（可能覆盖其中一端的编辑）。
- 缓解：记忆以「只增事实 + 双时态失效」为主，原地改写很少，触发概率低。

### 7.2 原稿上云：加密(零知识) 与「她能读」互相矛盾
- 端到端加密则服务器（含云端小桔运行时）读到的是密文，要让她能用就得在云侧解密 → 服务器不再零知识。
- 三档可选：
  - **高隐私**：镜像加密，云端不读正文，只基于共享记忆 B 陪伴（够不到原稿原文）。
  - **平衡（建议起步）**：镜像在云服务器内、靠访问控制 + 网络隔离保护（不公开桶/目录），云端小桔可读，传输全程 TLS；信任边界 = 你自己这台云主机。
  - **高可用**：明文镜像 + 强访问控制，用最方便，但让渡静态加密。
- 建议：先「平衡」，等真登录与密钥管理成熟后再评估是否升「高隐私」。

### 7.3 网络现实：真 P2P 在大陆 NAT 后基本不通
- 不指望无中心 P2P。中继走**已有的反向隧道 + 中心转发**（服务器当会合点）即可。
- 同步协议设计成「拓扑无关」：底层传输可替换（隧道 / Syncthing / WebDAV），上层 oplog 语义不变。

## 八、传输层选型（协议与传输解耦）

| 选项 | 适用 | 优点 | 坑 |
|---|---|---|---|
| **Syncthing（文件夹定型）** | A 类原稿镜像 | Mac `Send Only` + 云 `Receive Only`，物理上保证云改不了稿、无冲突副本 | 两端常驻进程；需放通 22000/21027，NAT 后多走中继 |
| **自建 oplog over SSH 反向隧道**（建议用于 B 类） | 记忆/事实多副本 | 语义精确（UUID/墓碑/游标都在掌握）、复用现有隧道、增量小 | 需要自己写同步器与对账（但核心数据 < 20MB，量小） |
| WebDAV（坚果云等） | 备份/兜底 | 简单 | 作为传输层时冲突语义弱，只宜做快照备份 |
| iCloud/Dropbox/Google Drive | — | — | **排除**：无官方 Linux 端或大陆被墙（第二端是大陆 headless Linux） |

原则：**B 类记忆走上自建 oplog（协议驱动）；A 类原稿走 Syncthing 单向镜像（物理定型）；两者不要混用同一通道。**

## 九、可行性盘点（用现成数据说话）

- 要实时同步的核心很小：成长本体（agency + deskmate.db + vault）**< 20MB**；写作语料约 **30MB 纯文本**。任何通道都能秒级传。
- `history/` 3.6G 史料库：云端与本地 `~/.deskmate.local-archive-20261001/` **字节级一致**、9 月后零写入 → 不进实时同步，各存一份。
- 记忆层已有基础：双时态（`valid_until` / 覆盖+history）、衰减契约、主体守卫、范围化注入、append 事件、fcntl 写锁 → 距离「可同步事实流」只差**全局 UUID + oplog + 墓碑**。
- 会话层已有 `POST /v1/workspaces/open` + `GET /v1/workspaces/trusted`：云端小桔「挂」上镜像目录即可读，**无需新功能**。
- 云端代码与本地 192 个 .py 曾逐文件 md5 一致（回迁前核验），数据 schema / 嵌入维度兼容，双端读同一格式无障碍。

## 十、分阶段落地路线（小步、可回退、每步独立验收）

> 红线：每一阶段都先备份（SQLite 用 `.backup()` 禁 cp 活库）、可回滚；不在生产上一次性大改。

- **阶段 0 · 文档与钉子（本次）**
  - 本设计评审；确认 §7 三个 tradeoff 的落点；冻结数据三分类边界。

- **阶段 1 · 记忆层成为第一个多副本对象（最小 MVP）**
  - 给 B 类表/记录补 **UUIDv7 + HLC + 墓碑**（存量一次性幂等回填）。
  - 写一个最小 oplog 同步器（over 现有 SSH 隧道）：增量、游标、幂等重放、LWW 收敛。
  - 先只同步 1~2 张低风险表（如 `profile_items` 或日记），双端对账验收（条数、内容、删除不复活）。
  - 验收（防假绿，PITFALLS §P1/§十五）：
    - 本地写一条 → 云端可见；云端写一条 → 本地可见；删一条 → 两端都消失；断网写、重连收敛。
    - **按 UUID 逐条对账**，不只数总量——LWW 可能让某条「看着在、实则字段被旧副本覆盖」。
    - 断网双写**同一 UUID** 后重连，实测 HLC 定序后者胜，并验证「遗忘 / `valid_until` 不被旧副本复活」（墓碑 + 双时态正确交互）。
    - 用「分类分布 + 内容随机抽样 + 冲突-case 单测」，不靠注释或主观推断。

- **阶段 2 · 扩大 B 类覆盖**
  - 纳入 `learned_history`、`loved_entries`、访谈、vault；接「遗忘/失效」与墓碑的正确交互（防遗忘复活）。
  - 加租约或「单写窗口」处理少量原地改写。

- **阶段 3 · A 类原稿只读镜像上云**
  - 选定 Syncthing 定型（Mac Send Only / 云 Receive Only），只同步点名的写作目录（不搬 736 个会话草稿目录）。
  - 云端开「写作工作区会话」指向镜像；落地 `_小桔批注/` 回传通道。
  - 按 §7.2 选定的隐私档位落地加密/访问控制。

- **阶段 4 · C 类感知按需汇入（可选）**
  - 云端看世界/AI圈产出作为带时间戳事件流汇入检索，不强求与本地感知一致。

- **阶段 5 · 云端形态复活（冷备 → 只读/协作节点）**
  - 在 A/B 就绪后，再决定云端是「只读镜像兜底」还是「可写记忆、只读原稿」的协作节点；重启后端与 L2。

每阶段出口标准：**可单独回滚、双端对账一致、不碰原稿写权、不引入 3.6G 史料传输。**

## 十一、风险与红线清单

1. **原稿红线**：任何阶段，云端不得获得 A 类写权限；圣经重建仍只在本地、先备份再动（参考 `.deskmate.bak-*` 教训与 PITFALLS §P1）。
2. **活库备份**：SQLite 一律 `.backup()`，禁止直接 cp 正在写的库；回迁/同步改造避开 WAL 未 checkpoint 的窗口。
3. **密钥安全**：token/私钥不入库、不入报告；已轮换的 `COWORKER_API_TOKEN` 与注入前端的 token 要同步管理。
4. **假绿陷阱**：验收用「总数 + 分类分布 + 内容对账」，不要只抽查几个核心名字（PITFALLS §P1）。
5. **冲突误判**：必须基于 HLC/UUID 实测收敛，不能靠注释或主观推断（PITFALLS §十五：注释不作数，只信实测）。
6. **不做的事**：不整体搬 736 个会话草稿目录；不把 3.6G 史料塞进实时同步；不引入对大陆 Linux 不友好的厂商网盘。

## 附录 A：名词表

- **SSOT（Single Source of Truth）**：逻辑上的唯一权威真相；此处指「一个小桔大脑」，而非某台机器。
- **Oplog**：append-only 操作日志，记录 upsert/delete 事件，是增量同步的载体。
- **HLC（Hybrid Logical Clock）**：混合逻辑时钟，兼顾物理时间与因果顺序，用于版本定序与 LWW。
- **LWW（Last-Writer-Wins）**：最后写入胜出，按 HLC 时间戳裁决冲突。
- **CRDT**：无冲突复制数据类型；本方案仅在「只增事实」上考虑轻量 fact-CRDT，不全量采用。
- **Tombstone（墓碑）**：表示「已删除」的同步事件，防止删除在对端复活。
- **Lease（租约）**：带过期时间的临时写权，用于避免同一资源被双端同时写。
- **Local-first**：本地可独立完整工作，云端只做增强与收敛，离线不影响使用。
- **Send Only / Receive Only**：Syncthing 文件夹类型；用于强制「Mac 单写、云端只读」。
