# 前端上游体验度对齐分析（2026-10-28）

> 背景：我们对官方上游 `andrewyng/openworker` 的跟踪长期只在后端，前端从上游带过一批老模块后基本没再跟进。本次把上游 `surfaces/gui` 稀疏克隆到本地（`/tmp/upstream_ow`）与我们的 `surfaces/gui/src` 逐文件比对 + 重点精读，针对"现状能提升体验"的维度给出可跟进清单。
> 上游近期（2026-07～10）在前端砸了大量 UX 投入；我们本地 377 个前端 commit 几乎全是**自研**（小桔/信箱/花园/皮肤/情绪…），所以"跟上游"应是 **cherry-pick 体验件**，绝不能整包同步（会冲掉小桔体系）。

## 0. 结论速览

- 我们**已与上游对齐**（早期带过）：主题（深/浅/自动）、工具调用人话化、流式显示收敛、token 用量累计。
- 真正上游有、我们缺、且能提升体验的，按优先级：
  - **P0**：①全局字号档位　②审批门对账与升级（消除僵尸卡）
  - **P1**：③本地模型引导安装/模型页 refinement　④团队·多智能体面板　⑤卡片画廊+场景回放 QA 工具
  - **P2**：⑥沙箱作用域可视化　⑦输入框草稿持久化　⑧可拖动面板
- 我们**领先/差异化上游**（护城河，别盲目跟）：小桔人格全系、信箱、花园、皮肤、桌宠、记忆图谱、创作流水线、手机 PWA、中文深度本地化、本地连接器。

## 2. 上游有、我们缺、可跟进（按优先级）

### P0 — 小改动、高回报、低风险

**(1) 全局字号档位 `textSize.ts`**
- 上游做了什么：`src/textSize.ts`，三档 `small(13px)/default(14px)/large(15px)`，`data-text-size` 挂 `<html>`，`index.html` 预渲染防闪，`styles.css` 用 token 块切换整套装字号。
- 我们现状：`SettingsView` 外观页**只有主题切换，无任何字号控制**；`styles.css` 经 grep **无任何 text-size token**（确认空白）。
- 价值：对长期读长对话/日记/文稿的写作者很实用，尤其大字号护眼。
- 落地要点：①拷 `textSize.ts`；②`index.html` 加预渲染块（仿主题那段）；③`styles.css` 增加 `[data-text-size="large"]` 等缩放（统一用相对字号，别硬编码 px）；④外观页加一排字号按钮，紧挨主题。
- 风险：低。需回归确认各面板用相对字号而非绝对 px。

**(2) 审批门对账与升级 `gateReconciliation.ts` + `ApprovalEscalation.tsx`**
- 上游做了什么：`retireFinishedGate` / `reconcileResolvedGates`（审批/提案卡解析后**可靠消失**，防漏 socket 事件导致"点头了却不消失/重复"）；`ApprovalEscalation` 在审批卡显示"reviewer 不确定 / 需人工 / reviewer 不可用"原因。
- 我们现状：有 `deskmate/MailboxPage` + 审批卡，但缺"解析后强制回收"的纯函数对账，存在僵尸卡/幽灵卡隐患（正是我们这类长尾 bug 的高发区）。
- 价值：消除审批·信箱卡的"卡死不消失"类问题，提升信任感。
- 落地要点：把两个纯函数搬进我们的 types/信箱逻辑；审批卡组件接 `ApprovalEscalation` 展示升级原因。
- 风险：低（纯函数 + 纯展示）。

### P1 — 中改动、显著体验提升

**(3) 本地模型引导安装 + 模型页 refinement（`models/ProviderGroups` / `LlamaCppSetup` / `LocalModels` / `PickModelDialog`）**
- 上游做了什么：模型按 **本地 / 订阅 / API key** 三组排列，connected 在前、搜索框、`Show N more` 折叠、每卡显示模型数；`llama.cpp` 引导：按 Mac 选尺寸、显示 licence、下载完 sha256 校验、429 倒计时等待。
- 我们现状：`ManageTabs` 有自研选择器（厂商×档位分组折叠、kilo/opencode 车道），但**无搜索/折叠/connected-first/每卡模型数**；也没有本地模型"引导下载+校验"流程。萧哥会跑本地模型（MiMo / llama-server）。
- 价值：大幅降低"加一个本地模型"的门槛；模型页更清爽。
- 落地要点：先抄 `ProviderGroups` 的搜索+折叠+connected-first+模型数（纯前端）；本地模型引导需后端支持下载/校验，分步评估。
- 风险：中（引导安装涉及后端本地模型管理能力）。

**(4) 团队·多智能体面板（`TeamView` / `TeamRail` / `TeamUpdateLine` / `teamRoster` / `teamView`）**
- 上游做了什么：worker 会话 rail、搜索、每个 worker 的 token 用量、更新行、团队聊天。
- 我们现状：仅有 `TeamChatView.tsx` 草稿 + `RoundtableContacts`（圆桌联系人），是 mock。
- 价值：若小桔要调度子智能体/圆桌（我们已有 `agent-group-chat-mock.html`），上游这套是现成、打磨过的多智能体 UI 骨架。
- 落地要点：参考 `TeamRail`/`TeamView` 把 `TeamChatView` 从 mock 升级为真实面板；接 `teamRoster`/`teamView` 的数据结构。
- 风险：中（取决于是否真要推进多智能体协作）。

**(5) 卡片画廊 + 场景回放（`gallery/`，dev-only）**
- 上游做了什么：dev-only 页（`/#/gallery`），把每个工具卡/审批卡在每种命名状态下渲染出来；外加可回放"场景"（保存的会话瞬间，无需服务器/模型）。
- 我们现状：前端有 **100+ 自定义组件**（小桔/信箱/花园/皮肤/情绪…），但**没有任何可视化 QA / 回归 harness**。
- 价值：对我们这种大量定制前端，是**最高杠杆的体验保障**——任何卡片改坏一眼可见，还能当组件活文档。dev-only，不上生产包。
- 落地要点：抄 gallery 模式（`states/*.ts` 状态快照 + `cards.tsx` 注册表 + `Gallery.tsx` 浏览器），先覆盖我们自己的高频卡片；场景回放可后做。
- 风险：低（dev-only）。

### P2 — 锦上添花

**(6) 沙箱作用域可视化（`SandboxChip` / `SandboxSection` / `ScopedStatus`）**：每会话显示"能做什么/受限什么"的 chip，配合我们权限体系，让用户看懂边界。
**(7) 输入框草稿持久化（`composerDraft.ts`）**：刷新/重开不丢正在输入的内容。小但贴心。
**(8) 可拖动面板（`windowDrag.ts`）**：DeskHome 多面板可拖动调整；低优先。
**(9) 其它上游通用件**（`CustomizationTab` 网络搜索供应商 / `WalletChips` 计费 / `SessionSites` 可达站点 / `ConnectorRequestCard`）：与我们的"本地优先 + 自带 key"模型契合度低，按需择取。

## 3. 我们领先上游、不要盲目跟的部分（护城河）

| 维度 | 我们 | 上游 |
|---|---|---|
| 人格/情感 | 小桔全系：情绪引擎、日记、信箱、花园、皮肤、桌宠、记忆图谱、创作流水线、AlterEgo、专家中心 | 通用 persona，无深度情感/陪伴 |
| 移动端 | 完整 `mobile/` PWA（WebAPK 安装、Dock、分屏） | 无独立手机端 |
| 本地化 | 中文深度本地化、本地连接器（QQ/微信等） | 英文为主、通用连接器 |
| 创作 | 改编→编剧→审稿→主编统筹流水线 | 无 |

> 跟进上游前端时务必保护这些不被上游通用结构覆盖——尤其"**小桔形象永不被皮肤替换**"这条红线（`PITFALLS.md` 明记）。

## 4. 跟进节奏建议

- **立即（半天级）**：P0-1 字号、P0-2 审批对账/升级。两个都是小纯函数/小控件，直接提升日常体验。
- **本迭代**：P1-5 卡片画廊 QA（先搭骨架，覆盖高频卡片）、P1-3 模型页搜索/折叠。
- **视规划**：P1-4 团队面板（取决于多智能体路线）、P1-3 本地模型引导（取决于后端能力）。
- **不建议**：整包同步上游前端（会冲掉小桔体系），采用"cherry-pick 体验件"策略，且每个件落地后跑前端单测 + 真机目测。
