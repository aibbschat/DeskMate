## 二、我核实为"对的"部分（文档可信度不低）

1. `~/Documents/已出版/` **确实存在**（24 个子项：大秦宣太后、大明水师、明朝烟火味儿…）。
2. `l2_settings.json` 落点**正确**：`deskmate/agency/settings.py` 的 `_default_path()` 返回 `$DESKMATE_DIR/l2_settings.json`，`_kill_switch_off()` 读 env `DESKMATE_L2_ENABLED` —— 文档写的开关位置准确。
3. `basicauth` 语法在服务器 Caddy **2.11.4 上实测 `Valid configuration`**（我拿临时 Caddyfile 验过），不会因版本弃用而启动失败。
4. "两端 L2 绝不同开"、"运行库禁 cp 要 sqlite3 .backup"、回滚预案、"paths.py 无写死云端路径" 这几条红线都对。

## 三、它标为"最紧迫"的那条，实测确实成立（而且我就利用了它）

我用**零凭据**从公网访问，实测：

```
https://xj.aibbs.chat/            → HTTP 200，无需任何鉴权
首页 HTML 中 64 位 token 明文      → 1 处（window.__COWORKER_API_TOKEN__）
拿该 token 调受保护 API             → HTTP 200，真的返回了 {"total":308, ...}
```

也就是说：**任何知道这个域名的人，都能拿到 token 并读写小桔的全部 API**（308 条记忆源、对话、日记…）。而域名是 Let's Encrypt 证书，**必进 CT 日志**，等于可被检索到。这个暴露从约 19:00 上线持续到现在。

所以步骤 0 我完全同意，但要补两点文档没写的：
- ⚠️ **8080 那块（腾讯隧道）是另一个 site 块**，`basicauth` 只加在 `xj.aibbs.chat:443` 上 → 若隧道仍启用，就是一条**旁路**。要么两块都加，要么确认隧道已关。
- ⚠️ **token 必须轮换**：它已经公开暴露数小时（连我都取到过）。只加密码不换 token，等于把钥匙留在门上。轮换后记得同步更新注入的 index.html（两处必须一致）。

## 四、结构性反对意见（这是我不建议按原样执行的核心原因）

文档的目标是同时要两件事：**大脑在 Mac（canonical 满真身）** 且 **云端 7×24 跑 L2（看世界/AI圈）**。但 L2 是**要写大脑的**（观察日记、世界观、认知沉淀、AI圈记录都落库）。于是：

**大脑在 Mac + 云端 L2 写大脑 = 两个写者 = 多主复制**。文档把它叫"镜像"，但它不是镜像，是双写。

而双写就必须解决合并。这里有个价值判断必须摆上桌：

| 资产 | 体量 | 可替代性 |
|---|---|---|
| 大脑（.deskmate：记忆/认知/世界观/日记） | 3.7G / 1445 文件 | **不可替代**——这是小桔的"她自己" |
| 写作语料 | 约 30MB 纯文本 | **可重建**——你脑子里和本地都还有 |

⇒ **风险应该压在文件上，不该压在脑子上。** 文档的方案恰好相反：它为了"稿子方便"去动大脑的复制拓扑。

## 五、步骤 5 的具体缺陷（都是可复现的工程问题，不是口味问题）

1. **rsync 覆盖"正在运行"的 SQLite**：脚本第 2 步把云端 `.deskmate/` rsync 覆盖到 Mac `~/.deskmate/`，但**Mac 端 app 是开着的**——在 SQLite 打开句柄之下替换数据库文件，轻则 app 读到旧 inode 继续写、双份数据分叉，重则 `database disk image is malformed`。反过来第 3 步把 Mac 的库推上云，而 Mac 此刻仍在写（WAL 未必 checkpoint）→ 云端拿到的可能是**半截事务**。要这么做，两端都必须先静止。
2. **每 30 分钟停一次云端服务**：L2 tick 会被打断（每轮"数分钟"），且脚本**没有 trap/finally**——中途失败（SSH 断、rsync 报错、sudo 超时）会把云端**留在 stop 状态**，小桔直接离线，直到有人发现。
3. **`merge_brain.py` 还不存在**，文档自己写"首版需先梳理表清单"。更麻烦的是它设想的 `INSERT ... ON CONFLICT DO UPDATE ... WHERE excluded.updated_at > 表.updated_at`：**LWW upsert 表达不了删除**（没有 tombstone）→ 你在 Mac 上"遗忘"掉的记忆，会被云端的旧行**复活**。对一个主打"记忆层可靠性"的产品，这是反效果。
4. **embedding 向量不能这样合**：`external_items` 的向量与"生成它的模型指纹"绑定，代码里有 `_vector_fingerprint()` 护栏——两端若跑了不同后端（比如一边本地 BGE、一边 API embedding），指纹对不上会**整批拒绝写入**。合并脚本若忽略这点，语义索引会卡死或混入不可比向量（余弦静默返回 0，表现为"检索永远空"）。
5. **顺序铁律仍不够**：文档写"先回灌再对齐"，但没有定义**同一行两端都改过**时谁赢、以及冲突如何回滚。`conflict_log.jsonl` 只留痕不解决。

## 六、步骤 6 的另一个问题：范围不对

文档同步的是 `~/Documents/已出版/`（已出版成书）。但你要她做的是**"查看进度、看人物有没有飘"**——那用的是**正在写的稿**，它们在 `~/Desktop/写作营素材库`、`~/Desktop/AI圈素材库`、`~/Desktop/国子监秘闻录_*.md`、以及 736 个 `~/OpenWorker/<会话id>/` 里的草稿。仅同步"已出版"，她依然答不了"进度到哪了"。

## 七、我的建议（两条安全版本，二选一）

### 版本 A（我推荐）：大脑留在云端（单写者），把**文件**送上去
- 大脑仍在云（唯一写者），L2 7×24 照跑；Mac 只是客户端。
- Mac 单向推 30MB 写作语料 → 云端 `/var/lib/openworker/写作/`，该目录对小桔**只读**；她直接读文件即可查进度/人物一致性。
- 批注走反向目录回 Mac。
- **零合并风险**；Mac 合盖后她照常能读、能自主干活。代价：稿子副本在服务器上。
- 传输层 rsync（今天可跑）/ Syncthing / 坚果云 WebDAV 三选一，详见 reports/小桔_写作工作区互通方案_2026-10-01.md。

### 版本 B（若你坚持"大脑和稿子都留在 Mac"）：那就必须放弃"云端 7×24 有脑 L2"
- 单一写者原则不许两头都写。要么：
  - **B1**：Mac 成为**常驻机**（不睡/迷你主机），大脑与 L2 都在 Mac，云端只做远程只读入口；或
  - **B2**：云端 L2 **关掉**，云端仅作只读镜像 + 远程浏览，不再产生新记忆（等于放弃"你睡了她还在成长"）。
- 若两条都不接受，那就只能回到版本 A —— **不是我在保守，是"单写者"这条物理约束决定的**。

### 如果最终仍要走 local-first，至少要这样改（把风险压到可接受）
1. 同步时**两端都静止**：先停 Mac app 与云端服务，用 `sqlite3 .backup` 产出一致性快照再传，传完再启；**绝不 rsync 覆盖运行中的库**。
2. 脚本加 `trap`，任何失败路径都要把云端服务**重新拉起来**。
3. 放弃"双向合并"，改为**单向 + 域划分**：云端 L2 只往"云端侧专有表/追加型 JSONL"写，Mac 单向导入；共享表**只允许一端写**。宁可少同步一点，也不要 LWW 猜。
4. 合并前做**全量备份 + 演练**，并在 staging 复制一份库先跑通，别直接上生产脑。
5. Basic Auth 覆盖 **443 与 8080 两块** + **轮换 token**。

## 八、我需要你拍板的一个问题（其余都由此决定）

**"Mac 合盖之后，云端还要不要继续自主成长（L2）？"**
- 要 → 大脑必须在云（版本 A）。文件和大脑分离，风险压在文件上。
- 不要 → 大脑回 Mac（版本 B），但要接受云端不再是"活的小桔"，或必须让 Mac 常驻。

这两个不能同时要——L2 必须有一个**常驻且唯一**的大脑来写。文档方案想两边都占，代价就是双写合并；我不建议把大脑押在那上面。
