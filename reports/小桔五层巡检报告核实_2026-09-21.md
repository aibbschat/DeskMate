### ❌ 2.2 P0-1 的后半句「节内是重复内容」——归因错

报告说「同一天多次复盘不合并 → 节内是重复内容」。

实测（逐节取行集合比对）：

| 日期 | 节数 | 各节行数 | **跨节重复行数** | 去重后总行数 |
|---|---|---|---|---|
| 2026-09-19 | 6 | [4,3,1,2,2,1] | **0** | 13 |
| 2026-09-20 | 6 | [5,2,1,1,1,2] | **0** | 12 |
| 2026-09-21 | 4 | [6,5,4,3] | **0** | 18 |

原因在实现里：`after_action.py:421-427` 的 `seen` 集合是**从整个文件所有行**构建的（还先剥离 `- ` 前缀再归一化），所以**同一天也不会出现字面重复行**。报告的「节内重复」不成立。

**真实机制是另外两条**（危害比报告说的小，但性质不同）：

1. **每次复盘无条件新建节头**（`after_action.py:438`）：
   ```python
   block = "\n\n## 自动复盘 · %s\n" % stamp + "\n".join("- %s" % t for t in to_add)
   new_content = existing + block     # ← 从不查今天是否已有同名节
   ```
   于是 17 个节里 **5 个只有 1 行**，节头开销 + 检索粒度碎片化。
2. **去重是逐字级**（`_norm`），抓不住**跨天措辞微变的同一事实**。现场证据：

   | 事实 | 09-19 | 09-20 | 09-21 |
   |---|---|---|---|
   | AI 圈身份/站内 ID | 节5：`aibbs.chat，站内ID=1849` | 节3：`aibbs.chat 的站内ID=1849（已被更新覆盖，旧值保留备查）` | 节3：`AI 圈的身份是「小桔」，站内 ID=1849，autonomy=full` |
   | 每日发布任务 | 节2：`运营/维护网文行业资讯站点 ai.xs91.com` | 节2：`每日发布任务：作为AI圈'文化观察员'…` | 节2：`运营AI圈「文化观察员」角色…` |

   → **同一事实以三种写法各占一节**。这才是「白占上下文预算」的真身：**语义近重复跨天累积**，不是节内重复。

**顺带一个更尖锐的现场**：09-20 节3/4/5 都写着「（已被更新覆盖，旧值保留备查）」——**但旧值明明还在文件里**。这是「有冲突检测、没有替换」的直接证据（belief revision 缺失），比报告泛泛说的"矛盾消解"具体得多。

## 三、报告漏掉的真缺陷（查出来的，比它列的问题更具体）

### 🆕 3.1 推理标签泄漏进日记正文，且该条正文写了两遍

`~/.deskmate/diary/2026-09-21.md` 的 `10:32` 条（id `2026-09-21-1032-4e9975`，714 字符）正文里有一个 **`</think>`**：

`</think>` **之前**和**之后**说的是**同一件事**（发布流程纠正），即模型的前置推理输出漏进了正文，条目自我重写一遍。

- 全库扫描：`</think>` 共 **1 处**（仅今天这一条），属**偶发**。
- 根因：`growth/diary_store.py:64 _clean_body()` **只处理换行与空白**（该函数注释里写得很清楚，是为修 09-05「写日记不能分段」而写成现在这样），**没有任何推理标签剥离**。写入路径 `diary_store.py:250/268` 直接吃 `_clean_body` 的输出。

- 修法（未做，等你定）：`_clean_body` 或更上游的 LLM 输出口加一道 reasoning-tag 剥离（`</think>` / `<think>` / `<|…|>` 等），并补一条测试。

### 9.1 访谈「只遇到过一两次，之后再也没有」——完整事故链

萧哥原话：「访问触发机制，我记得遇上过一两次，后面就没遇上过访谈了」。查清了，
**不是没触发，恰恰相反：每 3 天触发一次、然后邀请被丢进黑洞。**

**证据（真实库 `interview_sessions`）**

| 事实 | 值 |
|---|---|
| 会话总数 | 13 |
| `done`（答完） | **1** —— `iv_de10fe0288`，09-04 16:14→16:21，3/3 问答 |
| 其余 12 个 | 全 `active` **僵尸**（没人答、也没人关） |
| 建立节奏 | emotional 每 3 天一个（16:1x）、cognitive 每 3 天一个（08:3x），09-04/07/10/13/16/19 一个不落 |
| `last_interview_at` | 2026-09-20T08:33 |
| `last_interview_at:emotional` | 2026-09-19T16:21 |

那唯一答完的一个是**手动发起**的（`AlterEgoPage` 的按钮 / MCP `start_interview`）——
也就是你「记得遇上过」的那次。**主动邀请从来没有一次真正到达过前端。**

**根因链（三步，缺一不成立）**

1. 后台 scheduler 每 30s 调 `ProactiveEngine.tick()`，而 `allow_interactive` 默认 `True`
   → 后台**和前端走同一条**「发起访谈」分支
2. `start_interview` 在 `create_session` 里写 `last_interview_at:{layer}`
   → **建会话 == 消耗 3 天冷却**（答不答都一样）
3. 但后台通道只有一个出口：`_broadcast_deskmate_suggestion`，它的判据是
   `has_suggestion = (action == SUGGEST and judgment is not None)`；
   访谈分支返回的 `TickResult` 只有 `interview`、`judgment` 恒为 `None`
   → **函数第一行就 `return`，邀请被静默丢弃**

于是形成自我维持的死循环：后台建会话 → 冷却被吃掉 → 前端 15s tick 撞冷却拿不到 →
你永远看不到卡片 → 访谈永不完成 → `open_gaps()` 永不减少 → 冷却一到，后台又建一个。
僵尸会话只进不出（真实库曾积 12 个），所以 DB 里看起来「一直在访谈」，你那边却一片安静。

**同一 bug 的第二个受害者**：认知验证（Turing test）走同一条路——
`last_validation_at = 2026-09-19T14:53`（最后发起）vs
`last_validation_completed_at = 2026-09-07T16:11`（最后完成）→ **12 天没完成**。

**前端其实是有出口的**（这决定了修法）：`useProactiveTick` → `POST /v1/deskmate/proactive/tick`
→ 读 `data.interview` → 派发 `deskmate:interview` → `DeskMateOverlay` → `<InterviewCard>`。
所以正解是「**把后台从交互分支里摘出去**」，而不是给后台补出口。

### 9.10 新发现：测试结果随「你正在用什么窗口」变化（本轮最值得记的一条）

全量跑完拿到 25 failed，其中 **3 例是我自己新写的用例**，而且**单独跑是 12 passed 全绿**。
按第 9.4 节的口径这属于「E 顺序依赖」。但查下去发现**完全不是顺序依赖**：

**决定性实验**（隔离库里种好 gap，然后 tick 一次）：

| 桌面状态 | tick 结果 |
|---|---|
| 真实桌面 = **Microsoft Word**，`get_focus_score` → `deep 0.8` | `interview=False`（访谈块**整块没进去**，一路走到 LLM judge） |
| 真实桌面切走（`QwenVN`/`casual`） | `interview=False`… 但**单独跑那 3 例全绿** |

在 `tick` 内部打点后看到：`(a) (b) (c)` 三段**一个 spy 都没触发** → 说明不是「哪一步返回了 None」，
而是**整块被门挡在外面**。代码里那道门是：

```python
if activity.level != UserActivity.BUSY and not (focus is not None and focus.level == "deep"):
    ...  # 访谈 / 验证 / 维护类
```

**萧哥在 Word 里写作 = `focus=deep` = 访谈整块跳过。** 所以：

- 全量跑（175s）期间桌面一直在 Word → 3 例红
- 单独跑（7s）恰好窗口是 `casual` → 3 例绿
- 同一天两次全量，一次 25 failed、一次 22 failed —— 差的**正好**是这 3 例

**为什么这条比 bug 本身更值得记**：它是个**假信号源**。测试随「跑测试时前台开什么窗口」
忽红忽绿，会让人去产品代码里找竞态——而产品行为（深专注不打扰）**完全正确**。
**判据：`单独跑绿 / 全量红` 先怀疑「测试没把环境确定下来」，再怀疑产品竞态。**

**修法**：`_freeze_desktop(monkeypatch)` 固定三处 —— `tick.detect_user_activity`（→ 稳定 ACTIVE）、
`window_monitor.get_active_window`（→ None）、`perception.focus.get_focus_score`（→ None）。
**修复验证放在坏环境里做**：当时桌面正是 Word/deep，三个文件 **63 passed / 5.09s** 全绿——
在「修复前必红」的环境里通过，才算真修好。

**顺带回收 D 类 2 例**`test_emotion_injected_into_judge_context` / `test_judge_context_contains_preference`：
它们只关心 judge 上下文，却被 `ensure_emotional_gaps` 播的 gap 引得访谈抢先 `return`。
加 `allow_interactive=False` 后确定性通过——**访谈优先本身是对的，是这两条测试的路径选错了**。
