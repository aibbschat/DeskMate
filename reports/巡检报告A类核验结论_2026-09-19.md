## 二、逐条证据

### A1 ✅ novel_memory 重试逻辑与注释相反 — `deskmate/novel_memory/core.py:143-187`
- 143-145：`extra={"reasoning_effort":...}`
- 147-155：`_create()` 用闭包 `extra`，`**({"extra_body": extra} if extra else {})`
- 175-178：`except BadRequestError: if extra: resp = _create()` —— **`extra` 从未置空即重发**，provider 二次 `BadRequestError`
- 157-169：`_fallback_create()` 第 168 行 `**({"extra_body": extra} if extra else {})` 也带 `extra`，救不回
- 修复方向（报告给的）：重试分支先 `extra = None` 再 `_create()`。

### A2 ✅ 技能用量被注入/查看污染 — `deskmate/skills/manager.py` + `server.py`
- manager.py:223 `def format_skills_context`（docstring："匹配技能并格式化为上下文注入块"，返回 `<skills-context>`）—— **报告写成 `build_skills_context`，函数名错误**
- manager.py:254-258：注入循环内 `record_use(success=True)` + `increment_uses` + `_record_growth_skill_use`（熟练度+XP+亲密度）
- server.py:74-87 `skill_view`（查看详情）：第 75 行 `increment_uses` + 82-87 行 `GrowthEngine.record_skill_use(success=True, ...)`；注释明写"技能查看 = 使用事件"
- 结论：注入上下文 与 仅查看详情 都计一次成功使用，污染 success_rate / 成长 XP / curator"未用就清理" / badges"大师级 100 次"。报告定性正确，仅函数名需改。

### A3 ✅ 创作流水线同步 LLM 阻塞事件循环 — `deskmate/creation/chat_flow.py:363-385`
- 363：`def _progress_stream(self, label, fn, ...)` 是同步 `def`
- 371：`result = fn(*args, **kwargs)` 直接同步调用
- 385：`progress_msg, result = self._progress_stream("撰写大纲", self.pipeline.draft_outline)` 在 `async _do_draft_outline` 内无 `await`/`to_thread` 同步跑含 LLM 的 `draft_outline`
- 对照 service.py:471-520 `_stream_step`：495 行 `asyncio.create_task(asyncio.to_thread(run))` 正确桥接 —— chat_flow 未复用，SSE 期间事件循环被卡。

### A4 ✅ 测试未隔离 deskmate 真实数据目录 — `tests/conftest.py:17-27`
- 17-27 autouse fixture 只 `setenv COWORKER_STATE_DIR` / `COWORKER_SCRATCH_BASE`，**无 `DESKMATE_DIR`**
- 各模块硬编码兜底（如 agent.py:216 `or str(Path.home()/".deskmate")`、flowers.py:158、engine.py:1653）在测试环境仍指向真实库
- 佐证：`scripts/restore_cognitive_layer.py:2-6` 自述 2026-09-07 因全局 manager 指向真实库 + `persist` 全量覆盖，把 cognitive 层 37 条真实画像清成 5 条测试数据——**已实际发生**。

### A5 ✅ 个人隐私内容入库 — **且发现疑似神圣稿件入库（红线！）**
- `git ls-files '.novel_pipeline_fix/'` 返回 2 个被跟踪文件，其中一个文件名是 **`国子监秘闻录_找回.md`** —— 与项目红线"神圣稿件国子监秘闻录绝对禁止触碰"直接冲突，疑似神圣稿件被纳入版本库。
- 另一文件：`国子监第四章稻梁谋大纲_找回.md`（创作大纲副本，也属隐私草稿）。
- `restore_cognitive_layer.py:41-67` 内嵌萧哥真实创作观原文（`WAL_RECOVERED` 四条，如"写作的人是孤独的……"等），会被 git 跟踪。
- **处置建议**（红线级，需萧哥本人拍板）：① 先 `git rm --cached` 这两个文件 + 加入 `.gitignore`；② "国子监秘闻录_找回.md" 内容**由萧哥亲自确认**是否为神圣稿件全文，AI 不读不碰；③ 脚本内嵌的创作观原文改为从本地备份读取，不在仓库存明文。

### A6 ⚠️ config 示例与代码默认安全姿态相反 — `docs/config.example.toml` vs `coworker/config.py`
- 属实部分：`config.example.toml:12-16` `allowed_commands = [ls, cat, ... python3, pytest, node, npm, git status...]`，而 `config.py:27` `DEFAULT_ALLOWED_COMMANDS = []`。用户若复制示例即放开命令白名单，弱化防护——这条"安全姿态相反"成立。
- 不准确部分：`config.example.toml:7` `model="gpt-5.5"` / `:9` `max_iterations=12` vs `config.py:32` `gpt-5.6-sol` / `:34` `150` —— 只是默认值不一致，且示例 `max_iterations=12` 比代码 `150` **更保守**，不算"安全姿态相反"。
- 其他属实：`execution_level`(config.py:44) 等大量新字段（sandbox/auto_approve/web_search_provider）在示例文档完全未出现。
- 结论：报告方向对，但"model/max_iterations 相反"措辞过强；应按 Config dataclass 生成式同步文档。

### A7 ⚠️ 引擎反向依赖业务包 + 静默吞异常 — `coworker/engine.py`、`agent.py`、`catalog.py`
- 属实：`engine.py:1655-1695` `_xiaosheng_note` `try: from deskmate... except Exception: pass`；`agent.py:214-307` `_deskmate_context_provider`/`_deskmate_post_turn_hook`/`_deskmate_skill_index`/`_deskmate_mention_context` 全部 `try: from deskmate... except Exception: pass/return ""` —— 静默降级、不可观测。
- **不实（报告描述错误）**：`catalog.py:31` 报告称"内嵌 `try: from deskmate... except Exception: pass`"。实际读到的是**顶层硬 import**：
  ```python
  # catalog.py:30-31（模块顶层，无 try/except）
  from deskmate.tools.review import review_chapter, generate_report, load_manuscript_file
  ```
  deskmate 缺失时这里直接 `ImportError` 崩溃，而非静默降级。报告这条行号/描述与真实代码不符。
- 结论：反向依赖+静默吞异常在 engine/agent 成立；catalog.py 是硬依赖（缺包即崩），需单独修（改为可选导入或顶层依赖声明），不能套"静默降级"结论。

### A8 ✅ 前半 / ⚠️ 后半 — `coworker/emotes.py:41-52` + `engine.py:2257-2264`
- 前半属实：emotes.py:41-52 `_load_manifest()` 模块级调用，候选路径全不存在即 `raise FileNotFoundError`（第 52 行 `_MANIFEST = _load_manifest()` 在 import 期执行）；纯 CLI/无 GUI 目录部署 import 即崩。兜底路径仅 `Path(__file__).parent/"emotes.manifest.json"`，需同包带一份才不崩。
- 后半偏重：engine.py:2257-2264 `_assistant_message` 对每条助手消息调 `bake_assistant_emotes`；但 emotes.py 内 `bake_assistant_emotes` 自身有保护（非 emote 文本不动、`_ACTIVE_PACK` 未由前端上报时原样返回）。报告称"无 persona 守卫"依赖下游保护，措辞偏重，但 engine 层确实无显式守卫——属小瑕疵。

### A9 ✅ 出站护栏读-判-写竞态 — `deskmate/agency/outbound.py:41-110`
- 写端 `_append`(41-64)：第 49 行 `fcntl.flock(LOCK_EX)` + 56 行临时文件 `tmp.replace(p)` 原子替换 —— 有锁。
- 读端：`outbound_allowed`(71-87)、`dedupe_content`(90-98)、`peer_cooldown_ok`(101-110) 均直接 `_read(base_dir)`（无锁）。
- 竞态：引擎多入口（后台 tick / MCP tick / GUI POST）并发时，两条同秒出站各自无锁读旧状态 → 同时穿过频率/去重/冷却三道闸 → 同一内容可能发两次。代码层面属实（是否真触发取决于是否有并发测试，报告称无覆盖）。

### A10 ✅ 每 turn 无界 daemon 线程 + 每轮重建 Manager — `coworker/engine.py:583-601` + `agent.py:246-271`
- engine.py:583-601：每 turn `threading.Thread(target=self._post_turn_hook, ..., daemon=True).start()`（596-601），无并发闸/超时/失败可见性；注释 578-582 自承认"hook 含 2-5s 同步 LLM 调用"。
- agent.py:246-271 `_deskmate_post_turn_hook`：第 258 行每轮 `DeskMateMemoryManager(Path(base))` + 第 268 行每轮 `SkillManager(base_dir=Path(base))` 新建（含 DB/线程池初始化）；而**同文件** `agent.py:214-225` `_deskmate_context_provider` 已用模块级单例 `_deskmate_mgr_singleton` 避免重建——**两处不一致**，post_turn 未复用单例。
- 仅 `DESKMATE_AUTO_INJECT=="0"` 才跳过，非 deskmate 会话也照跑。报告成立。

### A11 ⚠️ garden 逐候选重建 EmotionTimeline 量级爆炸 — `deskmate/garden/flowers.py`
- `_mood_from_timeline`(278-297)：每次调用 `EmotionTimeline(base_dir=base_dir)._data.get(date)` —— **每候选新建 EmotionTimeline 实例**（重复读情感时间线）。
- `_candidate_flowers`(193-257)：222 行（recent_events 每事件）、253 行（每 badge）都调 `_mood_for_event` → `_mood_from_timeline`，N 候选即 N 次重建。
- `_material_events`(151-179)：读 `diary/materials/*.jsonl` 最近 120 文件、单文件上限 3000 行（`MATERIAL_LOOKBACK_FILES=120` / `MATERIAL_SCAN_CAP=3000`）。
- 结论：IO 浪费属实，但**是性能问题、非数据失真**，归 A 高危偏高估，建议下调至 B 性能类；花 id 幂等（注释 146）保证了不会重复开花，所以最坏是慢+耗 IO，不是出错。

## 三、建议处置优先级（供萧哥拍板）
