## 3. 分项设计

### 3.1 上下文组装：并行化 + 前置裁剪 + 副作用隔离（PR1）

**现状数据流**：`agent.py:923-1010 context_provider()` → `manager.py:667-1195` 串行执行约 20 个生产者 → 最后 `render_blocks()`（`context_budget.py:238-330`）按预算丢块 / 截断。

**核心问题**：预算判据在最后一步才生效，被丢弃的块已经付过完整 I/O / embedding / LLM 代价；`manager.py:958-960` 每轮 `EmotionEngine(...).describe_turn_context(record=True)` 即使整块被预算丢掉也照写库。

**设计**：把 `ContextBlock` 从"纯数据"升级为"带生产策略的延迟容器"：

```python
@dataclass
class ContextBlock:
    name: str
    text: str = ""
    priority: int = 50
    cap: int = 4000
    cap_light: int | None = None
    keep_light: bool = True
    # 新增（全部有默认值，向后兼容）
    group: str = "core"          # core | recall | profile | ambient | optional
    side_effect: bool = False    # True = 不可跳过（写库 / 记账）
    cost: str = "cheap"          # cheap | medium | expensive（expensive = embedding/LLM）
```

分两阶段：

1. **阶段 A（必做）**：`clock / manuscript / user_profile / emotion_state / weather / delivered / mailbox` 等轻量块照旧顺序产出；此时已经能算出 `light` 和已用 token。
2. **阶段 B（按预算决定）**：昂贵块（`file_recall` 的 embedding、`world_context` 的向量召回、`cognitive`、`prefetch`、`feeling`、`intent/reflection/lessons`）先查 `should_produce(name, light, remaining_budget)`，命中跳过条件的直接不产出。
3. **并行组**：阶段 B 内互不依赖的块用有界线程池（`ThreadPoolExecutor(max_workers=4)`，模块级单例）并发产出，结果按 `blocks` 声明顺序收集，**保证注入文本顺序不变**（prompt cache 的字节稳定性依赖这一点）。

**副作用隔离**：`record=True` 的情绪写入从"组装时"移到 turn 结束 hook（`manager.py:3467` 已有 `EmotionEngine(...).update_after_turn` 路径），组装阶段只读。

**失败可见**：每个生产者把异常写进 `ctx_stats[name] = {"ok": False, "error": ...}`，不再裸 `except: pass`（§3.9）。

**兼容与回滚**：
- 保留 `DESKMATE_CONTEXT_BUDGET=0`（旧行为）、新增 `DESKMATE_CONTEXT_PARALLEL=0` 一键退回串行。
- 文本顺序、块名、`cap` 全部不变 → 旧测试 `test_context_budget` 等不受影响。
- 风险：并发下的 SQLite / env 读取。每个生产者沿用现有"调用时解析路径"约定；共享可变状态（如 `EmotionEngine` 单例）需加锁或保持只读。

### 3.2 首字看门狗与超时分层（PR2）

**现状**：`httpx.Timeout(connect=15, read=600, write=60, pool=30)` + SDK `max_retries=2` + 应用层 `_CONNECTION_RETRIES=3`；`paid_fallback` 只在抛异常时切通道。

**设计**：

- 在 `OpenAIProvider._stream_impl` 外包一层**首字看门狗**：从调用起到第一个 chunk 超过 `COWORKER_FIRST_TOKEN_TIMEOUT`（默认 75s）→ 抛 `FirstTokenTimeout`（归入可重试/可降级异常）。
- 流开始后新增**idle 看门狗**：两次 chunk 间隔超过 `COWORKER_STREAM_IDLE_TIMEOUT`（默认 120s）→ 同样抛出。长文本慢速输出不会被误杀（阈值远大于正常 token 间隔）。
- 把新异常接入 `_is_retryable_connection_error` 与 `paid_fallback` 的降级链；**只在尚未发出第一个 chunk 前允许换通道**，已吐字则上抛（现有契约，`paid_fallback.py:272-274`）。
- `max_retries` 与 `_CONNECTION_RETRIES` 不再叠乘：看门狗触发后直接跳过 SDK 层重试。
- Anthropic / Gemini / Vertex / Bedrock 出口补显式 timeout（connect 15s / read 300s 起步）。

**验收**：用 stub provider 注入"永不返回首字"，断言 75s 内触发降级且只换一次通道；`tests/test_model_errors.py` 增例。

**设计**：

   - id 存在且内容 hash 相同 → 跳过（零写入）
   - id 存在且不同 → `UPDATE`（保留 sync 身份列）

4. `item_sources` / `item_history` / `cognitive_gaps` 同样按变更 id 处理，不再做全层孤儿扫描。
5. **保留**所有护栏：`layer='feeling'` 拒绝、空 incoming 拒绝、墓碑过滤、`_LAST_PERSIST_SOURCE` 记录。

**验收**：同内容 persist 两次 → oplog 增量 = 0；删 1 条 → 只 1 条 DELETE op；`test_memory_canon_*` / `test_cognitive_store_sync_identity` 与 sync 系列全过。

### 9.2.1 PR11 · 读路径：元数据与正文解耦、密钥缓存、收件箱分层

**#18 会话元数据解耦（先做，收益最直接）**

- 现状：`ConversationStore.load()`（`conversations.py:400-430`）无条件 `_read_jsonl()` 全量解析，再 `_repair_tool_pairing()` 全量重建；而 `app.py:844/878`、`manager.py:340` 只需要 `title / agent / workspace / n_msgs`。

**#19 SecretStore 缓存**

- 现状：`get()` → `_read()`（`secrets.py:206-212`）读文件 → `resolve()` 每次 `_load_dotenv()`（`:154`）。114 个调用点里，连接器工具、provider 路由、MCP 连接都在热路径。

**#17 收件箱分层**

- 现状：`InboxStore` 全内存 + 单个 2.4MB JSON；`_save()` 在 `add/resolve/promote` 三处全量重写（还带 `indent=2`）；历史 729 条 resolved 永不清理；`pending()` 每次 `list()` 全表扫描 + 排序，`list_sessions` 又按会话逐个调用。

### 9.2.2 PR12 · 回合前后固定开销

**#20 反思链改有界池 + 单飞**

- 回滚：`connect()` 是新增封装，逐 store 回退即恢复旧行为。
