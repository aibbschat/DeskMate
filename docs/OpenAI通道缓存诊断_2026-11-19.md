# OpenAI 通道 Prompt Cache 诊断（2026-11-19）

> 对应 token 审计 §4 第 2 步：验证「① 给 OpenAI 通道加 prompt caching」是否可做。
> 方法：只读真实账本 `~/.deskmate/deskmate.db` + 源码分析，未发任何请求、未改代码。
> 结论：**① 不需要做——通道原生支持自动前缀缓存，且已经在命中。** 真正该做的是提升命中率。

---

## 1. 诊断结论（纠正上一轮判断）

token 审计报告里写「OpenAI 通道没有 prompt caching、每轮 12900 token 全价重发」——**这是错的**，以本次数据为准：

| 证据 | 数值 |
|---|---|
| 近 30 天 `cache_read > 0` 的调用 | **662 / 1017 条** |
| 主力 mimo-v2.6-flash 命中率 | **577 / 801 = 72%** |
| 近 7 天主力通道缓存命中占总输入 | **44.2%**（cached 25.6M / 总 58M input） |
| 单条最大 `cache_read` | 113,920 token |

### 为什么客户端没注入缓存标记却有命中？

`coworker/providers/openai_provider.py:217 _usage_from()` 的注释给出了答案：

> `prompt_tokens` INCLUDES cached tokens, so the cached share is subtracted into `cache_read`; no write-side split exists on this API shape.

即：服务端（xiaomi mimo / opencode 网关）做**自动前缀缓存**——按请求前缀匹配，命中部分在返回的 `prompt_tokens_details.cached_tokens` 里报出来。客户端不需要、也没有能力显式开启。对照 Anthropic provider 的 `_add_cache_breakpoints()` 是另一套（需要显式断点）；两条通道机制不同，不能照搬。

**所以 §0 建议的「① 注入缓存标记」在 OpenAI 兼容通道上既无必要也无效——网关已经做了。**

---

## 2. 真正的问题：命中率两极分化

缓存命中率分布不是均匀的，而是**两头尖、中间空**：

```
命中率 ~0%    : 340 条
命中率 ~98%   : 56 条
命中率 ~99%   : 81 条
命中率 ~100%  : 20 条
（1%~95% 的每个桶都只有个位数~二十几条）
```

含义：**前缀要么整段命中（≈99%），要么整段不命中（≈0%）**——典型的「前缀被某个动态字段击穿，后续全部重算；直到下一次前缀重新稳定」。

进一步验证（近 2 天主力通道相邻调用）：

- 「高命中 → 掉到 0%」事件 50 次，相邻间隔中位数 **18s**
- 「0% → 重新高命中」事件 50 次，相邻间隔中位数 **11s**

也就是说缓存**平均每 10–20 秒就被击穿一次**。这正好对应「每轮对话/每次 tick 都变一次」的节奏。

---

## 3. 是什么击穿了前缀（源码定位）

服务端按请求 JSON 的**逐字节前缀**匹配。下面这些每轮变动的字段位于前缀或会推动前缀后移：

1. **`<system-context>` 附在最后一条 user 消息**（`engine.py:2709` 附近）
   - 里面有 `Now: YYYY-MM-DD HH:MM`（分钟级变动，`agent.py:929`）、`clock` 块（`manager.py` 的 `clock_context()`）。
   - 这块虽然被放在**消息尾部**，但尾部变动通常只击穿尾部；真正危险的是它把整段 `<system-context>`（13k token）作为**一个整体块**时，块内任一字符变动 → 整块缓存失效。

2. **13k 注入块里的动态内容**
   - `world` / `user_fact` / `feeling` / `emotion_state` / `delivered` / `mailbox` 等块，每轮重新查询，结果有微小差异（时间戳、计数、排序）→ 整块字节变 → 缓存失效。
   - 这些块在 `render_blocks` 输出里是**按名字顺序拼成一个大字符串**，任何一块变化都会让后续所有块的字节偏移。

3. **历史消息 append**：每轮 `self.messages.append(_assistant_message(turn))` + tool 结果，前缀本应稳定（append-only），但上面 1/2 的动态块是附在最新 user 消息上的，**不是 append 而是改写最后一条消息**——这正是 Anthropic provider 注释里强调的「最后一条消息会被改写，所以把 cache 断点放在它之前」的问题。

---

## 4. 可行且安全的优化方向（按性价比排序）

### A. 把动态块从「前缀块」里剥出来，放到请求最末尾（推荐，收益最大）

- 目标：让 `<system-context>` 的 13k 块里「稳定部分」（USER 画像、认知画像、偏好、史料纪律）字节不变；只把 `Now:` / `clock` / `weather` / `emotion_state` 这些**真正每轮变**的小块挪到整个 context 块的最末尾。
- 效果：前缀稳定 → 服务端缓存整段命中 ≈99%（已有 340 条 0% 命中的调用可转为高命中）。
- 风险：低——只改块的拼接顺序，不改内容语义；`render_blocks` 已有 `priority` 字段可复用。
- 验证：改前后对比 `cache_read/(input+cache_read)` 的分布（目标：0% 桶从 340 条降到 <100 条）。

### B. 注入块内容做「指纹稳定化」

- 对各块输出去掉时间戳/计数等逐轮抖动（如 `delivered` 的"今天 N 封"只在 N 变时才变），把毫秒级时间截断到分钟/小时。
- 风险：中——可能损失实时性；需逐块评估（天气/时钟本来就该实时，不能动）。

### C. 不要做的（已证伪）

- ❌ 给 OpenAI 通道注入 `prompt_cache_key` / `cache_control`：网关自动缓存，客户端标记无效（`_usage_from` 已证明）。
- ❌ 照搬 Anthropic 的 `_add_cache_breakpoints`：那是 Anthropic Messages API 专用机制，OpenAI chat.completions 形态不认。
- ❌ 缩减 13k 预算来「省 token」：违背了「沉淀必要」的前提，且缓存命中后这部分按 0.1x 计费，真正该提升的是命中率而非砍内容。

## 8. 缓存命中率优化实施（2026-11-19，已落地）

> 用户拍板：只做「提升缓存命中率」，夜间调度不动。
> 冲突规避：另一路正在做巨型文件拆分（`server/app.py`/`server/manager.py`，15:08 mtime）。
> 本改动核心放在 **`context_budget.py`（另一路不碰）**，`manager.py` 只改 2 行（import + `_add` 加 volatile 标记），
> `agent.py` 改时钟块位置——即使另一路随后把 `build_full_context_for_turn` 搬到 `context_assembly.py`，
> 这两行会随函数一起搬走，不产生语义冲突。

### 改动内容

1. `deskmate/memory/context_budget.py`：
   - `ContextBlock` 加 `volatile: bool = False` 字段；
   - 新增 `VOLATILE_BLOCKS` 集合（clock/weather/emotion_state/delivered/mailbox/user_episodes/manuscript）；
   - `render_blocks()` 输出时「稳定块在前、volatile 块在后」，各自内部保持原顺序（`stats["kept"]` 口径不变）。
2. `deskmate/memory/manager.py`（2 行）：`_add()` 里按 `name in VOLATILE_BLOCKS` 标记。
3. `coworker/agent.py`：`Now:` 时钟块从 `parts[0]` 挪到末尾（前缀稳定）。

### 为什么这样能提升命中率

服务端前缀缓存逐字节匹配。原来 13k 注入块里夹着时钟/天气/情绪等每轮变的小块，**一处变动击穿整段前缀**。
现在这些小块全在最末尾，前面的画像/认知/world/prefetch 等大块逐字节不变 → 网关 32k 前缀缓存能覆盖整段稳定部分。

### 验证

- 单元测试：`test_context_budget/test_deskmate_trace/test_user_episodes/test_latency_hot_paths/test_deskmate_memory_context_cache` = **73 passed**。
- 合成验证：稳定块最大位置 < 动态块最小位置（True）；真实函数两次组装（同一输入）逐字节一致。
- 效果验证需要**新请求跑一段时间**后对比账本（改前的历史数据不会变）：
  - 基线（近 7 天 mimo-flash）：命中率 44.3%，未命中 input 3211 万。
  - 改后目标：命中率显著提升（尤其那些原本 0% 命中的短调用转为高命中），未命中 input 下降。
  - 复核命令见 §6。注意：改后至少等 1–2 天新请求积累再看，旧账本不代表改后效果。
