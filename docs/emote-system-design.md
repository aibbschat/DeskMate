# 墨灵表情系统 · 架构设计与长远规划

> 状态：规划稿（待评审，未实现）。缘起：用户反馈「桌宠识别不了表情——只读到一串符号+一个中文词，没真懂表情」，并要求从微信/QQ 那样的**自有接入标准 + 生态闭环**角度做系统级设计；同时研究「大模型怎么识别表情」并借鉴现成项目。

## 0. 当前实现的痛点

现在表情是「缝补式」实现：LLM 输出 `![中文名](emote:NAME)`（markdown 图片语法 + 中文 alt），前端拦截 `emote:` 协议渲染成墨灵 SVG。问题：

1. **模型把 `emote:v` 当成普通 markdown 图片**，甚至自己转述成 `![v](emote:v)` 后说「识别不了」——它没把这套当成「表情指令」。
2. **含义只靠 persona 里一段散文 + alt 文字**，模型没当真，理解不稳定。
3. **没有「标准 / 注册表 / 生态」概念**，难以扩展、难以复用。

核心认知：**自定义表情压根不在 LLM 训练数据里，模型从零理解不了它的「含义」**。要让模型懂，只有两条路：① 在上下文里明确告诉它含义（语义 grounding，可靠、便宜）；② 把表情图喂给视觉模型 VLM（贵，且仍离不开文字标注）。不存在「模型自己看懂墨团」的魔法。因此我们做的是——**让「含义」成为系统标准的一部分，模型只是标准的消费者**。

## 1. 研究结论（可借鉴的现成做法）

| 来源 | 是什么 | 借鉴点 |
|---|---|---|
| **Tuya 多模态情绪输出**（开发者文档，真实方案） | 把「表情↔情绪」映射表写进系统提示，并强调「**只能用下面定义的，禁止自创**」 | **closed-vocabulary 范式**：让 LLM 稳定输出受控表情集的最干净做法 |
| **sticker-reply-skill**（GitHub 真实项目） | AI 用表情包的 skill：核心是 `stickers/index.json` 清单（filename/emotion/description/tags/scene/intensity/reply_mode）+ 模型输出 `[sticker:xxx]` 标记 + 应用查表渲染 | **清单即「接入标准」**，模型与应用共用同一真相源——正是我们要的 |
| **EmojiAgent / 智谱**（多模态表情语义引擎） | 数据层（2856 个 Unicode 表情基础语义库 + 场景标注 + 动态特征）+ 模型层（视觉-文本双塔跨模态对齐）+ 服务层（解析/分析/生成 API） | 表情理解要有**语义库**做底座，未来可扩展 |
| **微信表情开放平台**（用户点名的参照） | 创作者投稿专辑（16/24 张·专辑，240×240，统一画风，平台审核，公众号/视频号/小程序/红包封面分发，赞赏/付费变现） | **标准化规格 + 专辑为单位 + 注册/审核/分发 + 生态闭环** |
| **LobeChat 表情包插件设想** | 轻量关键词匹配 + 规则引擎做情绪识别，非侵入式插件 | 不必上重型模型，先规则后演进 |

关键论文佐证：arXiv 2402.01681《Emojis Decoded》指出，Unicode emoji 模型还能靠训练数据理解，但**无标准 Unicode 的自定义表情必须借助 VLM 或上下文说明**——坐实了「自定义表情要靠系统告知含义」。

## 2. 架构原则

- **Manifest 唯一真相源**：机器可读、版本化；「语义(meaning)」与「渲染(render)」彻底解耦。
- **Closed vocabulary**：模型只能使用 Manifest 中登记的表情，**禁止自创**。
- **系统侧语义标注**：用户发来的表情，后端在喂给 LLM 前展开为结构化含义，**保证模型「懂」**，不靠模型猜。
- **同一套表情处处可用**：聊天 / 桌宠反应 / 主动提醒 / 勋章报喜 / 圆桌共用。

## 3. 架构（见对话内嵌分层图）

- 顶层 `Emote Manifest`：id · name_zh · name_en · category · semantic(含义/触发) · emotion · render(svg) · pack · version。
- 左支「模型理解侧」：结构化词表注入（closed vocab）→ incoming 语义标注（兜底）→ few-shot → 未来可选 VLM。
- 右支「渲染侧」：SVG 矢量组件（墨灵水墨风）→ 主题/动效 → 多挂载点 → `emote:` 协议拦截渲染。
- 触达面：聊天气泡 / 桌宠反应 / 主动提醒 / 勋章报喜 / 圆桌。
- 生态闭环：Pack（主题专辑）→ Registry（统一登记）→ 未来用户自制 Pack → 审核分发 → 反馈反哺。

## 4. 根治「识别不了」的三板斧（P0，立刻止血）

1. **系统侧语义标注（关键）**：用户发来 `![卡文抓狂](emote:stuck)`，后端在喂给 LLM 前自动展开成
   `[用户表情：卡文抓狂 —— 含义：用户卡文/写不出/创作受阻，借墨灵表达抓狂情绪]`。
   含义由系统携带，模型必懂。直接复用现有 `EMOTES` 注册表的 `label` + `keywords`。
2. **结构化词表注入**：把 Manifest 生成紧凑表格注入系统提示（`id｜中文名｜含义｜触发场景`），并声明「只能使用下表，禁止自创；收到用户表情对照下表理解并自然回应」——**替代现在那段散文**。
3. **few-shot 示例**：2–3 个「用户发 X → 理解为 Y → 恰当回应」的例子。

> 可选未来（P3）：把 SVG 渲染成位图喂 VLM，让模型真「看到」表情——成本高，且仍离不开文字标注，优先级低。

## 5. 分阶段规划

- **P0 止血（推荐先做的）**：系统侧语义标注 + 结构化词表注入 + few-shot。纯后端/提示词改动，低风险、立竿见影、不依赖重做。
- **P1 标准化地基**：把 `EMOTES` 提升为正式 `emotes.manifest.json`（机器可读 + 版本号 + 中英名 + category + semantic + emotion + render + pack），前后端共用；前端渲染从 Manifest 读取。
- **P2 Pack / 专辑 + 注册表**：表情按主题成包（桌宠日常 / 写作场景 / 节日特辑），Registry 统一登记；触达面扩展到主动提醒、勋章报喜（之前留的增强点）。
- **P3 生态闭环（远期）**：用户自制 Pack 入口、审核、分发、反馈反哺——真正像微信那样「什么表情都能接入」。
