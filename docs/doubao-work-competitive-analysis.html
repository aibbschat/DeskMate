豆包工作（字节跳动）深度研究与借鉴分析

研究对象：豆包工作（2026-08-25 发布，企业级办公 Agent）　·　对标：OpenWorker / 墨灵桌搭（C 端创作者伴侣）
研究日期：2026-08-25　·　资料来源：光明网、新京报、证券时报、广州日报、新华财经等公开报道（已交叉比对）
一句话结论：豆包工作 = 「飞书企业上下文 + 通用办公 Agent + 多 Agent 工作小队 + 云端持久执行」的 B 端办公范式； 我们 OpenWorker/墨灵 = C 端「创作者桌搭伴侣」，赛道不同。
可借鉴的是 思想而非形态——其中最值得抄的 3 条（指哪改哪局部编辑 / 创作回流知识沉淀 / 圆桌综合报告）与历史小说创作场景高度契合，且我们已有大半地基，投入产出比极高； 而「飞书打通 / 企业安全 / 云端持久」是字节的 B 端护城河，不该抄。

一、能力雷达对比（10 维度）

豆包工作（B 端办公） OpenWorker/墨灵（C 端创作桌搭）

评分为本研究基于公开报道与项目现状的定性估算（1–5）。核心看点：我们在知识沉淀闭环、情感陪伴/成长、多 Agent 协作三项领先或持平； 豆包在多模态生成、桌面操控、长任务云持久、企业安全四项占优（后两项属 B 端诉求，非我们方向）。

五、可借鉴清单（按优先级）

P0优先做 · 场景高度契合、地基已具备

  • 「指哪改哪」稿件局部协作编辑
    现状：manuscriptReview 已有审稿标记，但编辑仍是整段/整稿级。豆包做到「框选任意局部→定点改→不重生成整篇」，对历史小说逐句打磨痛点精准。
    落地：前端选区 → 后端局部补丁 API（diff 式替换，保留上下文）→ 升级 manuscriptReview 标记协议。投入小、差异化强。
  • 创作产出回流「圣经」闭环（强化版）
    现状：圣经（可核验实体）+ longterm + journal + USER.md 已在，但「一次创作产出的设定/人物/史料是否自动 upsert 进圣经」链路不够顺。
    落地：after_action 加一条「稿件结构化抽取 → 圣经实体确定性 upsert」（复用 entities.py + verify_records）。下次调用直接命中，越写越懂你的书。
  • 圆桌「工作小队」议题驱动分工 + 综合报告
    现状：圆桌 7 专家已具备，偏「议题群聊」，缺任务卡/进度/成品交付。
    落地：圆桌加任务/进度视图（对标 dsh）+ 输出升级《综合研判报告》（已列入规划）。复杂题材（如某段历史考据）并发考证后出一份汇总。

P1值得做 · 增强体验

  • 长任务后台「不中断」可视化：proactivity 引擎 + scheduler tick 已具备，但用户感知弱。借鉴豆包「状态可见 + 可挂起/恢复」，前端加后台任务面板（进度/日志/可取消）。无云也能做。
  • 技能/连接器开放市场范式：SkillManager 已有 38 MSApps + imported 包。强化「技能即 persona 能力包」的 marketplace 感（已对齐 agentskills.io 格式）；顺带补 learning_graph 前端面板（API 已就位）。
  • 桌面「手」场景化：nut-js sidecar 已验证。补 macOS 屏幕录制/辅助功能权限校验，把 computer-use 收敛到「稿件/资料」场景，而非通用操控。

P2 / 不抄赛道不同 · 字节的 B 端护城河

  • 飞书/企业上下文打通：我们是个人创作者，无企业权限体系。「上下文」应是个人创作脉络（圣经+USER.md+稿件），不是企业聊天记录。
  • 企业级安全合规 / 双项认证：C 端本地应用无此合规诉求。
  • 云端持久执行 / 手机远程操控：需云后端，与本地桌搭形态相悖。

六、我们的差异化护城河（豆包没有的）

情感与成长

  • 墨灵（桌宠）GrowthEngine 成长系统——陪伴维度豆包为零
  • 桌搭形态（桌面常驻、低打扰、主动关怀）

严肃创作能力

  • 历史考据「圣经」体系：可核验、可删除、纯 Python 核验，拒绝传言
  • 圆桌 7 专家 + @召唤 的创作者协作范式
  • 本地桌面「手」（操作本机文件/软件）

优先级动作理由 / 投入
