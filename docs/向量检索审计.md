# P2-2 记忆向量检索审计与落地改进

> 审计日期：2026-08-29 ｜ 实施方：WorkBuddy ｜ 可重跑脚本：`scripts/audit_retrieval.py`

## 一、审计结论（一句话）

**墨灵当前的记忆检索底座是「纯关键词 / 子串匹配」——全仓不存在 `vectors.json`，
`vault_store.search` 是逐文件子串扫描（连 FTS5 都未启用）。** 文档里「vectors.json 已 1.1MB」
的说法与代码实际不符（疑为上游规划或旧机器状态残留），应以代码为准。

- ✅ **显式查询召回可靠**：8.1 评测集 50 题 100% 通过（用户画像/全局/项目/vault/圣经 五类全中）。
- ⚠️ **隐式查询有缺口**：用户问「年号」但记忆写「朝代」这类同义/跨称提问，纯关键词接不住
  （即文档 P08 暴露的缺口），这是「越用越懂你」的真实短板。

## 二、检索机制实地核查

| 层 | 代码位置 | 实际机制 |
|---|---|---|
| Recall（近期记忆） | `manager._search_recent_memory` | 关键词 + CJK 2-gram 子串匹配 |
| 全局记忆 | `manager._search_global_memory` | 关键词子串匹配（`_extract_keywords`） |
| Archival（vault） | `vault_store.search` | 逐 `.md` 文件子串扫描 + 关键词命中数排序 |
| 项目记忆 | `manager._search_project_memory` | 关键词子串匹配 |

**没有任何一处调用 embedding / 向量索引 / FTS5 SQL。** 关键词检索对「成化」≠「明朝」这种
跨称表述天然失效。

## 三、落地改进（不伪造向量库，务实封堵缺口）

在既有关键词检索上**接入查询扩展（别名桥接）**——零 LLM、fail-open、可观测：

- 新增 `deskmate/memory/query_expand.py`：`EXPANSION_MAP`（年号↔朝代/庙号双向表，重点覆盖
  萧哥专攻的明朝年号）+ `expand_keywords()`（命中才扩展、去重、封顶 20，不臆造）。
- 接入两处检索分词：`manager._extract_keywords`（Recall/全局层）与 `vault_store.search`
  （Archival 层），均 fail-open。
- 效果：问「成化年间的制度」→ 扩展出「明朝/宪宗/成化年间」→ 命中记忆里的「明朝官制」「朱元璋」。
  P08 缺口实测封堵（见探针）。

## 四、是否要上真向量层？

**当前阶段不必。** 理由：

1. 查询扩展 + 关键词已覆盖已知同义/跨称（年号↔朝代等可枚举强关联），零成本、可复现、可单测。
2. 真向量层需 embedding 模型 + provider + 索引构建/维护，是工程大项，收益主要在「自由语义」
   （非已知别名）场景——当前「越用越懂你」召回需求已被满足。
3. 若后续要覆盖开放域同义（如「赶稿」↔「截稿压力大」），再引入 embedding 向量层，
   且可平滑叠加在现有 `expand_keywords` 之后（provider 可用时启用，不可用回退关键词）。
