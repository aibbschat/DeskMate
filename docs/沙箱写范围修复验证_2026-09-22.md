# 「沙箱无写权限」定性 + 修复验证报告

日期：2026-09-22　提交：`83cdfee`（已推 backup，**未碰 origin**）

---

## 一、结论

**不是环境限制，是代码缺口。已修。**

「进度跟踪·国子监」每次收尾都写「正典待你手动同步，**沙箱无写权限**，老规矩」——
这句话指向的不是 macOS 权限，而是**同一次会话里存在两套写范围**：

| 执行层 | 写范围由谁定 | 白名单内容 |
|---|---|---|
| `write_file` 等文件工具 | `coworker/roots.py` 的 `RootDir(writable=True)` | 你在界面上加的目录 + 定时任务自动加注的 Desktop / Documents / Downloads |
| `run_shell`（命令） | `coworker/sandbox/macos_sandbox.py` 的 Seatbelt profile | 只白名单 workspace + `/tmp` + `config.mounts` |

**`roots` 从未传给沙箱**。于是同一个目录：文件工具写得进去，命令一写就死。

## 二、定性证据（为什么排除了 TCC）

决定性线索来自 09-21「写作营每日文章」的运行记录，它自己写着：

> 桌面经 shell 写入被 macOS 权限拦截……**改用文件写入工具直写桌面路径成功**。

同一天、同一个 app、**同一个目录**：`run_shell` 死，`write_file` 活。

→ 若是 macOS TCC（隐私权限），那是**进程级**的，两个工具会一起失败。
**只有工具级差异**才会出现这种分裂 ⇒ 问题在 Seatbelt profile 的**白名单缺项**，与系统权限无关。

## 三、根因

`coworker/sandbox/config.py` 里的 `Mount` / `SandboxConfig.mounts` 能力**早就写好**，
但 `agent.py::build_engine` 构造 `sandbox_cfg` 时**从来没有填过 `mounts`**（永久 `[]`）——
**能力在、从未接线**。

反证作者本意：`manager._scheduled_write_roots` 的 docstring 自己写着这些 roots 是为了
「aligns the file tools with what AUTO already permits for **shell redirection**」——
**本来就是给 shell 用的**，只是没接上。

## 八、两个自己踩的坑（记在这里免得重犯）

1. **Seatbelt 是 deny 优先于 allow，不是 last-match-wins。**
   我原以为换个位置能「加固」，还写了注释；对照实验证明**位置无关**（移动前后都拦得住）。
   动安全代码前先用真实内核验语义，别信文档印象。
2. **测试探针不能放 `/tmp`。**
   profile 本就 blanket-allow `/tmp`，断言会退化成恒真（`pytest tmp_path` 正落在那儿）。
