# 上下文总预算硬上限实验报告（2026-11-20）

## 缘起

萧哥实测：同一问题（读原文理「归营路线：铜雀-渡口村-翻山后-高村」，怕与夜不收来路冲突），
Hermes 两三分钟出答案还带建议，小桔 9 分钟仍在执行的路上。怀疑「大量上下文」是根因。
昨天（11-19）已做集中性能优化（PR0–PR21，含缓存复用、tool schema 预算 48000、
inject 稳定块在前等），今天仍慢，故要求搭一个**上下文总预算硬上限**实验，
前提：**不能影响答案质量**。

## 一、实测：这 9 分钟到底发生了什么

从 `~/.deskmate/deskmate.db:llm_usage` 还原 14:30:46–14:39:19 的调用：

| 指标 | 实测值 |
|---|---|
| 9 分钟内模型请求 | **20 次** |
| 单次上下文 prompt_chars | 8.7 万 → 13.2 万字 |
| 最慢首字等待 | 23.2 秒 |
| 最长单次流式 | 118 秒 |
| 模型 | mimo-v2.6-pro（主力推理）+ mimo-v2.6-flash（旁路抽取） |

关键：`cache_read` 常见 4–9 万 token —— 说明昨天优化的**前缀缓存在大量命中**，
13 万字里有相当部分是缓存复用，不是全量重算。所以「上下文大」本身被缓存部分对冲了。

## 二、注入链路现状（代码实测）

出站请求 = system prompt + 历史消息 + `<system-context>` 注入块 + 工具 schema。各路预算：

| 一路 | 大小 | 现有预算 | 备注 |
|---|---|---|---|
| system prompt | ~1.3 万字 | 无 | deskmate.md 11727 + persona 873，稳定前缀，有缓存 |
| 工具 schema | ~4.8 万字 | 48000 字符（昨优化） | 独立预算，不进 prompt_chars |
| `<memory-context>` 注入块 | ~1.7 万字 | 13000 token（context_budget.py） | 已分级裁剪，稳定块在前 |
| 历史消息（读原文 tool result + 过程轮） | 随轮次累积 | **仅 compaction 102400 token** | ⚠ 见下 |

⚠ **关键发现**：compaction 触发线 = `0.8 × 128000 = 102400 token`，而本题实测
input_tokens 最高 96748 —— **没到线，压缩从未触发**，所以多轮读原文的历史一直累积、
每轮全量重发。这才是「越跑越慢」的机制。

## 三、实验装置（已实现，默认关闭）

- `coworker/context_window_budget.py`（底座无关、纯标准库、fail-open）
- 挂在唯一 provider 出口 `coworker/engine.py::_outbound_messages`
- 开关：`COWORKER_CONTEXT_TOTAL_BUDGET`（默认 0=关闭）；`COWORKER_CONTEXT_TRIM_TOOL_RESULTS=1` 可 opt-in 裁原文（实验用）
- 白名单豁免（绝不裁）：system 人格底座 / 首条 user / 末条 user（含注入块）/ 带 tool_calls 的 assistant / tool result（原文）
- 只裁中间的 assistant 过程自述轮次；触及豁免底线时整个放弃（宁可超预算也不伤核心）
- 可观测：`engine._last_context_budget_report`（before/after/各路字符/裁了几轮/豁免路由）+ 裁剪时 warning
- 测试：`tests/test_context_window_budget.py`（11）+ `tests/test_context_budget_outbound.py`（3），全绿；默认关闭 zero-diff 已钉死

## 四、决定性实测结论

用「读四章原文理路线」的多轮结构做 A/B：

```
原始: system 2405 + user 54 + assistant 193 + tool 12543 = 15195 字
budget=OFF:    15195 -> 15195（不变）
budget=20000:  15195 -> 15195（本来就够，无需裁）
budget=12000:  15195 -> 15195（触及豁免底线 at_exempt_floor=True，拒绝裁）
```

**结论：在不影响答案质量的硬约束下，总预算硬上限几乎无处下手。**

原因：中间过程轮（可裁）只有 193 字（1.3%），而大头是原文 tool result（12543 字，82%）
与人格 system 底座——两者恰恰是答案依据、是白名单豁免项。砍光可裁部分也只降 1.3%。

这印证了动手前的判断：**「保质量的裁剪（砍旧的伤上下文）」与「保缓存（砍尾部只击穿尾）」
方向相反**；而唯一量大的可砍项（原文）又不能砍。所以这条路——在 OpenWorker 内靠
「砍上下文」提速——空间极小。

## 五、根因指向 & 建议

真正能让本题提速的方向，按收益排序：

1. **降往返次数**（收益最大）：本题 20 次模型往返是 9 分钟的主因。让一次读稿覆盖多章、
   减少「读一章→说一句→再读」的碎步，比砍字符有效得多。这是 agent loop 编排问题，
   与底座无关。
2. **让 compaction 在本题触发**：触发线 102400 token 偏高（本题 96748 没够）。
   但降线会引入摘要 LLM 调用 + 可能丢原文细节，须谨慎评估——**这正是"不伤答案质量"
   与"提速"的冲突点**。
3. **不搬底座也能做**：上述两项都在 OpenWorker 内，无需换 Hermes。搬底座只会换引擎，
   不会自动减少往返次数；且 Hermes 2200 字快照装不下小桔的完整人格+记忆，
   搬过去要么降级成"失忆的小桔"，要么得重写 MemoryProvider 把 49 表喂回去——是另一笔大账。

**对用户「Hermes 更快」的诚实解读**：Hermes 快，很可能是因为它一次出答案（往返少），
而不是引擎本身更快。这个实验把「是不是上下文太大」证伪了大半——是**往返次数 + 缓存时效**，
不是字符总量。
