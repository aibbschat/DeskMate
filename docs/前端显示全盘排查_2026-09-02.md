## 三、小桔日记的规律（萧哥问的重点）

### 两套"日记"，别混

| | A. 小桔日记 | B. 我们的日记（MomentFeed） |
|---|---|---|
| 存储 | `~/.deskmate/diary/YYYY-MM-DD.md` | `deskmate.db` → `user_posts` 表 |
| 作者 | 小桔（第一人称） | 萧哥 + 小桔留言 |
| 生成 | `DiaryWriter`（零 LLM，模板渲染） | 用户手敲 |
| 现状 | **仅 2 篇**：08-29、08-31 | 9 条，**全是 `author='me'`** |

萧哥看到的"她写了两条"就是 A 的那 2 篇文件。B 里小桔一条都没写过。

### 核心规律：**只在你手动点按钮时才写**

```
DiaryWriter.ensure_today()
    ↑ 唯一调用方
POST /v1/deskmate/diary/today   (app.py:3437)
    ↑ 唯一调用方
DiaryPanel.tsx:247 / :288  两处按钮的 onClick
```

全项目 grep 结果：`ensure_today` 只出现在后端路由 + 单元测试里，
**没有任何后台任务 / 定时 tick / proactivity 心跳会调用它**。

### 硬证据：09-01 有 28 条事件，却没日记

```
2026-09-01 当天事件数: 28   （memory_learned / skill_evolved 等）
2026-09-02 当天事件数: 0
今日日记已存在? False
```

08-29 和 08-31 那两篇都是 **08-31 15:22 一次性生成**的（当时手动触发/测试）。
之后 09-01 忙了一整天（28 个事件）、09-02 至今，一篇都没再生成。

### 附带问题：当天生成一次就固化

`ensure_today()` 的幂等是「当天文件已存在且非空 → 直接返回」。
意味着**早上 9 点点一次，当天剩下的事就永远进不了这篇日记**。
日记里写死的"累计对话 N 轮"也只是触发那一刻的快照
（08-31 那篇写着 190 轮 / Lv.7，库里现在已是 203 轮 / Lv.9）。

### 内容生成逻辑（零 LLM，如实记录）

`_render_diary()` 把当天 `recent_events` 按 kind 翻译成第一人称：
`skill_used` / `user_corrected` / `creation_approved` / `memory_learned` 等，
最多列 6 条事实 + 默契/信任/心情/Lv + 当日徽章 + 最投入领域。
无事件时写"今天没有太多动静。我安静地待着，等你忙完。"
——**fail-open，绝不编造**，这点做得对。

## 四、其他发现

### `growth.json` 是空壳，真数据在数据库

```
~/.deskmate/growth.json          → intimacy 0.0 / level 1 / total_chats 0 / recent_events []
deskmate.db → json_blobs[growth] → intimacy 100.0 / level 9 / total_chats 203 / recent_events 50
```

后端 `GrowthEngine` 实测读到的是**数据库**（203 轮 / Lv.9），显示层**当前正确**。
`growth.json` 只是 08-31 迁库时遗留的 legacy 文件（`state.py:178` 的 `legacy_path`），
但它的 mtime 是 09-01 20:28 —— 说明**仍有代码在写它**，即 `save_state` 曾走过文件模式
（MEMORY 里记过这个坑：`_is_default_dir()` 判定，55af26d 修过，看来没修干净或有别的路径）。

**风险**：若某次 DB 读不到而回落到 legacy，会读到全 0 的空壳，桌宠瞬间退回 Lv.1。
建议排查写入方后把该文件改名 `.bak`。

### `recentMemories` prop 无人传入

`StatusPanel.tsx:850` 的「近期记忆」块依赖 `recentMemories`，但全项目**没有任何
组件传入这个 prop** → 该区块永不渲染。同理 `StatusPanel` V1 整体未被渲染。
属历史遗留死代码。
