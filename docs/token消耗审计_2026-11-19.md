> 范围：只查「哪里在浪费/重复烧 token」与「怎么省」，不改代码（另一路在并行改造）。

## 0. 结论先行

当前 7 天烧了约 **4280 万 token**，IoU 上分两块：

1. **前台/后台的「每轮固定注入」**：每轮注入 **12904 token**（p95 12984，几乎精确顶到 13000 预算）——这是所有对话轮、后台 judge、专家、bot 发言都要付的固定成本，且**在 OpenAI 兼容通道上不享受任何 prompt cache**，100% 全价重发。
2. **模型选择**：主力 `mimo-v2.6-flash` 801 次 / 3313 万 token（占 77%），`hy4-flash-free` 169 次 / 763 万。

最大的 three 个浪费点（按可省金额排序）：

| 排名 | 浪费点 | 证据 | 可省量级 |
|---|---|---|---|
| ① | **OpenAI 兼容通道无 prompt caching**，每轮 12900 token 全价重发 | `openai_provider.py` 只读 `cached_tokens`，从不注入缓存标记；Anthropic 有 `_add_cache_breakpoints` | 缓存命中后重复部分约 **0.1x** 计费，理论上每会话可省 50–90% 的重复前缀 |
| ② | **注入块被裁剪仍全额采集 + 每轮顶满预算** | trace：`memory_references` 丢 498 次、`mailbox` 377、`lessons` 270；p50/p95/max 都≈13000 | 采集侧 CPU/延迟浪费；token 侧可降 20–40% |
| ③ | **账本 scene 全空**，无法定位哪条链路在烧 | 今天 132 次调用 scene 全 `(空)`；`scene_scope` 只在 consult/bot_group 两处，且没覆盖到后台 judge / 前台 turn | 没有归因就没有精准优化，属于「看不清的浪费」 |

## 2. 浪费点逐条分析

### ① OpenAI 兼容通道无 prompt caching（最高优先级）

- 证据：`coworker/providers/openai_provider.py:225` 只是从 usage 里**读** `cached_tokens`；全文件没有任何向请求注入 `prompt_cache_key` / `cache_control` / 前缀缓存标记的代码。对照 `anthropic_provider.py:345 _add_cache_breakpoints()` 明确做了两处断点（system+tools、最后一条消息尾部）。
- 后果：主力模型走的是 OpenAI 兼容通道（火山/mimo/hy4 等），每轮把系统提示 + 13k 注入块 + 全部历史 + 工具 schema **完整重发**，没有一份走缓存价。
- 方案方向（需先确认供应商支持哪种）：
  - OpenAI 原生 / 兼容 `prompt_cache_key`（部分兼容网关支持）+ 自动前缀缓存：把**稳定不变的前缀**（system、人格、注入块、工具 schema）放在请求最前且逐字节稳定，尾部的「本轮用户消息 + 时钟」放最后。
  - 若网关不支持缓存，至少做**请求体指纹去重**：同一份 context 在 TTL 内复用（已有轮内缓存，但跨轮没有）。
- ⚠️ 风险：`engine.py` 的 `<system-context>` 是附在**最后一条 user 消息**上的，且里面有 `Now: <分钟>` 时钟、`clock` 块——这些每分钟变动，会把整段前缀的缓存击穿。要把时钟/动态块挪到最后，稳定块前置。

### ② 注入块「采集了又被裁」+ 预算恒满

- 证据：trace 里 `memory_references` 被丢 498 次、`mailbox` 377、`lessons` 270、`reading` 93、`reflection` 89、`intent` 66。这些块的共同点是 `priority>50` 或 `keep_light=False`，会被 `render_blocks` 整块丢。
- 后果：`build_full_context_for_turn` 仍为每个块跑 I/O / SQLite / embedding（PR1 已并行化，但成本仍在），然后 `render_blocks` 丢弃。token 上，其它保留块顶满 13000。
- 方案方向：
  - **前置裁剪**：`render_blocks` 判定前，先算 `light` 和预算，显然会被丢的块（`priority>50` 且预算已超）直接不采集。
  - **预算分级**：闲聊/短指令轮降低预算（当前闲聊只 2/555，白名单太窄）；把固定块（USER 画像 5100、cognitive 4500、world 4500）拆成「常驻核心 + 按需召回」。
  - 用户明确说「思考、沉淀有必要」，所以这里以**砍重复与无效采集**为主，不砍有效内容。

### ③ scene 全空，无法归因

- 证据：今天 132 次调用 scene 全 `(空)`；`scene_scope` 只在 `consult.py` 和 `bots/runtime.py` 两处调用，而主力消耗来自前台 turn 和后台 proactive tick（均没打标签）。
- 后果：无法回答「后台空闲时烧了多少」，优化没有靶子。
- 方案方向：在 `engine._loop` 入口按来源打 scene（前台=`foreground`、后台 tick=`proactive_tick`、专家=`expert_consult`、bot=`bot_group`、定时任务=`scheduled`）。contextvar 已能在 PR3 跨线程池传播（`engine._astream` 用了 `copy_context`），补调用点即可，零行为风险。

### ④ 空闲时段仍在消耗（22–23 点 ~340 万 token）

- 后台 proactive tick 默认开，30s 一跳。已有护栏：quiet window 90s、指纹去重 1h、共享节流 1h、用户不在桌前跳过、感知信息不足跳过。
- 但 `EmotionEngine` 的 `get_self_expression_pending()` 会**强制放行 judge**（`tick.py` `_force_judge`），绕开指纹去重；`world_search` 有 24h cooldown（正常）。
- 方向：确认夜间这 340 万是 judge 强放行还是定时任务；若是前者，给「强制放行」也加个低频上限（比如每小时最多 N 次）。

### ⑤ 短问答也付满额上下文

- `is_light_turn` 白名单太窄（555 轮只有 2 轮判为闲聊）。像「早」「在吗」走了窄白名单能省，但「进度到哪了」被 `_PROGRESS_HINTS` 强制当工作轮（有意为之，因为要 intent 块），这类轮仍付 12900 token。
- 方向：引入「轻量工作轮」档（非完整闲聊，但预算减半、跳过 cognitive/world 重块），按 intent 命中判断。

## 4.5 追加：用户实测反馈的归因（11-19 下午）

用户反馈：主模型小米，2–3 天用了 60%+；OpenClaw Go Plus 套餐 97%，绝大部分是它消耗。顺着账本反查（近 3 天 1017 条调用）：

### 真正的消耗结构：少数「巨型长任务」吃掉大头

| 指标 | 数值 |
|---|---|
| 近 3 天调用 | 1017 次，其中小米 806 次 / 58.7M token |
| 按 120s 间隔聚类 | 87 个任务轮 |
| 每轮调用次数 | 中位 3、均值 9.3、**max 134** |
| **≥10 次调用的巨型轮** | **18 个** |
| 最大 4 个轮 | 134 次/472万、124 次/**585万**、106 次/396万、83 次/335万 token |

**结论**：把 3 天 60% 额度烧掉的不是「空闲也烧」，而是**十几个跑了 10–30 分钟、几十到上百次模型调用的长任务**。单轮 input 高达 **10 万 token**（远超每轮 13k 的注入预算），是长文档读稿把大段正文反复塞进上下文。

### 缓存为什么没救住这些巨型轮

11-18 那个 585 万 token 的轮里，典型调用是：

```
input=91,708  cached=32,768  out=3,317   命中率=26%
input=77,129  cached=32,768  out=3,161   命中率=30%
input=81,498  cached=32,768  out=6,229   命中率=29%
```

缓存命中**恒定卡在 32,768 token**，而 input 是 8–10 万——网关的前缀缓存只覆盖了前 32k，后面 5–7 万全是全价。这与 §1 的「44.2% 缓存覆盖」一致：普通短对话缓存很好，长任务因为前缀太长/变动太大，缓存够不着。

另外还看到 `out=8,000` 连续出现（输出顶到上限），以及巨型轮里混着 `hy4-flash-free / longcat / iceman`——**Go Plus 套餐的 97% 正是这些长任务跨越通道时的消耗**（opencode 通道 211 次调用 / 1183 万 token，主要是 hy4-flash-free 169 次）。

### 所以「启动就烧」的真相

- **后台 proactive tick 确实有消耗**（22–23 点约 340 万 token），但它已有指纹去重/1h 节流，不是 60% 的主力。
- **主力是长任务**：一旦启动一个读稿/专家任务，它会连续 10–30 分钟、上百次调用，每次带 8–10 万 token 的正文，且大段正文的缓存命中只有 32k。
- 用户感知成「启动后消耗快」，是因为这些长任务往往由后台或自动触发，看起来像"没操作也在烧"。

### 可省且不影响任务执行的点（按收益排序）

1. **长文档读稿的缓存友好化**：让同一文档的正文在连续轮里逐字节稳定，并放在请求靠前位置，使网关 32k 前缀缓存尽量覆盖正文头部；避免每轮重新切分/重排正文导致缓存从头失效。
2. **避免「裁完重读」**：巨型轮里 input 9 万+ 且反复出现，符合工具结果被压缩后又重读的模式；`toolresult` 的 spill + 转录路径要保证「裁一次、记路径、不重读全文」。
3. **长任务中记忆注入只付一次**：每轮 13k 注入在 100+ 轮里重复发送；若任务前缀稳定，服务端缓存本应覆盖，但被动态块击穿（见诊断文档 §3）——把动态小块挪到末尾即可。
4. **输出 8000 顶格**：确认是任务需要还是 `max_tokens` 截断后的重试；若是后者，属于纯浪费。

需要 Owner 用账单核实：小米套餐与 Go Plus 的计费口径（是否按 token / 按次 / 缓存价折扣），再决定上述哪一项先做。
