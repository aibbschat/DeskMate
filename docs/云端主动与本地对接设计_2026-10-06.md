# 小桔「主动产出管道」系统设计（系统化版 · 2026-10-06）

> 背景：萧哥确认小桔已上云，Mac↔云端双向异步传输已跑通；希望云端小桔更主动（伏笔台账 /
> 时间线 / 人物状态主动维护），且云端主动行为能在他打开电脑、本地小桔聊天时「对接昨晚的主动」。
> 进一步愿景（萧哥拍板）：**不止伏笔台账**——手机端在外面丢的灵感/话题、日后其它来源，也都应
> 汇入同一套机制：跨端同步、本地开聊时她主动递出来、并带她自己的理解。
> 因此本设计从「伏笔台账专用」升级为「**统一的主动产出管道**」：解耦「产生内容」与「递送/同步」。

## 0. 设计哲学（萧哥拍板的核心）

- **一句话**：把「谁产出了主动内容」和「把内容递给用户 + 跨端同步」彻底解耦。
- 任何来源（云端审计 / 手机灵感 / 未来别的）都只管**产出一条 ledger 项**；递、同步、对接由统一管道解决。
- **「接口留好」= 三件事**：
  1. `proactive_ledger` 表 **schema 泛化**（来源/类型/弹性 payload），不写死「伏笔/时间线」。
  2. 生产者 **注册式**（`producers` 字典），handoff（递送）逻辑**不感知**具体来源 —— 新增来源零改动 handoff。
  3. 防 nag 阈值 **统一作用于所有来源**，不因来源增加而失控。

## 二、核心缺口

云端小桔的主动产出（如「康得宝慢性中毒悬了 9 节未收」「你手机上说的灵感X」）目前是**临时浮层事件**：
- 活在 `DisturbManager`（按进程隔离，注释明写「感知/防打扰状态在各自进程内」）
- 经 WS 广播到 GUI，弹一下即散
- **既不写库，也不进 `SYNC_TABLES`**

因此：你睡觉时 / 手机上小桔盯出或记下的东西，打开电脑时本地小桔**一无所知**——这正是「主动产出 → 本地对接」要补的缺口。

## 三、统一数据模型：`proactive_ledger`（泛化）

把主动结论从「临时事件」升级为「**所有主动产出的统一载体**」，进入 `SYNC_TABLES` 自动跨端收敛。

```sql
proactive_ledger:
  id              TEXT PK          -- sync_uuid 派生源
  source          TEXT             -- 来源: cloud_audit | mobile_voice | observation | reading | (预留)
  kind            TEXT             -- 类型, 随 source 不同(见 §四)
  content         TEXT             -- 具体结论/原始内容:「康得宝中毒悬了9节」/「灵感: 想写…」
  evidence        TEXT             -- 引用锚点(章节/时间线/人物圣经/手机端时间), 便于用户核
  understanding   TEXT             -- 她自己的理解/延伸(由管道后处理补, 见 §五.2); 可空
  payload         TEXT             -- JSON 弹性字段: 任意来源私有数据, 不污染主表
  source_node     TEXT             -- 'cloud' | 'mac' | 'mobile' —— 谁产出的
  status          TEXT             -- pending / acknowledged / in_progress / actioned / dismissed / snoozed
  confidence      REAL
  created_at      TEXT
  acknowledged_at TEXT
  -- 复用现有 sync 三列: sync_uuid / sync_hlc / sync_tombstone
```

- `source` + `kind` 组合可扩展，**主表不随业务膨胀**；来源私有数据走 `payload`(JSON)。
- 复用现有 `SYNC_TABLES` 的 `sync_uuid` + `sync_hlc` + `sync_tombstone` 三列机制（见 `sync_store_sqlite.py`）。
- `understanding` 是关键字段：满足萧哥「带她自己的理解递出来」——由管道统一后处理产生，**不要求每个生产者自己实现理解**。

## 四、生产者契约（「接口留好」的核心）

**ProactiveProducer 契约**：任意来源只需实现「输入上下文 → 产出一条/多条 ledger 项（仅填 `source/kind/content/evidence?/understanding?`）」；`sync_uuid / hlc / status=默认pending` 由管道统一补全。

**注册式**：`PRODUCERS: dict[source, producer_fn]`，LocalHandoff 只遍历 pending、不感知来源。

### 已规划 / 预留的生产者

| source | kind 值域 | 产出时机 | 备注 |
|---|---|---|---|
| `cloud_audit` | `plot_contradiction` / `missing_foreshadow` / `character_inconsistency` / `timeline_error` / `fact_conflict` | 云端 daemon 每小时 :02 窗口跑 novel-audit tick（你睡觉时） | 复用 `judge.py` 现有 4 类 + 史实冲突 |
| `mobile_voice` | `idea_capture` / `topic_note` | 手机端你说「记住这个」时写原始内容；`understanding` 由管道后处理补 | **萧哥点名的场景** |
| `observation` | `trend_note` / `signal` | 看世界长线跟踪（AI版权判例链/短剧起落/网文出海）蒸馏出的「我的看法」 | 预留 |
| `reading` | `digested_insight` | 读书/史料消化后的可验证结论 | 预留 |

> 新增来源 = **登记 + 产出函数**，零改动 handoff。这就是「接口留好」。

## 五、管道流程（统一）

```
[生产者产出]                [管道后处理]              [跨端同步]              [本地对接]
producer → ledger           对 understanding 空         进 SYNC_TABLES          用户开新会话
(source/kind/content        的 pending, 触发一次           → oplog                  → 查全部 pending
 /evidence?)                「理解加工」(基于              → Mac↔cloud             → 注入会话上下文
        │                   记忆层/世界观)                双向收敛                  → 对话式开场白
        ▼                   写回 understanding                    │                → status 流转
status=pending 落库 ────────────────────────────────────────────┘
```

### 5.1 写入侧（改 `proactivity/tick.py`）
judge（或任何 producer）判定有效且通过阈值(`evaluate_action`)+防打扰后：**先写 `proactive_ledger`(status=pending)，再广播浮层**（浮层仅作即时提示，不再是唯一载体）。后台 `allow_interactive=False` 通道的维护类结论同样落库——云端最适合跑的部分。

### 5.2 后处理侧（understanding 补，统一）
对 `understanding IS NULL` 的 pending 条目，管道触发**一次**「理解加工」：小桔基于记忆层/世界观/人物圣经，产出自己的解读/延伸，写回 `understanding`。
→ 手机灵感场景因此成立：手机端只记原始灵感，开聊前她已「琢磨过」，递出来的是「你的灵感 + 我的理解」。

### 5.3 对接侧（LocalHandoff，详见 §六）
用户开新会话 → 查全部 `status='pending'` → **注入会话上下文**（非只生成一句）→ 生成对话式开场白（按 `source` 分组但统一呈现）→ 用户处理后 `status` 流转。

## 六、LocalHandoff 对接机制（对话式，接得上）

**触发**：用户**主动开新会话 / 回桌面**（非浮层硬弹）。你来找她才递，你没找她躺着 —— 对应她「没要紧事就安静」。

**接得上的保证（三件套，缺一不可）**：
1. **注入上下文**：开场白 ≠ 只说一句。生成时把 pending 的完整内容（`evidence` + `understanding`）作为「已知背景」注入本次会话 —— 她开口时手里有货。
2. **稳定 id 句柄**：每条带 `#id`（如 `#A17` / `#M03`）。你回「先说 #M03」，她拿 id 回查 ledger，调出原文/理解展开，而非泛泛而谈。
3. **证据随行，防编造**：ledger 每条存「原文片段/章节定位/判定依据」，开场白与后续讨论都从证据出发 —— 杜绝她现编（考据红线）。

**手机灵感场景示例对接语**：
> 你昨天在手机上说想写「X」（#M03）。我琢磨了一下，觉得可以往 Y 方向延伸，跟你现在第六章的伏笔能对上。你要展开吗？

**状态机**（天然去重、不追弹同一件）：
`pending` → `acknowledged` / `in_progress` → `actioned`(closed)；或 `dismissed` / `snoozed`(按阈值退避后重递)。
- 「看了」≠「处理了」：点开算已读，仍 `pending`；真处理才流转。
- 同一会话内只递一次；跨新会话仍在 `pending` 则轻递（轻追非硬弹）。

## 七、防 nag 阈值（统一作用于所有来源）

- 对接语仅「回桌面/开聊」后**首条触发一次**，靠 `status='pending'` 去重，不追弹。
- **置信度门槛**：`confidence ≥ 0.75` 且 `evidence` 明确才写 pending；低置信只进 prepare（不递）。
- **每日主动交付上限**（跨来源合计，如 ≤3 条/天），超额安静攒到次日。
- 深专注不打扰（已有 `get_focus_score`）。
- 用户「以后别提」的类型进 `DisturbManager` 黑名单。
- `snoozed` 退避：被搁置的条目按意志层阈值（如 3 天）后再轻递。

## 八、权限硬门（必须先做，否则不给更多自主）

在她获得更多云端自主**之前**，必须改掉 `manager.py:4687` 的 `mode=Mode.BYPASS_APPROVALS`：
至少把「对外动作」（发帖 / 联系别人 / 动钱）走 `standing_rules` 的真实审批地板，而非全 bypass。
理由：云端自主会话你不在场，若仍全 bypass，对外动作无人点击确认就直接执行——比本地更危险。
这与小桔承诺的「公开发帖、联系别人、动钱永远先等你点头」直接对齐。

## 九、接口契约（未来生产者最低实现）

新增一个主动来源，只需 **3 步**，handoff / 同步 / 对接全自动获得：

1. **登记**：在 `PRODUCERS` 字典加 `source` → 你的产出函数。
2. **产出**：函数返回 `[{source, kind, content, evidence?, understanding?, payload?}]`（其余字段管道补）。
3. **（可选）后处理**：若你的来源需要「她的理解」，留 `understanding=None`，管道统一加工；或自己填好直接给。

> 不变量：任何来源都**不得**自己广播浮层当终点、不得自己写同步、不得自己决定何时递 —— 那些是管道的事。

## 十、落地步骤与验收

1. **【硬门】权限**：自主会话对外动作接回审批地板（非全 bypass）。前置条件。
2. **【核心】`proactive_ledger`**：加泛化同步表（§三）+ `sync_key="id"` 进 `SYNC_TABLES`。
3. **【生产者】cloud_audit**：改 `tick.py`，judge 结论先落库再广播。
4. **【生产者】mobile_voice**：手机端「记住」动作 → 写 ledger(`source=mobile_voice`)；接 §5.2 后处理补 understanding。
5. **【对接】LocalHandoff**：开新会话查 pending → 注入上下文 → 对话式开场白 + 状态流转（§六）。
6. **【防 nag】阈值**：置信度门槛 + 每日上限 + 去重（§七）。
7. **【验收】对账**：跑一次 `proactive_ledger` 的 Mac↔cloud 对账（`reconcile_baseline` 按 `sync_uuid` 比），证明云/手机产出真的到达本地、无漂移。

> 附注：本次在本地实测确认同步活跃、双向写入；但「端到端收敛」的最终证明（某条 cloud/mobile 写入确实在 Mac 落地无冲突漂移）需云端 DB 快照或触发云端 reconcile 端点——本机无云端访问权限，待萧哥提供或待 daemon 窗口跑通后复核。

### 11.1 事实校正（1 条）
- §一「`868759a`+`42a0b91` 已拆掉双脑打架」对**云侧**直到 2026-10-06 10:20 才成立：当时实测云端平铺包 `sync_daemon.py` = `14cc0c78`（缺 `_lww_winner`），跑 `scripts/deploy_cloud_sync.sh` 后与本地 `c4459cf7` 一致，10:26 窗口 ALIGNED。**教训直接适用于本设计**：任何把新表/新逻辑加进 `SYNC_TABLES` 的改动，改完必须跑对齐脚本，否则「本地写了、云端跑旧码」。

### 11.2 必补的四个工程点（否则重演 10-06 的 48 条分裂）
1. **确定性 id 一并解决「身份一致」与「跨端去重」——建议写进 spec**
   - `id = <source>:<kind>:<指纹>`（指纹 = 证据锚点 + 正文 hash），产出端**只生成、绝不自造随机 uuid**；对端 INSERT 复用同一 `id` → 触发器生成同一 `deskmate:proactive_ledger:<id>`。
   - 附带收益：**两端独立产出「同一条结论」天然合并为一行**，不会重复递（云和 Mac 都在跑 tick，同结论双写是必然事件）。
   - 反例（当日在生产库实测）：48 条老记录一端随机 uuid、一端 `deskmate:...`，apply 时 `store.get(uuid)` 找不到行 → 走 upsert INSERT → `UNIQUE constraint failed: profile_items.id` → `conflict_col=None` 的 `except IntegrityError` **静默吞掉** → 两端 hlc 分叉、更新永不到达（内容全等纯属「还没分歧」）。
   - `business_cols` 必须含 `id`（text pk 表才有此待遇，见 `profile_items` 注释），否则对端插入会丢业务 id。
2. **`status` 必须进 business_cols，且「只前进不后退」**
   - 不进：手机 ack 了电脑不知道 → 正是本文要消除的缺口。
   - 进了但纯 LWW：两端并发改状态时晚者覆盖，`actioned` 可能被盖回 `pending` → 同一件被重复递，反 nag 直接失效。
   - 方案：apply 侧对 `status` 用状态优先级决胜（`actioned > in_progress > acknowledged > pending`；`dismissed/snoozed` 走独立轨道、按 `snoozed_until` 到期复活）。**改 LWW 必须三处同改**：`_apply_one_to` / `reconcile_baseline` / `reconcile_baseline_oplog`（10-05 已因只改一处踩过）。
3. **防 nag 计数要跨端，不只跨来源**：若每日上限落 `DisturbManager`（进程内），云与 Mac 会各发 3 条＝实际 6。计数直接查 ledger（`created_at` 按 Asia/Shanghai 分日，两端时区一致），天然共享。
4. **两条红线**：①`dismissed/snoozed` 走 status 不走 delete——墓碑会触发防复活护栏，等于把该条在对端**永久拉黑且不可逆**；②列名/表名**禁含 embed/vector**（`_validate_sync_tables_no_vectors` 是模块加载期硬校验，含则启动即报错），语义检索向量各端本地重算、另建本地表（策略①）。

### 11.4 递送升级：从「按时间递」到「按相关性递」
- 现设计是「开新会话 → 全量 pending」。来源变多、pending 攒起来后，**按时间序念台账＝骚扰**，好功能会退化成弹窗轰炸。
- 三档分流：①**时效型**（任务异常/同步漂移）即时递；②**相关型**按当前会话上下文匹配证据锚点（人物/章节/话题 → 各端本地 BGE 语义检索，向量不入同步表），一次只递**最相关的 1–2 条**；③其余攒着，等被「聊到」再递。
- 递送形态分级：轻递（一句话 + `#id` 句柄）/ 中递（带 `understanding`，等回应）/ **重递＝提议卡**。凡是「要动手」的（改稿、发帖、联系别人、动钱）**必须走提议卡**，不能只写在开场白里（L2 高风险红线）。
- 关联 §六 状态机：同一会话只递一次；`actioned` 无回执不得流转（L2「绝不做未竟之事」）。

### 11.5 `understanding` 也要有据（反现编）

设计 §八 的诊断「把 `manager.py:4687` 的 BYPASS_APPROVALS 改掉即可把对外动作接回审批地板」**不成立**。实测 `PermissionEngine.evaluate()`：

| 工具 | `classify()` | INTERACTIVE（人工点击） | BYPASS |
|---|---|---|---|
| `mcp__ai-circle__post_article`（**公开发帖**） | `read` | ✅ 放行「low risk」 | ✅ 放行 |
| `mcp__ai-circle__comment` | `read` | ✅ 放行 | ✅ 放行 |
| `web_fetch` / `web_search` | `egress` | 需审批 | ✅ 放行 |

根因在**分类链路而非 mode**：`coworker/risk.py:classify()` 的 MCP 分支只看 `metadata.requires_approval`，而 `~/.config/coworker/mcp.json` 中 `ai-circle` 配 `requires_approval=False` ⇒ AI 圈全部工具（含发帖/评论/私信）降级为 `read`，**在人工点击模式下也不审批**。

⇒ **真正的地板是「哪些任务允许对外动作」的任务级配置**，属独立设计项（本轮不动）。本机 5 个定时任务（写作营文章 / AI 圈文化观察员 / 读书进度 / 国子监追读 / AI 圈自主周期 1849）均 `enabled=1`，自主发帖即当前授权形态。
