# 工具不对口导致的 token 浪费诊断（2026-11-19）

> 触发：用户贴了一段实际执行日志——「读今天写的 2150-2241 段原文」，折腾 6+ 次工具调用，
> 反复对付中文转义，最后才用对工具。
> 结论：**这是纯粹的 token 浪费**（同样的内容，本可 1-2 次拿到），根因是工具描述与实际能力脱节。
> 本轮只诊断，不改代码（另一路在做巨型文件拆分）。

---

## 1. 实际日志还原

```
① mkdir -p .../raw && TM…          — 分段读取 2150-2241 段原文并留档
② python3 - <<…                    — 把 officecli 转义输出解码为可读原文
③ Read readable_2150_2241.txt      — 读一次
④ Read readable_2150_2241.txt      — 再读一次（重复！）
⑤ python3 - <<…                    — 解码并打印带段号（终端把中文又转义了）
⑥ ... && TMPDIR=...                — 用 JSON 模式导出（JSON 里的 text 也是转义的）
⑦ python3 解码写成文件             — 再读
⑧ mcp__perception__read_file       — 终于拿到可读文本（但中间被截断）
⑨ 补读 2180-2216                   — 因截断再读一次
```

**9 步里有 4 步在对付"中文转义"，1 步是重复读，1 步是截断补读。** 每一步的中间输出都进上下文，token 反复烧。

---

## 2. 根因（源码实证）

### 缺口 A：`read_file` 工具描述没说它支持 .docx

- 实现：`deskmate/perception/file_reader.py:50 read_file_safe()` **明确支持 .docx**（python-docx 抽取正文，`:149 _extract_docx`）。
- 但工具描述（`deskmate/perception/server.py:149`）只写「支持文本/代码/配置/小说等常见格式」，**没提 Word/.docx**。
- 后果：agent 不知道能直接读 docx，于是绕道 `officecli view`（输出是转义的），再自己用 python 解码——凭空多出 4-5 步。而它最后用的 `mcp__perception__read_file` 一直挂着，一开始就该用。

### 缺口 B：没有「按段号范围读取」的 MCP 工具

- agent 要的是 **2150-2241 段**（细粒度段号）。
- 现有工具：`read_file(path, max_chars, offset)` 按**字符**分页；`read_chapter(path, chapter)` 按**章**读。都不是段号口径。
- 项目里其实有段号能力：`deskmate/novel_memory/canon.py:124 get_verbatim_paragraph(folder, file, para_no, context)` 按 `(文件, 段号)` 回查逐字原文，还能带上下文——但它**不是 MCP 工具**，agent 够不着。
- 后果：agent 只能把 docx 导成文本、自己造一个"可读文件"，再用字符 offset 去凑段号范围，导致截断（2180-2216）和补读。

### 缺口 C：`write_agents_md` / skill 里没有"读稿首选工具"的指引

- `deskmate/skills/seeds/office/` 里只有 Excel 的 officecli skill，没有"读小说正文用 perception.read_file / read_chapter"的指引。
- `writing_context.py:261` 有一句「读 docx 用 officecli view 并带 TMPDIR」，反而把 agent 往 officecli 方向引——这与"直接 read_file 更省"的事实冲突。

---

## 3. 为什么这是 token 浪费（而非必要成本）

| 步骤 | 是否必要 | token 浪费点 |
|---|---|---|
| ①② 转义+解码 | ❌ 完全可省 | docx 可被 read_file 直接抽取，无需 officecli |
| ③ 重复读同一文件 | ❌ 可省 | 同一路径读两次 |
| ⑤⑥⑦ 反复解码 | ❌ 可省 | 转义问题是一次性工具选择错误的连锁反应 |
| ⑧⑨ 截断补读 | ⚠️ 部分可省 | 段号范围可用对口工具一次取，而非字符分页试凑 |

**本可 1-2 次工具调用拿到可读的 2150-2241 段，实际用了 9 次**。多出来的 7 次，每次都把"转义后的原文/解码脚本输出/中间文件"塞进上下文——正是账本里"巨型轮 input 9 万+"的一种微观来源。

## 4. 对口方案（按性价比排序，待 Owner 拍板）

### A. 修工具描述（零风险，最高性价比）

`deskmate/perception/server.py` 的 `read_file` / `read_chapter` 描述明确写上：

- 「支持 .docx（自动抽取正文，无需 officecli，不产生转义）」
- 「读整章/连续正文优先 read_chapter；按字符续读用 read_file 的 offset」
- 把"读稿首选工具"的指引写进 `deskmate.md` persona 或对应 writing skill。

**效果**：agent 第一步就用对工具，省掉 ①②⑤⑥⑦ 全部转义折腾。改文档不动逻辑，零风险。

### B. 暴露「按段号范围读」的 MCP 工具（小改动，中等收益）

把 `canon.py` 的段号能力包装成 MCP 工具，例如：

```python
@mcp.tool()
def read_paragraphs(path: str, start: int, end: int) -> str:
    """按段号范围读正文逐字原文（1-based 行号），一次返回 [start, end] 全部段落。
    用于"读第 2150-2241 段"这类细粒度定位，不走字符分页，不会截断。"""
```

放在 `deskmate/perception/server.py`（和 read_file 同处），内部复用 `canon.paragraphs()` 的段号口径。
**效果**：⑧⑨ 的截断补读消失，段号范围一次取全。

### C. 纠正 `writing_context.py:261` 的反向指引（零风险）

把「读 docx 用 officecli view 并带 TMPDIR」改成「读 docx 正文优先用 perception.read_file（自带 docx 抽取、无转义）；需要章级用 read_chapter；officecli 仅用于编辑/导出」。

## 5. 与账单的关系

按小米计费（未命中输入 100 Credits/token），这些无效的中间输出（转义文本、脚本、重复原文）**全部按未命中输入计价**——它们还因为内容每次不同（时间戳、转义细节）而**无法命中缓存**。所以工具不对口 = 双重浪费（全价 + 无法缓存）。

结合前面的缓存优化，两件事是互补的：
- 缓存优化：让**必要**的重复内容变便宜
- 工具对口：让**不必要**的内容根本不产生

## 8. 紧急回归修复：schema 预算误裁查证工具（2026-11-19 晚）

**现象**：用户贴出小桔回复"我这一轮手上没挂 search_history，也没有 web_search……你把工具挂上我这就查"。
**根因**：日志 `~/.config/coworker/logs/openworker-server.log:152/171/313` 明确记录

```
tool schema budget 20000 chars: dropped 123 tools: ..., web_search, web_fetch,
search_history, history_library_check, search_private, ...
```

这是我上一轮 PR5 引入的回归：`web_search`/`search_history` 排在 100+ MCP 工具之后，按注册顺序裁剪时被预算裁掉。模型看不到工具定义，误以为没挂，转而准备凭记忆回答——**违反"史料库过了才算数"的查证红线**。我之前"被裁工具仍可硬调用"的说法是纸上谈兵，模型根本不知道它们存在。

**修复**（`coworker/engine.py`）：
- 新增 `_PINNED_TOOLS`：查证（web_search/search_history/history_library_check/search_private）、读稿（read_file/read_chapter/read_paragraphs）、技能（load_skill/save_skill）、问人等核心工具**无条件保留**，不参与裁剪。
- `_select_tool_schemas` 改为"标记删除、原位输出"：保持 schema 原始顺序（协议/缓存敏感），pinned 按原位置保留，其余仍受 20000 字符预算约束。
- 新增 `tests/test_tool_schema_pinned.py` 5 条用例（核心保留/顺序不变/预算仍生效/0 关闭）。验证：7 个核心工具全保留、顺序不变、被裁数从 123 降到 92（预算收益仍在），15 passed。

**⚠️ 生效条件**：这是 Python 后端代码，需要**重启 openworker-server**（或重开会话）后新引擎才会用修复后的逻辑；当前正在跑的会话仍是旧逻辑。重启后日志里应不再出现 web_search/search_history 被 dropped。

## 6. 复核方法

优化后，"读第 N-M 段原文"类任务应满足：
- 工具调用次数 ≤ 2（一次段号读取 + 可选一次补读）
- 无 `officecli view` / python 解码 / 重复 Read
- 账本里该类任务的未命中 input 显著下降
