## 〇、一句话

**把「谁是主脑」从隐含假设变成代码里可读的事实**：本地用心跳租约宣告「我在场」，
云端读到在场租约即让出**可让渡**的活，只保留**云端专属**能力。租约过期云端自动接管，
本地回来再自动收回 —— 全程无需通知、无需你手动开关。

## 二、目标与非目标

### 2.1 目标

1. 本地在场时，云端**不重复**做本地能做的事 —— 直接省下火山/小米额度。
2. 本地不在场（关机/睡眠/出门）时，云端**自动接管**，能力不丢。
3. 云端**专属**能力（Mac 关机时也要跑的）**任何时候都不受影响**。
4. 切换**零操作**：不需要你点任何开关，不需要通知云端。

### 2.2 非目标（明确不做，防范围膨胀）

- ❌ 不下线云端小桔的任何能力（你 10-09 明确「不是说要关云端」）。
- ❌ 不新建「看世界」/ `observation` 生产者。
- ❌ 不改台账 schema、不改同步协议、不改递送（handoff）逻辑 —— 那是 §对接文档已定的部分。
- ❌ 不做「谁更聪明谁做」的动态竞标（复杂度不划算，见 §七 备选方案讨论）。

## 三、核心机制：节点角色 + 在场租约

### 3.1 为什么是「租约」而不是「实时检测」

你原话是「云端检测到本地的动作后，就停了」。我建议改成**前置声明 + 租约**，理由：

| | 实时检测（云端看本地在干嘛） | 前置声明 + 租约（推荐） |
|---|---|---|
| 延迟 | 云端要等同步窗口才知道（:02，每小时） | 本地启动即生效，**零延迟** |
| 可靠性 | 依赖本地动作恰好被同步 | 依赖心跳本身，心跳断了=退化为单机模式，**fail-safe** |
| 成本 | 云端每次判断都要拉状态 | 云端每窗口读一行 |
| 竞态 | 两端同时认为对方不在 → 双跑 | 租约有明确 owner，**天然单主** |

**关键性质**：租约是**单调的**——本地在，就一直是主；本地不在，租约过期，云端接管。
不存在「两端同时自认主」的脑裂，因为只有本地会发主脑租约。

### 3.2 数据模型（新增一张小表，不进 `SYNC_TABLES`）

```sql
node_presence:
  node        TEXT PRIMARY KEY   -- 'mac' | 'cloud'
  role        TEXT              -- 'primary' | 'standalone'
  heartbeat_at TEXT              -- ISO 时间戳
  ```

```
为什么**不**进 `SYNC_TABLES`：它描述的是「设备此刻在不在」，是**易失状态**，
不是需要跨端收敛的业务事实。若走同步，云端读到的是**几十分钟前**的 Mac 心跳（同步窗口每小时），
租约就失去了时效意义。→ **各自本地写，云端通过既有隧道直接读 Mac 的当前值**。

> 这是本设计与 §对接文档的一处刻意分歧，已标注。读法：§11.2①的教训针对的是**业务数据**，
> 本表是**瞬时状态**，两者语义不同。

### 3.3 判定逻辑

```python
def local_primary(ttl_minutes=90) -> bool:
    """Mac 是否在场且自任主脑（fail-safe：读不到 = 不在场 = 云端接管）。"""
```

| 场景 | 本地行为 | 云端行为 |
|---|---|---|
| Mac 开机在用 | 心跳每 30s 刷新 | 读到新鲜心跳 ⇒ **让渡**可让渡活 |
| Mac 睡眠/关机 | 心跳停止 | 租约过期 ⇒ **接管**全部可让渡活 |
| Mac 崩溃 | 心跳停止 | 同上（fail-safe 落在云端，能力不丢） |
| 两端同时启动 | 只有本地发主脑租约 | 云端无条件让渡 |
| 隧道断（云读不到 Mac） | 本地照常工作 | **视为不在场** ⇒ 接管（宁可多干，不漏干） |

**TTL 取 90 分钟**的依据：云端同步窗口是每小时（:02），租约要能跨过一个完整窗口而不误判过期。

### 3.5 `automation` 是什么（拍板前必读）

**它不是「执行任务」的，是「体检报告员」** —— 自己不跑任何活，只回答一件事：
**定时任务有没有跑砸。**

盯的就是萧哥现有的 5 个定时任务（实测 `automation.db`）：

| 任务 | cron |
|---|---|
| 写作营每日文章 | 09:30 |
| AI圈·网文观察日报 | 09:40 |
| 每日读书：萧盛已出版作品 | 10:00 |
| AI圈·小桔每日自主巡检 | 10:30 |
| 进度跟踪：国子监秘闻录 | 16:00（工作日） |

**只报两种坏情况**：① 该跑没跑成（cron 到点无执行记录）；② **跑了但零产出** ——
回执写 `ok` 但实际啥也没干（代码注释原话：「专为火山限额跑空设计」）。

实测报过的 5 条全是这两种形态，且**跨两端都有**：

```
[10-07 cloud] 「AI圈轮巡」回执 ok，但实际没产出（疑似火山限额跑空）
[10-07 mac  ] 「进度跟踪：国子监秘闻录」该跑却还没跑成
[10-09 mac  ] 「每日读书：萧盛已出版作品」该跑却还没跑成
```

§对接文档 §11.3 把它列为「**价值最高的一条**」：过去任务跑空只有人肉发现，现在她自己报告。

#### ⚠️ 但它现在**在误报**（2026-10-09 萧哥实测指出，实测复核坐实）

上一版我写「那次限额事故正是它本该提醒你的」—— **该结论错误，此处更正**。
实测：台账里 5 条 `automation` **全是 `miss`，没有一条是 `zero`**。
即「零产出」判据**从未生效**，而「该跑没跑成」判据**在乱报**。
**净效果是噪声源，不是保护网。**

**三重缺陷叠加（全部实测确认）**：

| # | 缺陷 | 实测证据 |
|---|---|---|
| ① | `last_run` **只在任务结束时更新**，生产者在**运行期间**读它 | 10-09 读书任务 10:00:57 开始、**10:37:16 结束**，而误报时间 **10:34:13** ⇒ evidence 写 `last_run=2026-10-08 10:00`。**跑了 36 分钟，它在第 34 分钟报「没跑成」** |
| ② | 硬锚点判据写 `task_type in ("daily_reading", "progress_tracking")`，但**实测 5 个任务的 `task_type` 全是 `None`** | 该判据对**所有任务永不触发**；而 `timeline.jsonl` 里其实**有**正确记录（10-09 `daily_reading` 就在） |
| ③ | 零产出用**关键词匹配**判失败，且假设「产出必进 artifacts」 | 失败词表含**抱歉/失败/无法/火山/额度**；而成功汇报原文就含「不属本次清理范围，我不擅自删除」，且读书任务 `artifacts: []`（正文写进 `.deskmate/tmp_reading/`，不走 artifact 通道） |

**⇒ 必修，否则任何分工/节流优化都只是在给一个坏传感器调参。**
详见 §五·决定 4。
#### 为什么它是分工特例

**两端各有一份互不相干的 `automation.db`，且都不在 `SYNC_TABLES`**：

| | 本地 | 云端 |
|---|---|---|
| 任务库落点 | `~/.config/coworker/automation.db` | `/var/lib/openworker/automation.db` |
| 是否同步 | ❌ | ❌ |

⇒ 本地排的任务，**云端根本不知道它们存在**；生产者只读**本机**那份库，
所以它只能报告「我这边」的任务。

| 方案 | 你在用电脑时 | 出门/关机时 |
|---|---|---|
| **完全让渡** | ✅ 云端报云端的任务 | ✅ 云端继续报 |
| | ❌ **本地 5 个任务出问题无人报** | — |
| **条件接管**（推荐） | ✅ 两端都报，靠**共享节流**保证每小时只跑一轮 | ✅ 云端继续报 |

**完全让渡的漏洞**：你在本地排的 5 个任务，Mac 一关就彻底没人盯。

**方案（推荐）**：`automation` **不参与让渡**，但加**共享节流**（§四·第 2 层）——
两端仍各跑，靠共享簿记让「同一小时只有一端真跑」。既省 token，又不丢 Mac 关机时的覆盖。

## 四、四层保险（缺一层都不够，按收益排序）

> ⚠️ **2026-10-09 补充**：初稿只有三层（原 R1/R2/R3）。实测发现 R0（§1.2 / §1.4）
> 才是浪费大头，且**与节点分工完全无关** —— 本地单脑自己就能把一个史实问题判 34 次。
> 故新增**第 0 层**并置于最前。**若只做一件事，做第 0 层。**

### 第 0 层：指纹锚定优先（治 R0 · **收益最大、可独立落地**）

现状 ``_deterministic_id`` 的指纹是 ``content`` 的 sha1，而模型每次重判都换措辞
（"你的理解没错…" / "抱歉我之前的设定搞反了…" / "这里确实存在矛盾…"）⇒ 指纹全变 ⇒ 零合并。

**两个改法，建议同时上**：

1. **`plot_contradiction` 必须带 `anchor`**（§对接文档 §11.9 的「方案 D」已有 `finding_key` 通道，
   但 judge 不保证每次都给）。缺 anchor 时应**拒绝落库**，而不是退回 content-hash
   —— 一个没有锚点的矛盾判定，**下次还会被判出来 33 次**，落库只是把重复搬进数据库。
2. **退回 content-hash 的路径改为模糊去重**：落库前用 `_bigrams` 算相似度，
   与近 N 条同 `kind` 记录比较，超阈值则**合并回原行**（更新证据 + 置信度）而非新建。
   `ledger.py` 已有 `_bigrams` / `_relevance_score_bigram`，**零新算法**。

> **这一层不需要任何节点概念、不改同步、不改 schema**，是四层里唯一能单独 PR 落地的。
> 34 条 → 1 行的效果，**单这一层就能砍掉约 29% 的台账量与对应的重复 judge 调用**。

### 第 1 层：生产者门（主路径 · 省 token）

```
run_producers_all() / tick 的 cloud_audit 分支
    → 先问 should_run(source, node)
    → 本地在场时，云端对可让渡 source 直接 return 0（**连 judge 都不调**）
```

省 token 的关键是**在调 LLM 之前就返回**。`cloud_audit` 的成本大头是
`judge_proactive_action`（一次完整 LLM 推理），门必须开在它之前。

### 第 2 层：共享节流簿记（治 R2 —— **最容易被漏掉的一层**）

把 `proactivity_meta` 的节流 key **从本端簿记改为跨端可见**，或更简单：
在 ledger 里查 `proactive_ledger` 的 `created_at` 判断「本小时本 source 是否已产出过」。

```python
# 伪代码：两端共享的节流判据
def _throttled_shared(source, window_s, base_dir):
    # 查 ledger：该 source 在 window 内是否已有任一节点的产出
    ```
    SELECT 1 FROM proactive_ledger
    WHERE source=? AND created_at > ?
    LIMIT 1
```
```

**这一层独立于第 1 层**：即使分工表配错、或未来新增生产者忘了加门，
**两端也不会在同一小时各烧一轮**。它是对 R2 的直接根治。

### 第 3 层：跨节点内容级去重（治 §1.3 的跨端重复）

现状只按 `source:kind:指纹` 去重，模型改写措辞即失效。补一层：

```
同 (kind, anchor) 或 内容相似度 > 阈值 且 **另一节点**已产出 → 跳过
```
复用第 0 层已落地的 `_bigrams`/`_relevance_score_bigram`（`ledger.py` 已有，无需新算法）。

> **与第 0 层的分工**（避免重复设计）：第 0 层管**同节点内**的措辞漂移（34→1），
> 第 3 层只管**跨节点**撞车（`最近改《国子监秘闻录》` mac×5+cloud×1）。
> **第 3 层必须限定「另一节点」** —— 若不限定，它会与第 0 层重复且更激进：
> 同节点内两次**真正不同**的讨论会被误合并。限定跨节点后误杀面小得多，
> 且跨端撞车本就该合并。

## 七、为什么不做「实时检测本地动作」（备选方案讨论）

你的原方案是「云端检测到本地动作后停」。我评估后不推荐，理由已在 §3.1 列出，

## 附录 B：automation 已恢复（2026-10-10，`b54cf71`）

萧哥拍板恢复。上线前用真实 `automation.db` 试跑，**抓到方案 B 自身的漏洞**：

实测 10-10 06:49 跑体检，5 个任务**全部**被报成「今天回执 ok 但 timeline 查无实产」——
而它们 cron 是 09:30/09:40/10:00/10:30/16:00，最近一次全在 10-09。**它们连跑都还没跑。**

这是缺陷①「用 `last_run` 判运行中」的**同型错误**：换了字段，但同样没问「此刻该不该已经有产出」。
判据②原本只看今天 timeline 有无记录，缺一个「今天是否已到点」的前置条件。

修法：新增 `_cron_due_today(cron, now)`，判据②要求 `due_today 且 ran_today` 同时成立。

顺带修该函数自身的**时区 bug**：本地午夜原用 `now % 86400` 算——那是 **UTC 午夜**。
本机 UTC+8 时 `now=06:49` 会落到前一天 22:49，起点错一天。改用 `datetime` 构造本地 00:00。

`MISREPORTING` 清空但**保留该模块**：它是「当前不可信生产者」的集中登记处，
将来再出误报只需往里加名字，不必改 `ledger.py`。

**验证**：真实库 0 误报；三场景（真故障报 / 正常不报 / 无 timeline 保守不报）全对；71 passed。

### 教训

修「误报」时容易只盯着旧症状，**同类错误会以别的形式复发**。本轮两处根源相同：

1. 用了「上次跑的时间」，没问「本次该不该已经跑」；
2. 用了「相对偏移」（`now % 86400`），没问「时区是什么」。

判据类代码的每条分支都该先回答：**此刻是否已具备判断条件？**
