# 创作流水线 · 对话流化重构方案

> 状态：方案 v0.1（待评审）
> 目标：把「审批状态机」重构为「原生对话流」——创作即对话，用户是导演，专家是被召唤的顾问。

---

## 1. 问题定义（为什么重构）

现状（代码事实）：
- 创作流水线是 **7 阶段强制状态机**：创建 → 写大纲 → 审大纲 → 主编拍板 → 写剧本 → 审剧本 → 主编拍板 → done。
- 前端以 **步骤条 + 阶段按钮** 呈现，用户必须逐关点击推进。
- 专家（大纲专家/审核专家/主编/圆桌）是**必经关卡**，不是可召唤的顾问。
- 审核意见藏在独立面板；审核标准（criteria）写死在代码里不展示；「主编」其实是用户自己，但界面让它看起来像神秘黑箱。

用户痛点：
1. **流程繁琐**：点「开始创作」不开始，还得再点「写大纲」；7 关逐一点击。
2. **不透明**：审了什么、怎么审、标准是什么、意见是什么——不可见，用户是「工具人」。

根因：**把「多专家协作」实现成了「多阶段强制流水线」，可视化展示的是流程而不是协作**。
对比 WorkBuddy 专家团（已调研，拆包验证）：专家 = 可选插件，**内联卡片推荐 + 用户主动「召唤」**，一次一个、围绕当前需求、意见进对话流、用户是雇主。本质相同（多 Agent 协助创作），体现完全不同。

---

## 2. 目标与设计原则

**一句话：把整个创作流程放入原生对话流，用户在每个节点看到专家在做什么、为什么、意见是什么，并随时决策。**

设计原则：
1. **创作即对话**：概念 → 大纲 → 剧本 → 定稿，全流程在一条对话线程里发生；没有「按钮关卡」。
2. **用户是导演，专家是顾问**：专家随叫随到（@召唤 / 建议卡），意见内联，用户随时拍板。
3. **透明 > 仪式**：审核标准可见、审核过程可见、每个产出可追溯、定稿可回看。
4. **保留资产**：生成能力（写大纲/写剧本）、改编圣经（novel_index）、SSE 流式、圆桌研讨、docx 落地——全部保留，只换「流程骨架 + 呈现层」。
5. **状态机降级为数据层**：pipeline 状态机保留为「防并发 + 状态记录」的内部约束，不再作为用户可见的关卡。

---

## 3. 目标形态（信息架构）

一条对话线程，消息类型分 7 种：

| 消息类型 | 内容 | 呈现 | 用户操作 |
|---|---|---|---|
| `user` | 用户指令/决策/打回意见 | 普通对话气泡 | 输入 |
| `progress` | 生成中（正在写大纲…） | 流式进度条（SSE） | 无 |
| `artifact` | 产出物：大纲/剧本全文 | 长文卡（折叠/预览/滚动） | **定稿 / 重写+意见 / @专家讨论** |
| `review` | 审核意见卡 | 结论徽标 + 逐条标准 + 可执行修改 | 采纳/回复讨论 |
| `milestone` | 定稿节点（含 docx 链接） | 里程碑卡 | 打开 docx / 续写 |
| `expert_card` | 建议召唤某专家 | 内联卡片（用户决定） | **召唤 / 跳过** |
| `roundtable` | 圆桌研讨流 | 多专家发言流（SSE） | 参与/采纳 |

**状态徽标**（非阻塞，只读）：顶部一行「大纲 ✅ · 剧本 创作中 · 第2集 待写」，作参考，不锁流程。

**交互模型**：
- 用户自由输入；系统识别意图 → 触发对应生成/审核/召唤 → 结果以消息回流。
- 用户决策 = 对话回复：「定稿」「这版方向不对，重写，强调动机X」「@审核专家 说说逻辑硬伤」「召唤圆桌终审」。
- 专家意见内联：审核完成后，审核意见卡直接跟在产出卡下方，不跳转面板。

## 4. 方案分层

### Phase A：对话流化（先解决「工具人错觉」，改动集中在前端）

**前端**
1. 新建 `CreationChatView.tsx`（复用 `TeamChatView` 骨架：作者分组 / @mention / composer / 轮询）。
2. 消息渲染器扩展：`progress` / `artifact` / `review` / `milestone` / `expert_card` / `roundtable` 六种富消息卡片。
3. `CreationPipelineView` 降级为「结构化视图」：只读状态总览 + 历史产出回看（可选入口，不再是主界面）。
4. 步骤条 → 状态徽标（只读）。

**后端**
5. 新增创作对话存储：`{author, author_role, type, text, meta, seq, ts}`（type 对应 7 种消息），按 `space` 持久化。
6. 新增「对话意图 → 动作」解释器 `parse_intent(text)`：识别 写大纲/重写/定稿/打回/@专家/圆桌 等指令 → 调现有 executor 方法。
7. 复用现有 SSE：生成进度（note/progress）→ `progress` 消息；完成 → `artifact` 消息；审核意见 → `review` 消息。
8. **主编拍板**：用户对话里说「定稿」→ 解释器调 `lead_verdict`；说「重写：xxx」→ 记录 user_note 并调打回。**主编=用户这件事直接在 UI 说明**（「你决定：定稿 / 重写」）。

### Phase B：专家可召唤化（对齐 WorkBuddy）

**后端**
9. 专家以对话参与者注册（大纲专家 / 审核专家 / 编剧 / 圆桌 7 专家），复用 `coworker/personas` + 现有专家调用。
10. 新增 `@召唤`：对话里 `@大纲专家` → 唤起该角色在当前上下文发言（复用 roundtable 的专家调用 + @mention 唤醒语义）。
11. 新增专家建议卡：当检测到「需要专业判断」时，后端返回 `expert_card` 消息，**用户决定召唤/跳过**（对齐 recommend-experts：不静默启用、不重复打扰）。

### Phase C：透明化增强

**后端**
12. 审核标准可见：`review` 消息携带 criteria 全文（「按这 4 条标准审：结构/契合原著/无硬伤/…」）。
13. 审核过程流式：审核专家按标准逐条核验，SSE 逐条上报（复用圆桌 `info` 流式），用户看到「正在核对史实…正在核对逻辑…」。

**前端**
14. 审核卡展示标准 + 逐条核验过程 + 最终结论与可执行意见。

## 6. 共存与迁移

- **数据层不变**：老 pipeline 状态机、草稿、docx 全保留；对话流只是新的「用户入口 + 呈现」。
- **已建项目无缝续接**：对话视图读取现有 snapshot → 从当前状态续起（大纲已定稿则直接进入剧本对话）。
- **两视图并存**：对话流为主视图；结构化视图作为「总览/回看」保留，可随时切换。
- **分集模式**：消息带 `episode` 标签，产出卡标注「第X集」；对话指令作用于当前集。

---

## 7. 风险与取舍

| 风险 | 对策 |
|---|---|
| 对话自由度高 → 意图识别不准 | 解释器兜底：识别不了就回退为「对话求助」消息（列出可选指令），不静默乱动 |
| 长文产出在对话流里可读性差 | artifact 默认折叠，点击展开/进预览阅读器（复用现有预览阅读器） |
| 并发生成 | 沿用 busy 锁：同一空间同时只跑一个生成任务，其余排队/提示 |
| 用户可能仍想要「一键直通」 | 提供「一键全流程」对话指令（写大纲→写剧本→定稿连续跑，随时可打断） |
| 老用户习惯状态机视图 | 两视图并存，默认进对话流，可切回结构化视图 |

---

## 8. 验收标准

1. 创建项目后，**无需点任何阶段按钮**，直接在对话里推进：输入「写大纲」即开始流式生成。
2. 大纲/剧本产出以对话消息呈现，每条带「定稿 / 重写+意见 / @专家讨论」。
3. 审核意见卡内联：展示审核标准 + 逐条核验过程 + 结论 + 可执行修改意见。
4. 用户拍板=对话回复（定稿 / 重写：xxx），**全程无黑箱、无神秘主编**。
5. 随时 `@专家` 召唤，专家在当前上下文发言；建议卡由用户决定是否启用。
6. 圆桌终审流式发言、docx 落地、原著圣经注入，全部保留。
7. 分集模式按集对话、按集定稿、按集出 docx。

---

## 9. 实施顺序建议

1. **Phase A 后端**：对话存储 + 意图解释器 + 创作对话 SSE（约半天）
2. **Phase A 前端**：CreationChatView + 富消息渲染 + 视图降级（约 1 天）
3. **Phase B**：专家 @召唤 + 建议卡（约 1 天）
4. **Phase C**：审核标准/过程流式透明化（约半天）
5. 端到端验证 + 回归（旧 pipeline 不受影响）
