# 读稿往返瓶颈诊断（2026-11-20）

> 承接《上下文总预算实验报告_2026-11-20.md》。上一份证明了"砍上下文走不通"，
> 这一份回答"那 9 分钟到底花在哪、能不能合成几次"。结论先行：**真凶是读稿碎步
> 导致的往返次数，不是引擎慢，也不是上下文字符总量。**

## 一、证据来源与口径

- 数据源：`~/.deskmate/deskmate.db:llm_usage`，窗口 2026-11-20 14:30–14:42（覆盖萧哥
  那道"归营路线"提问）。
- 分类方法：**工具轮**判定 = `completion_chars == 0 且 completion_tokens < 3000`
  （模型只吐 tool_call、没有正文）；**正文轮** = 有正文输出。
- 诚实标注：
  1. 账本**没有 tool name 字段**，"工具轮 = 读稿"是基于三个特征的高置信推断——
     input 高达 6–10 万、completion 为 0、且该窗口的任务是"先读原文再比对路线"。
     不是从工具名直接看到的。
  2. `cache_read` 累计值超过 `input`（工具轮 120%、正文轮 175%），说明 mimo 的缓存
     字段是**跨轮累计/语义口径**，不能当精确命中率。故本文**不宣称省了多少 token**，
     只谈可确证的**往返次数与首字延迟**。

## 二、实测数据（40 次调用）

| 类别 | 次数 | input 合计 | 首字合计 | stream 合计 |
|---|---|---|---|---|
| 工具轮 | 20 | 832,607 token | 107.7 s | 318.7 s |
| 正文轮 | 20 | 568,637 token | 59.0 s | 793.9 s |

- 墙钟跨度 11.6 分钟，全部 stream 累计 1113 s（多轮交错，故累计 > 墙钟）。
- 工具轮 input（83 万）**超过**正文轮（57 万）——读稿重发的量比真正的回答还大。
- 4 次工具轮 `cache_read=0`（前缀失效的那几次），其余大量命中缓存。

## 三、根因链（四步）

1. **读稿工具一次只读一章**：`deskmate/perception/file_reader.py:read_chapter()`
   的 chapter 参数是单个 `str | int`，一次返回一章。
2. **一道题要读多章**：归营路线需比对铜雀→渡口村→翻山→高村 + 夜不收来路，
   至少 4–5 章 → 4–5 次工具调用。
3. **每轮全量重发**：`coworker/engine.py` 的 agent loop 每次迭代把 `self.messages`
   整包发提供应商，读稿结果 append 后下一轮更大 → 复利式膨胀（5.9万→6.5万→8.3万→10.9万）。
4. **compaction 没出手**：触发线 `0.8×128000 = 102400` token，该窗口单次最高
   `input=108666` 仅偶尔越线，绝大多数在 9.6 万以下，**基本不触发**，历史一路累积。

结论：**Hermes 两三分钟，很可能是因为它一次读全文、一次推理出答案；小桔是
"读一章→说一句→再读"的碎步，20 次往返 × 每次几秒到二十几秒首字 = 9 分钟。**
这不是"引擎慢"，是"任务被拆成的往返次数多"。

## 四、被排除的嫌疑（同样重要）

- **上下文字符总量**：昨日实验已证（豁免底线挡住，砍无可砍）。
- **记忆/情绪等旁路 LLM**：`Explore` 全仓核查——deskmate 侧旁路（post_session_summary、
  情绪、skill evolve 等）**根本不写 llm_usage**（它们直连 OpenAI SDK，见
  `deskmate/memory/llm.py:293/548`），且全部是 daemon 线程 / create_task 后台跑，
  `turn_done` 在启动它们之前就发出——**不阻塞用户看到答案**。它们是"记账外烧钱的第二战场"，
  但不是这 9 分钟的主因。
- **底座本身**：无证据。同一模型通道下，差异来自往返次数，不是引擎。

## 五、对症方案（✅ 方案 A 已实现，见第七节）

### 方案 A：一次读多章（最对症，零质量损失）
新增 `read_chapters(path, chapters: list)` 工具，一次调用返回多章正文（各带原有
覆盖率标注），把 4–5 次读稿往返压成 1 次。
- **保质**：正文一字不砍，模型反而能同时看到全部章节做交叉比对（比逐章读更利于发现
  "夜不收来路冲突"这类跨章问题）。
- **风险**：单次返回多章可能顶爆上下文——需要保留单章 `max_chars` 上限 + 总量上限，
  超限时明确告知"分两批读"，不能静默截断。
- **落点**：`deskmate/perception/file_reader.py` 加纯函数 → `perception/server.py`
  加 MCP 工具 → 提示词引导"跨章比对优先一次读多章"。

### 方案 B：降低往返的通用机制（备选）
- 调低 compaction 触发线，让它更早介入（但会引入摘要，有质量风险，需谨慎评估）。
- 合并旁路调用（双份 post_session_summary → 单份）：省 token，但不影响用户等待时间。

### 红线遵守
不碰 reasoning_effort、不减唤醒、不压字数、不压摘要；所有方案以"事实不丢、结论不变"
为前提。先红后绿写契约测试，HEAD 基线同口径比对失败清单。

## 六、一句话结论

**不用换底座。慢的根子在"读稿被拆成 20 次往返"，这是 OpenWorker 上就能修的软肋；
把读稿从"一章一次"改成"一次多章"，往返砍 3/4，正文一字不砍。**

## 七、方案 A 实施记录（2026-11-20 下午，已落地）

萧哥拍板后已实现，涉及三个文件：

| 文件 | 改动 |
|---|---|
| `deskmate/perception/file_reader.py` | 新增纯函数 `read_chapters(path, chapters, *, max_chars_per, max_total, coverage)`；复用 `split_chapters`，按书内顺序返回；顶部一份权威【覆盖率】标注，章内轻量标题不重复；单章超限标"后半未加载"、合计超限列"分两批读"参数、未找到列实际章标题；`coverage=False` 供内部消费者。新增常量 `DEFAULT_MULTI_CHAPTER_TOTAL=120000`（低于压缩触发线）。 |
| `deskmate/perception/server.py` | 新增 `@mcp.tool() read_chapters`，docstring 写明"跨章比对优先用本工具、别逐章往返"；工具清单补一行。 |
| `tests/test_perception_read_chapters.py` | 8 个先红后绿契约测试：多章逐字/标题片段/覆盖率唯一/内部消费者/单章超限/合计分批/找不到/原工具口径不变。 |

- **验证**：9/9 新测试 + 读稿相关既有测试 57/57 全过；MCP 注册确认（11 工具、`read_chapters` 在、schema required=`[path, chapters]`）；`_select_tool_schemas` 48000 预算下 11 个工具全保留、无裁剪。全套回归 `46 failed / 5590 passed`，与上轮基线失败清单逐条一致，零新增红。
- **边界修正**：MCP 签名不能用 `list[str]`——pydantic 会拒绝文档教的整数列表 `[1,3]`；改为无类型 `list` 并加契约测试钉死。
- **端到端演练**（5 章归营稿、每章约 1400 字）：旧路径逐章 `read_chapter`×4 = 4 次往返 6357 字符；新路径 `read_chapters`×1 = 1 次往返 6516 字符（多出的 159 是覆盖率/标题开销）；4 章关键句全在、未点名的第 5 章正文未混入。
- **保质**：正文一字未砍，只加组织与覆盖率；原 `read_chapter`/`list_chapters` 口径不变（1v1 地基红线）。
- **生效条件**：Python 改动重启 app 即生效；这是 MCP 工具（非前端），无需重打包前端。
